# 全平台指标使用矩阵

> 版本：2026-06-26
> 范围：管理员侧栏 21 个菜单入口中出现的核心业务指标。
> 目的：明确同一个指标只能有一个标准口径、一个权威来源、多个页面只做展示。
> 第一事实源：[FlowTennis 全平台数据口径总表](/Users/shaobaolu/Desktop/FlowTennis/flowtennis-mgmt-main/docs/FlowTennis全平台数据口径总表.md)。

---

## 1. 使用规则

1. 本表是指标统一的使用清单，不代表当前代码已经全部按本表实现。
2. `权威来源` 是后续代码必须读取的位置；页面不得绕开它自己计算核心指标。
3. `当前重复计算风险` 用来指导后续审计和 CI，不在本文档里直接改代码。
4. 任何新页面展示本表指标，必须先把页面加到“展示页面”列。
5. 任何新指标上线前，必须先进入数据口径总表，再进入本矩阵。
6. 指标必须区分“全局 cohort 指标”和“当前页面列表指标”；两者不能共用同一个展示名。
7. 当前页面列表指标只能说明当前页面筛选结果，不能反向代表全平台总指标。

## 1.1 普通学员 / 正式学员 / 线索池关系

| 关系 | 统一定义 | 允许展示的位置 | 禁止做法 |
|---|---|---|---|
| 普通学员当前视图 | 当前仍处于体验链、尚未成为正式课包客户的客户；应从统一客户生命周期视图产生 | 普通学员 | 只查 `students` 表；把已成交客户留在普通学员当前列表；把当前列表数字当作全局体验链漏斗 |
| 正式学员当前视图 | 已发生有效正式课包成交的客户；对齐 `COURSE_DEAL_CUSTOMERS` 或正式课包客户口径 | 正式学员 | 和“体验后成交人数”混用；把直接成交排除在正式学员外 |
| 体验链历史漏斗 | 从线索 cohort 看预约、已体验、体验后成交、成交后续费 | 线索池；转化与留存；经营分析 | 用普通学员当前列表倒推历史漏斗 |
| 线索池顶部漏斗 | 必须和转化与留存读取同一指标模型 | 线索池 | 在 `leads.js` 前端本地重算预约 / 已体验 / 体验后成交 |
| 普通学员顶部卡片 | 只展示当前普通学员视图内的预约、已体验、待转化等状态 | 普通学员 | 展示“课程成交”主卡片；把普通学员当前视图和全局成交漏斗直接比较 |
| 正式学员顶部卡片 | 只展示正式课包客户、复购、续购、课包余额等正式教学链指标 | 正式学员 | 和体验后成交人数对齐；把体验后成交当作正式学员总数 |
| 会员管理视图 | 统一客户生命周期中的订场会员账户视图 | 会员管理 | 把会员账户当独立自然人客户表，导致和订场用户、线索池无法互斥 / 串联 |

最小防回退样本：

1. 客户 A：已约体验，但未创建学员档案。必须进入体验链漏斗；如普通学员页面当前能力不能展示，必须明确标注不能代表全量。
2. 客户 B：已创建学员档案，已约体验，未成交。应在普通学员当前视图。
3. 客户 C：已体验后购买正式课包。应退出普通学员当前视图，进入正式学员；同时保留在体验链历史漏斗的“体验后成交”。
4. 客户 D：未体验直接购买正式课包。应进入正式学员和课程成交，但不进入体验后成交。
5. 客户 E：只订场或只储值。可进入线索总成交或订场会员口径，但不进入正式学员。
6. 客户 F：订场用户后成为会员。会员管理必须作为订场用户 / 客户生命周期子视图，不能产生第二个自然人。

## 4. 强门禁方向

| 门禁 | 检查内容 |
|---|---|
| 核心公式唯一性 | 禁止 `public/assets/scripts/pages/*.js` 直接写总成交、转化率、复购率、财务金额等核心公式 |
| 跨页面一致性 | 同一批样本下，线索池 / 转化与留存 / 经营分析输出一致 |
| 学员分层互斥 | 同一客户在同一统计时点不能同时出现在普通学员当前列表和正式学员当前列表 |
| 普通学员来源 | 普通学员当前视图必须来自客户生命周期分层，不能只从 `students` 表筛 |
| 普通学员卡片文案 | 普通学员顶部禁止出现“课程成交”主卡片；正式课包成交指标只能出现在正式学员或转化漏斗 |
| 漏斗历史与当前列表分离 | 体验链历史漏斗不能用普通学员当前列表倒推 |
| 财务一致性 | 财务总览 / 经营总览 / 收款流水 / 入账流水同周期金额守恒 |
| 教练一致性 | 教练课时统计 / 教练人效 / 教练工作台同一教练同周期指标一致 |
| 下拉字典一致性 | 页面下拉选项必须来自 `business-taxonomy.js` 或数据口径总表登记字典 |
| 待补 ID 阻断 | 本矩阵标记 `待补标准 ID` 的核心字段，补 ID 前不得宣称全局统一 |

## 5. Vibecoding 真实踩坑记录

本节只记录 FlowTennis 实际遇到过或已经暴露风险的问题。后续 AI 接手全局统一、页面改造、指标修复、导入修数时，必须先看本节。

1、问题：测试用例缺口，AI 说做到了但实际没做到。
场景描述：测试很松，只测页面能渲染、按钮存在、接口不报错，没有测业务逻辑；更没有测反例。比如普通学员、正式学员、线索池转化这些关系，只测“有字段”，不测“人该不该进这个列表”。
解决方案：每次修 bug 必须加回归测试。测试必须覆盖这次出错的反例，例如已预约但无学员档案、体验后成交、直接成交、只订场、只储值、退款、作废、重复客户。

2、问题：AI 声称“全局统一”，实际只改了部分页面。
场景描述：只改了一个页面、一个字段、一个顶部卡片，就说“全局统一”；然后又说门禁和测试通过。真实原因是门禁只覆盖了它改过的那一小块。
解决方案：凡是说“全局统一”，必须同时给出覆盖矩阵：页面、字段、筛选、顶部卡片、表格列、详情、导出、接口、测试。没覆盖的必须写“未覆盖”，不能说全局。

3、问题：同一个后端接口数据，前端页面又各自拼一遍。
场景描述：几个页面拿的是同一个后端数据，但有的页面自己在前端筛选、合并、补字段、算指标，导致同一批数据在不同页面显示不同数字。
解决方案：核心指标只能在统一 read model / 指标模型里算。页面只能展示结果。禁止页面、接口、脚本各自重新计算同一个业务指标。

4、问题：原始数据库字符串直接暴露到前端。
场景描述：页面显示 `2026-06-26 03:37:16` 这类数据库 ISO 时间，或显示 `shunyi_mapo` 这类内部校区代码，或显示内部 ID、流水 ID、调试字段、拼接痕迹。
解决方案：所有面向运营、教练、用户的展示字段必须经过格式化。时间显示为业务可读格式，校区显示中文标准名，内部 ID 和调试字段默认不展示。

5、问题：让 AI “改全部表格”，它只改了 1 个页面。
场景描述：用户说“所有表格”或“全局”，AI 没先列清单，边看边改，最后只改了当前打开的页面或搜索到的第一个文件。
解决方案：动手前必须先列“要改哪些页面 / 文件 / 字段 / 表格 / 详情 / 导出”。用户确认不少，再开始改。最终回复必须对照这个清单逐项说明完成情况。

6、问题：一个转化数据，三个页面都不一样。
场景描述：线索池、普通学员、经营分析都在展示转化相关数字，但各自口径不同。线索池本地算一套，普通学员从 `students` 表筛，经营分析从后端聚合算。
解决方案：线索池、普通学员、正式学员、转化与留存、经营分析必须读取同一个客户生命周期和指标模型。同一批样本数据必须跨页面输出一致。

7、问题：为了兜底历史数据，AI 自己放宽口径。
场景描述：文档已经定义了标准口径，但代码为了兼容旧数据，把旧字段、备注、状态文案都算进来，导致“看起来数据多了”，但口径变松了。
解决方案：历史字段只能作为输入别名映射到标准字段，不能扩大标准口径。需要兼容旧数据时，先写“旧字段 -> 标准字段”映射和反例测试。

8、问题：文档是约束，但代码还能绕开。
场景描述：文档写了同一个字段只能一个口径，但页面、接口、脚本仍然可以自己算一次。只要某个页面偷懒本地算，就会出现同字段不同结果。
解决方案：文档后必须跟 CI。CI 要检查核心公式唯一性、跨页面一致性、页面禁止本地重算、下拉字典来源、展示字段白名单。

9、问题：AI 修改时只看局部文件。
场景描述：修线索池时只看 `leads.js`，不看经营分析、普通学员、正式学员、读模型和测试；修普通学员时只看 `students.js`，不看客户生命周期。
解决方案：凡是涉及字段、指标、转化、留存、金额、校区、来源、教练归属，必须先做影响面搜索，再列受影响页面和文件。

10、问题：缺少跨页面一致性测试。
场景描述：单页测试都通过，但线索池、转化与留存、经营分析同一指标数字不一致；普通学员和正式学员也可能同人重复出现。
解决方案：必须有跨页面一致性测试。同一批样本下，关键指标要同时验证多个页面或多个 read model 输出一致。

11、问题：普通学员只从 `students` 表筛。
场景描述：已预约体验但还没生成学员档案的人，会被普通学员页漏掉；但线索池或转化漏斗里又算进去了。
解决方案：普通学员当前视图必须来自 `customerLifecycle` / 统一客户生命周期视图。若页面暂时只展示有学员档案的人，必须明确标注“仅学员档案视图”，不能叫全量普通学员。

12、问题：普通学员顶部展示“课程成交”。
场景描述：普通学员页顶部出现“课程成交 22 | 0”这类文案，运营会误以为普通学员里有课程成交；实际上成交后应进入正式学员。
解决方案：普通学员顶部只展示当前普通学员视图内的预约、已体验、待转化等状态。课程成交只放正式学员或转化与留存。

13、问题：正式学员数和体验后成交数混用。
场景描述：正式学员数应该看正式课包客户，但有人拿“体验后成交人数”来对齐，导致直接成交客户被漏掉。
解决方案：正式学员对齐正式课包成交客户；体验后成交只是体验链历史漏斗分子。直接成交进正式学员，不进体验后成交。

14、问题：会员管理被当成独立客户表。
场景描述：订场用户、会员账户、线索客户各自成表，页面如果把会员账户当独立自然人，就会导致同一个人无法串联、重复统计或漏统计。
解决方案：会员管理必须是统一客户生命周期中的订场会员账户视图，是订场用户 / 客户生命周期的子集，不是独立自然人客户表。

15、问题：列表改了，详情、导出、弹窗没改。
场景描述：AI 修改页面时常只改列表列名或顶部卡片，详情抽屉、编辑弹窗、导出 CSV、筛选项仍然是旧字段或旧口径。
解决方案：每个字段必须按“顶部卡片、筛选、列表、详情、编辑弹窗、导出”逐项验收。最终回复必须说明每一项是否覆盖。

16、问题：门禁通过，但覆盖范围太窄。
场景描述：测试只覆盖线索、学员、会员、财务的一小部分，21 个菜单页面没有逐页覆盖。门禁通过不代表全平台正确。
解决方案：门禁结果必须附覆盖范围说明。没有覆盖的页面、字段、指标、下拉，不能用“测试通过”包装成“全部正确”。

17、问题：缓存或前端状态让页面显示旧数据。
场景描述：后端接口返回已经对了，但某个页面仍显示旧数字，因为前端缓存、局部状态、页面本地数组没有刷新。
解决方案：验收要分三层：后端接口返回、前端状态取值、页面展示。只验证接口不够。

18、问题：AI 顺手改大范围代码。
场景描述：原本只是补一个字段或修一个统计，AI 顺手重构文件、改公共组件、改样式、改数据加载链，导致风险扩大。
解决方案：小问题小改。涉及核心读模型、财务、公共状态、页面加载策略、大范围重构，必须先列方案并得到用户确认。

19、问题：提交前不说明没覆盖什么。
场景描述：最终只说“已修复、已测试”，但不说哪些页面没看、哪些场景没测、哪些字段没覆盖。
解决方案：最终回复必须分开写：已改什么、覆盖哪些页面和字段、跑了哪些测试、没覆盖什么、仍有什么风险。

20、问题：旧字段继续扩散成新口径。
场景描述：为了兼容导入，保留了“账号、姓名、需求产品、意向等级”等旧字段，结果后续页面继续拿这些旧字段做展示和筛选。
解决方案：旧字段只能在导入或读取入口映射成标准字段。页面展示、筛选、导出只能使用标准字段名。
