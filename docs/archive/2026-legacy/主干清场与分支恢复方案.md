> 版本：2026-05-12  
> 目标读者：技术负责人、外部架构顾问、接手开发、其他 AI  
> 文档目标：把当前“主工作区脏、`main` 不可信、分支难合并”的问题拆清楚，并给出一套可执行的恢复方案。  
> 使用场景：当技术负责人要决定“先继续开发，还是先收拾主干”时，这份文档用于说明为什么必须先收拾主干，以及怎么收。

## 1. 先说结论

你们现在最大的问题之一，不是“不会用 Git”，而是：

**当前 `main` 和主工作区，已经不再是一个合格的开发基线。**

这会直接导致：

1. 新分支虽然从技术上能开出来，但基线本身不稳定。
2. 分支开发期间，很多改动都在碰同一批高冲突大文件。
3. 合并 `main` 时不是普通冲突，而是“功能逻辑、脏改动、试验代码、未回收上线改动”一起冲突。
4. 最后大家不是在开发功能，而是在人工搬运代码、核对差异、试错回归。

所以：

**如果不先做主干清场，后面所有分支规范、发布规范、测试规范，都会打折扣。**

### 2026-05-12 正式收官补充口径

第一阶段收官后，本轮主干正式收官执行口径补充为：

1. 在新 `main` 正式恢复前，`origin/thread26-staging-latest` 是唯一可信主干收官锚点。
2. 当前旧 `main` 只做差异核查，不再作为第二阶段新需求默认切分支来源。
3. `codex/match-real-launch` 已封存，只能只读比对或人工摘取，不允许整线回流。
4. 其余历史候选与保护分支也不得整分支直接回主干，详见 [2026-05-12-主干正式收官执行清单与风险清单](/Users/shaobaolu/Desktop/FlowTennis/flowtennis-mgmt-main/docs/2026-05-12-主干正式收官执行清单与风险清单.md)。

## 2. 这份文档解决什么问题

这份文档重点回答 6 个问题：

1. 为什么当前 `main` / 主工作区不再可信。
2. 为什么即使新开分支，最后还是难合并。
3. 主干不可信会带来哪些真实业务后果。
4. 什么叫“主干清场”。
5. 主干清场应该按什么顺序做。
6. 清场完成后，日常分支开发怎么恢复。

## 3. 当前真实问题，不是“有点乱”，而是“基线失真”

### 3.1 什么叫基线失真

一个合格的开发主干，应该满足：

1. `main` 能代表当前系统最新可信代码。
2. 主工作区是干净的，不长期挂着一堆未收口改动。
3. 已上线代码、仓库代码、开发基线三者基本一致。
4. 新分支是从“稳定事实”切出去的。

你们现在的问题，是这 4 条都已经被破坏。

### 3.2 当前主工作区的典型症状

从当前仓库状态看，主工作区长期混着：

- 已修改但未收口的核心代码
- 未纳管的新脚本
- 未纳管的新测试
- 大量 `_local/requirements` 文档
- 历史修复脚本
- 可能已上线但未回主干的代码

这说明主工作区不是正常“当前开发现场”，而是：

**功能开发区 + 试验区 + 修数区 + 规划区 + 历史残留区** 的混合体。

### 3.3 为什么这会让你感觉“明明开了新分支，还是很痛”

因为你分支切出去的时候，默认假设是：

- 主干是稳定的
- 你只要处理自己的改动

但现在实际情况是：

- 主干本身就可能夹着历史脏改动
- 高冲突大文件已经在多个方向被修改
- 线上实际状态和仓库主干可能不完全一致

所以你不是在“基于稳定主干加一个功能”，而是在：

**基于一个长期未彻底收口的施工现场，再搭一层施工。**

## 4. 为什么分支开发最后会困难重重

这件事必须拆成技术原因，而不能只说“冲突多”。

### 4.1 原因 1：主干不干净

如果主工作区长期挂着几十个改动、很多新文件没纳管，那么：

- 新分支切出去时，心理上以为切的是“当前正确版本”
- 实际切出去的是“当前混合状态”

这会导致后续每次合并都要问：

- 这段改动是正式功能还是临时试验？
- 这段代码是不是已经上线但没回收？
- 这个脚本到底是应该进主干还是只用于本地修数？

### 4.2 原因 2：关键文件冲突密度太高

当前最危险的几个文件：

- `api/index.js`
- `public/index.html`
- `public/assets/scripts/core/state.js`
- `public/assets/scripts/core/bootstrap.js`
- `public/assets/scripts/pages/schedule.js`
- `public/assets/scripts/pages/coachops.js`
- `public/assets/scripts/pages/courts.js`
- `wechat-miniprogram/miniprogram/pages/schedule/schedule.js`

这些文件有几个共同点：

1. 大
2. 共享逻辑多
3. 多个需求都会碰
4. 一个改动不容易完全局部化

所以分支合并时不是简单行级冲突，而是：

**业务逻辑冲突。**

### 4.3 原因 3：需求不是局部改动，而是跨链路改动

你们很多功能都不是只改一个页面。

例如课包相关需求，往往同时碰：

- `packages`
- `purchases`
- `entitlements`
- `schedule`
- `finance`
- 小程序显示

这意味着：

- 一个需求横跨多表
- 横跨多页面
- 横跨多个端
- 横跨前后端

这种改动天然就比普通局部功能更难合并。

### 4.4 原因 4：存在“已上线但未彻底回主干”的可能

你已经明确感觉到：

“有些东西明明上线了，为什么主工作区还在改？”

这在工程上通常说明几种情况之一：

1. 上线是从别的分支 / 工作副本发出去的
2. 发布时做过人工搬运
3. 某些临时修复只在线上路径存在，没回主干
4. 文档、脚本、测试和主功能没有同步收口

结果就是：

- `prod` 状态
- `main` 状态
- 主工作区状态

三者可能不再完全一致。

一旦三者不一致，分支开发的合并难度就会急剧上升。

### 4.5 原因 5：功能开发和修数脚本混在同一主干

当前同一个仓库里既有：

- 正常产品功能
- 修复脚本
- 审计脚本
- 导入脚本
- 历史补账逻辑

这会造成两个问题：

1. 功能开发的主干被运维性质改动污染
2. 功能分支和修数分支经常碰到同一批表、同一批规则

## 5. 主干失真会造成哪些具体业务后果

这不是纯工程洁癖，而是会直接影响业务。

### 后果 1：开发时间被代码搬运吞掉

表现为：

- 功能实现本身很快
- 最后大量时间花在“从旧分支一点点挪到新基线”

### 后果 2：回归范围不可控

因为你根本不确定当前待合并改动里，哪些是：

- 本次需求
- 历史残留
- 临时修数
- 已上线未回收

### 后果 3：上线风险显著上升

因为你不是在发布一个清晰的功能集合，而是在发布：

**一坨掺杂历史残留的混合改动。**

### 后果 4：团队协作越来越慢

随着主干越来越不可信，每个人都会倾向于：

- 少合并
- 多拖延
- 多人工搬运
- 不敢重构

最终系统只会越来越难动。

## 6. 什么叫“主干清场”

主干清场不是：

- 把所有未提交改动一把清掉
- 或者简单 `git stash`

这会很危险。

主干清场的正确含义是：

**把主工作区和 `main` 重新恢复成一个唯一可信、可继续开发、可继续开分支的稳定基线。**

它包含 4 个动作：

1. 识别现有改动到底属于什么类别
2. 决定哪些必须回主干，哪些必须隔离
3. 把主干收口成清晰状态
4. 建立以后不再失真的制度

---

## 7. 主干清场前，先做改动分类

这是第一步，不能跳过。

当前所有改动必须强制分类成下面 6 类：

### A 类：已上线且应长期保留的正式代码

处理原则：

- 必须补回 `main`
- 必须补对应测试和说明

### B 类：已开发完成但未上线的功能代码

处理原则：

- 单独放进 `feature/*` 分支
- 不允许继续挂在主工作区

### C 类：线上紧急修复代码

处理原则：

- 单独放进 `hotfix/*` 分支
- 必须标注修复原因和影响范围

### D 类：修数 / 审计 / 导入脚本

处理原则：

- 不应继续混在普通功能开发流里
- 应归入 `ops/*` 分支或 `ops/` 目录管理

### E 类：试验性 / 半成品 / 不确定是否保留的改动

处理原则：

- 单独归档
- 不允许继续污染主干

### F 类：临时规划文档 / 需求文档

处理原则：

- 要么归档到文档区
- 要么转入正式项目文档体系

## 8. 主干清场执行步骤

这里给的是可以落地执行的顺序。

### 第 1 步：冻结新需求进入主干

在主干清场期间：

- 停止往主工作区继续堆新功能
- 停止边清场边继续混开发

否则永远清不完。

### 第 2 步：盘点“线上真实状态”

技术负责人必须先回答：

1. 当前线上实际跑的是哪一个提交 / 哪个分支逻辑
2. 有没有线上热修没回主干
3. 有没有已上线但只存在于本地工作区的改动

如果这一步不做，后面清理出来的 `main` 仍然可能不是生产事实。

### 第 3 步：导出当前主工作区改动清单

需要明确列出：

1. 已修改文件
2. 未跟踪新文件
3. 哪些属于功能代码
4. 哪些属于脚本
5. 哪些属于测试
6. 哪些属于文档

### 第 4 步：按 A/B/C/D/E/F 六类归档

这一步必须人工判断，不要自动化瞎分。

### 第 5 步：先收 A 类

也就是先把：

- 已上线
- 应长期保留

的正式代码回主干。

因为这部分最影响“主干是否能重新代表真实系统”。

### 第 6 步：再拆 B/C/D/E/F

把剩余内容分别转走：

- 功能去功能分支
- hotfix 去热修分支
- ops 去运维分支
- 试验性改动去归档分支
- 文档去正式文档区

### 第 7 步：重新生成干净 `main`

这一步完成后，标准应该是：

1. `git status` 干净
2. `main` 能代表当前可用产品状态
3. 核心测试能通过
4. 财务快照数值能对齐

### 第 8 步：完成正式扶正并公告唯一来源

这一步必须明确落字：

1. 新 `main` 是基于 `origin/thread26-staging-latest` 的审阅后收口结果
2. 从这一步开始，新的 `feature/*`、`hotfix/*`、`ops/*` 才允许从新 `main` 切出
3. 在这一步完成前，所有新分支仍只能从 `origin/thread26-staging-latest` 切出
4. 责任拍板人必须明确宣布“旧 `main` 封口完成，新 `main` 已恢复可用”

## 9. 主干清场后的分支恢复标准

主干清场不是结束，恢复可持续开发才是目标。

清场完成后，新的规则必须是：

### 9.1 `main` 只放“当前可信可上线状态”

不允许再让 `main` 变成：

- 半成品堆积区
- 本地试验区
- 修数脚本临时停放区

### 9.2 所有新需求必须单独 `feature/*`

一个功能一个分支。

补充：

1. 在新 `main` 正式恢复前，所有新需求默认从 `origin/thread26-staging-latest` 切出。
2. 恢复完成后，所有新需求再统一从新 `main` 切出。

### 9.3 所有线上问题必须单独 `hotfix/*`

不要再在普通功能分支里顺手修线上问题。

### 9.4 所有修数脚本必须单独 `ops/*`

不要继续混在主功能流里。

### 9.5 合并前必须先同步最新 `main`

这样可以把冲突尽量前移，而不是拖到最后一起炸。

### 9.6 历史分支不得整线回流

以下分支默认只允许只读比对或人工摘取：

1. `codex/match-real-launch`
2. `legacy/local-main`
3. `protect/main-uncommitted-20260428`
4. `verify/main-baseline`
5. `staging-latest-candidate`
6. `codex/clean-main`
7. `codex/match-main-merge`

## 10. 为什么主干清场必须在环境分层前后一起考虑

这点很重要。

主干清场如果只清代码，不清环境，后面还是会重新脏掉。

因为现在的一个核心问题是：

**本地预览 / 测试联调 / 小程序联调离线上真实数据太近。**

这会导致：

1. 开发改动很容易围着生产事实转
2. 很多临时补丁自然进入主工作区
3. 修数和开发混在同一条链路里

所以主干清场和环境分层是绑定动作：

- 主干清场解决“代码基线不可信”
- 环境分层解决“数据基线不可信”

两者只做一个都不够。

## 11. 主干清场完成的验收标准

技术负责人必须有一个明确的“清场完成”定义。

### 必须同时满足：

1. `main` 工作区干净
2. 当前线上逻辑已对齐主干
3. 历史临时修复不再只存在于本地工作区
4. 功能代码、修数脚本、试验代码已分流
5. 核心回归测试通过
6. 财务关键数字与基线一致
7. 新功能可以正常从 `main` 开分支
8. 合并一个普通功能分支不再需要大规模人工搬运

只要这 8 条里有 2~3 条还没满足，就不能说主干已经恢复。

## 12. 对技术负责人的推荐执行顺序

如果是技术负责人接手，我建议顺序如下：

### Phase 1：识别事实

1. 确认线上真实运行状态
2. 确认主工作区当前改动分类
3. 确认哪些改动已上线未回主干

### Phase 2：恢复主干

1. 回收 A 类正式代码
2. 隔离 B/C/D/E/F
3. 得到干净 `main`

### Phase 3：恢复日常开发

1. 建 `feature/hotfix/ops` 三类分支纪律
2. 规定合并前同步和回归
3. 停止长期在主工作区堆改动

### Phase 4：和环境治理联动

1. 本地开发不再默认用生产数据
2. staging 做集成验证
3. prod 只承接正式上线

## 13. 为什么这份方案是可靠的

这份方案不是“教 Git 小技巧”，而是抓住了真实根因：

### 根因 1：主干不是稳定基线

方案里通过“改动分类 + A/B/C/D/E/F 分流 + 回收已上线改动”来处理。

### 根因 2：功能开发与修数混流

方案里通过 `feature/hotfix/ops` 三类分支分流来处理。

### 根因 3：已上线状态、主干状态、本地状态不一致

方案里通过“先确认生产事实，再回收主干”来处理。

### 根因 4：共享大文件带来的高冲突

这份方案本身不能立刻消灭大文件，但它能先让大文件冲突从“混乱状态”降到“有纪律状态”。

这就是为什么它是当前阶段可靠的方案：

- 不空谈
- 不假设系统已经很干净
- 先恢复基线，再恢复敏捷

---

## 14. 一句话结论

如果不先做主干清场，后面所有“分支开发规范”“发布规范”“回归规范”，都会建立在一个不可信的基线上。

这样做的结果只会是：

- 表面流程越来越多
- 实际开发越来越慢
- 合并越来越痛苦
- 系统越来越不可信

所以：

**主干清场不是整理卫生，而是恢复这套系统继续迭代能力的第一步。**
