# FlowTennis 日常开发与发布治理方案

> 版本：2026-05-10  
> 目标读者：老板、产品负责人、技术负责人、开发、AI 协作代理  
> 文档目标：回答 4 个问题  
> 1. 现在系统到底有几个端，为什么一个改动会牵一大片。  
> 2. 为什么即便新开分支开发，最后合并 `main` 还是很痛苦。  
> 3. 为什么现在几乎每次提新功能都会出问题。  
> 4. 如果希望“每天都能迭代，但系统还能健康稳定”，应该怎么治理。

---

## 1. 先说结论

你们现在遇到的问题，不是“某个开发粗心”，也不是“功能太多所以偶尔会乱”，而是：

**当前系统还没有进入“可持续日更迭代”的工程状态。**

它现在更像：

- 多个端共用一套高耦合后端
- 多个业务域共用一批关键表
- 主工作区长期不干净
- 分支基线不稳定
- 发布前没有足够强的回归和对账闸门

所以现在每次开发并不是：

`写功能 -> 测一下 -> 合并 -> 上线`

而更接近：

`写功能 -> 踩共享逻辑 -> 合并冲突 -> 回归不全 -> 上线误伤 -> 花一天修数`

这就是为什么你会感觉：

- 功能本身十几分钟
- 收拾烂摊子花 90% 时间

这个感觉是对的，而且是结构性问题，不是情绪问题。

## 2. 现在到底有哪几个端

这件事必须说清楚，因为“端越多、共用越深、回归成本越高”。

当前实际上有 5 个使用面：

### 2.1 管理后台 Web 端

主要使用者：

- 管理账号登录
- 运营
- 财务
- 管理员

承载内容：

- 学员
- 课包
- 购买
- 权益
- 排课
- 订场
- 会员
- 财务
- 账号
- 价格
- 校区

### 2.2 教练端 Web 登录视图

这不是独立系统，而是和管理后台共用同一个 Web 工程、同一个后端，只是：

- 登录角色不同
- 页面可见范围不同
- 数据过滤方式不同

也就是说：

**教练端 Web 不是独立隔离代码，而是同一套代码里的角色裁剪模式。**

### 2.3 教练端 PWA

也就是教练端 Web 的 PWA 适配版本。

仓库里有明确证据：

- `public/manifest.webmanifest`
- `public/service-worker.js`

说明：

- 它本质还是 Web 端
- 只是加了安装壳、缓存壳、离线壳

所以：

**PWA 不是独立后端，不是独立业务层，而是同一套 Web 的“包装形态”。**

### 2.4 教练端微信小程序

目录：

- `wechat-miniprogram/`

这是一套独立客户端实现，但仍然请求同一个后端 API。

也就是说：

- 前端代码不同
- 后端接口基本共用
- 数据口径仍然共用

所以任何后端逻辑变化，都可能同时影响：

- 管理后台 Web
- 教练端 Web
- 教练端 PWA
- 教练端微信小程序

### 2.5 约球小程序 / 约球系统

这部分虽然有自己的数据域和 Postgres 表，但并没有完全独立。

因为：

- 它有自己的 `match_*` 表
- 但又会把约球财务同步写回 `match-court-finance`
- 最终仍然会影响订场财务口径

所以它不是完全隔离的产品，而是：

**一个半独立、半耦合的子系统。**

## 3. 为什么一个改动会牵扯这么大

因为现在不是“一个端一套隔离后端”，而是：

- 多个客户端
- 共用一套 API
- 共用一批核心数据表
- 共用一批共享规则函数

所以一个改动可能同时影响：

1. 管理后台显示
2. 教练端显示
3. PWA 行为
4. 教练小程序行为
5. 约球财务联动
6. 财务页汇总口径

这也是为什么你感觉：

“我明明只动了一个地方，怎么最后好多地方都出问题了。”

因为技术上它们根本没彻底分家。

## 4. 为什么即便开新分支开发，最后合并 `main` 还是很困难

这是你现在最痛的点之一，我拆开讲。

### 4.1 你以为的分支开发前提

正常情况下，分支开发成立，必须满足 3 个前提：

1. `main` 是干净的
2. `main` 是最新稳定事实
3. 你分支只改自己要改的部分

只要这 3 个前提成立，分支开发就很顺。

### 4.2 你们现在不满足这 3 个前提

你们现在的问题是：

#### 问题 1：主工作区长期不干净

从当前仓库状态看，主工作区长期存在：

- 已修改但未收口的核心代码
- 一堆新加但未纳管的脚本
- 一堆新加但未纳管的测试
- 一堆 `_local/requirements` 规划文档
- 历史修复脚本和功能开发混在一起

这意味着：

**主工作区本身已经不是“稳定母体”，而是一个长期施工现场。**

#### 问题 2：`main` 不一定等于“真正干净最新状态”

你说“有些都上线了，但为什么还在主工作区”，这背后通常有几种可能：

1. 代码已经手工拷到别处发布了，但没完整回收进主工作区
2. 分支合并时不是标准 merge/rebase，而是人工搬运
3. 有的改动在线上分支、临时分支、工作副本里存在，但没回到统一主干
4. 文档、脚本、测试和主功能不是同一次提交收口

结果就是：

**线上状态、`main` 状态、主工作区状态，不再严格一致。**

一旦这 3 个状态不一致，后面所有分支开发都会很痛。

#### 问题 3：很多功能都在改同一批大文件

当前高冲突文件包括：

- `api/index.js`
- `public/assets/scripts/core/state.js`
- `public/assets/scripts/core/bootstrap.js`
- `public/index.html`
- `public/assets/scripts/pages/schedule.js`
- `public/assets/scripts/pages/coachops.js`
- `public/assets/scripts/pages/courts.js`
- `wechat-miniprogram/miniprogram/pages/schedule/schedule.js`

这些文件有个共同特点：

- 大
- 共享逻辑多
- 很多人 / 很多需求都要碰

所以即使你新开分支：

- 你改了 `api/index.js`
- 别人也改了 `api/index.js`
- 你改了 `state.js`
- 别人也改了 `state.js`

最后不是“代码谁对谁错”，而是：

**大家都在同一间厨房做菜，最后锅铲一定打架。**

#### 问题 4：功能不是局部封闭改动，而是跨域改动

比如一个课包功能，往往不只改：

- `packages`

还会顺带改：

- `purchases`
- `entitlements`
- `schedule`
- `finance`
- `state`
- 小程序教练端显示

所以你不是在改一个点，而是在碰一条链。

链越长，分支越难合。

#### 问题 5：没有真正的“集成基线”

现在看起来更像：

- 大家各自开发
- 然后试图往 `main` 塞

但缺少一个明确机制：

- 谁负责整理 `main`
- 谁负责确认 `main` 可合并
- 谁负责做合并后回归

结果是：

你分支虽然是新的，但要合并的对象本身已经不稳定。

### 4.3 所以本质不是 Git 难，而是基线烂

你不懂技术没关系，你只要记一句：

**分支难合并，不是因为“你不会用分支”，而是因为“主干本来就不干净、不稳定、不一致”。**

所以后面真正要治理的，不只是“教大家开分支”，而是：

1. 先把主干整理干净
2. 让 `main` 重新成为唯一可信基线
3. 再恢复正常分支开发

## 5. 为什么现在几乎每次提交新功能都会出问题

这个问题不能只回答“因为测试不够”，那太浅了。

真正原因有 8 层。

### 5.1 原因 1：多个端共享同一套后端逻辑

你现在不是做单端产品，而是做：

- 管理后台
- 教练端 Web
- 教练端 PWA
- 教练微信小程序
- 约球系统

后端很多逻辑是共用的。

所以一个改动，很容易变成多端回归。

### 5.2 原因 2：财务不是独立账本，而是聚合结果

当前财务页不是只读独立财务台账，它会同时看：

- `purchases`
- `entitlements`
- `entitlement_ledger`
- `financial_ledger`
- `courts`
- `membership_orders`
- `membership_benefit_ledger`

所以改课包、改权益、改订场、改会员，都可能把财务带偏。

### 5.3 原因 3：启动逻辑和修复逻辑也会写线上

这个是最大风险之一。

也就是说：

- 不是只有“点保存”才会改线上
- 服务启动、repair、自修复、脚本执行，也会改线上

所以开发者以为自己“没碰财务”，并不代表系统真的没碰。

### 5.4 原因 4：共享大文件太多

当前最核心的逻辑集中在少数大文件里。

结果是：

- 改动半径大
- 冲突多
- 容易误伤旧逻辑

### 5.5 原因 5：旧链路和新链路并存

比如文档里说当前主链是：

`packages -> purchases -> entitlements -> schedule`

但系统里 `products / classes / plans` 还在线、还能写。

这会导致：

- 新人按新链改
- 旧逻辑还在影响结果
- 最后口径不统一

### 5.6 原因 6：性能问题是结构性，不是单点

你说：

- 登录慢
- 数据加载慢
- 保存弹窗过几天又不行
- 修两天好一点，过几天又慢

这通常说明不是“某个请求偶尔超时”，而是：

1. 读取还是大包扫描
2. 热点页依赖太多原始表
3. 热缓存 / 启动逻辑 / 大页聚合互相干扰
4. 修一处只是缓解表象，没有改底层读写方式

所以会反复。

### 5.7 原因 7：发布前没有足够强的回归闸门

现在不是“完全没测试”，而是：

- 有规则测试
- 有页面测试

但缺少：

- 真实财务快照对比
- 多端联调验收
- 合并后主干回归
- 发布前 staging 全链路回归

所以很多问题是上线后才暴露。

### 5.8 原因 8：功能发布和数据修复没有彻底分流

现在功能开发仓库里同时放着：

- 功能代码
- 审计脚本
- 修复脚本
- 导入脚本

这会导致团队长期处于：

- 一边开发
- 一边修线上
- 一边救火

的状态。

这种状态下，系统几乎一定会反复出问题。

## 6. 这套系统如果想健康运行，必须达到什么状态

你要求的是：

- 不出问题
- 不反复出问题
- 每天可以持续迭代

如果要实现这个目标，系统至少要达到下面 6 个条件：

### 条件 1：主干干净

`main` 必须重新变成：

- 唯一可信基线
- 不带私人脏改动
- 不带未收口试验代码

### 条件 2：环境隔离

至少分清：

- 本地开发
- 测试 / staging
- 线上生产

而且这不是“最好有”，而是必须有。

如果本地预览、测试联调、微信小程序联调还在直接共用线上真实数据或线上财务口径，那么这套系统就还没有达到合格 SaaS 平台的最低迭代标准。

### 条件 3：财务隔离

财务页不能继续靠多业务表临时拼。

### 条件 4：修复隔离

修数据必须是一条独立流程，不能和日常发功能混在一起。

### 条件 5：回归标准化

每次上线前要明确跑哪些回归，不再靠感觉。

### 条件 6：多端回归清单

改后端时，必须知道影响：

- 管理后台
- 教练端 Web
- 教练端 PWA
- 教练微信小程序
- 约球小程序 / 约球后台

## 7. 日常开发治理方案

这一段是最重要的执行方案。

---

## 7.1 主干治理

### 目标

让 `main` 重新成为唯一可信基线。

### 2026-05-12 收官窗口补充

在新 `main` 正式恢复前：

1. `origin/thread26-staging-latest` 是唯一可信主干收官锚点。
2. 旧 `main` 只做差异核查，不作为第二阶段新需求默认来源。
3. `codex/match-real-launch` 及其他历史候选分支只允许只读比对或人工摘取，不允许整线回流。
4. 所有新分支默认从 `origin/thread26-staging-latest` 切出。

### 规则

1. 主工作区不再作为长期开发垃圾场。
2. 所有未收口的脏改动必须分类处理：
   - 要保留的，收口进分支
   - 不确定的，归档到专门目录或专门分支
   - 已上线但未回主干的，补回主干
3. 主工作区不能长期挂着几十个未提交改动继续开发。

### 你现在要拍板的事

需要安排一次“主干清场”：

1. 盘点哪些改动已经上线
2. 盘点哪些改动只是本地试验
3. 把试验代码和正式代码分开
4. 把 `main` 清理成可继续开发的状态

这是恢复敏捷的前提，不做这一步，后面所有分支策略都会继续痛。

---

## 7.2 分支治理

### 推荐最简方案

不要搞太复杂，适合现在小团队的方式是：

1. `main`
   - 只放“可上线、已回归、已通过验收”的代码

2. `feature/<日期>-<功能名>`
   - 每个功能单独分支

3. `hotfix/<日期>-<问题名>`
   - 线上紧急修复单独分支

4. `ops/<日期>-<修数事项>`
   - 修数据、修脚本、审计脚本单独分支

在新 `main` 正式恢复前，以上 3 类业务分支都从 `origin/thread26-staging-latest` 切；恢复后再统一改为从新 `main` 切。

### 绝对禁止

1. 在主工作区直接长期堆功能
2. 一个分支同时做多个无关需求
3. 功能分支里顺手塞修数脚本
4. 修线上数据直接在功能分支里做
5. 从旧 `main`、`codex/match-real-launch`、历史候选分支直接切第二阶段新需求分支
6. 把 `codex/match-real-launch`、`legacy/local-main`、`protect/main-uncommitted-20260428`、`verify/main-baseline`、`staging-latest-candidate`、`codex/clean-main`、`codex/match-main-merge` 整分支直接回主干

### 为什么这样能缓解你的痛

因为你现在最麻烦的是：

- 功能改动
- 修数改动
- 性能改动
- 结构改动

全混在同一波提交里。

分支一旦按性质拆开，合并成本会明显下降。

## 7.2A 约束机制治理

你现在最现实的情况是：

- 你自己不会记住所有技术约束
- 长期主要靠 Codex 帮你开发

所以约束必须主要落在“Codex 自己必须遵守的机制”上，而不是依赖你人工提醒。

### 建议采用四层约束机制

#### 第 1 层：`AGENTS.md`

定位：

- 仓库级硬约束

适合放：

- 红线
- 禁止事项
- 哪类需求默认不得碰财务
- 本地预览不得默认连生产
- 发布前必须过哪些门槛

#### 第 2 层：正式治理文档

定位：

- 已冻结结论和中长期治理方向

适合放：

- 架构诊断
- 环境治理
- 主干治理
- 性能治理
- 标准页治理

#### 第 3 层：Skill

定位：

- 把“这类任务怎么做”固化成标准流程

适合放：

- FlowTennis 总治理 Skill
- 性能治理 Skill
- 标准页改造 Skill
- 财务安全 Skill

#### 第 4 层：Checklist

定位：

- 最后交付闸门

适合放：

- 合并前检查清单
- 发布前检查清单
- 财务回归清单
- 多端冒烟清单

### 结论

后续不应再主要依赖“长提示词”来约束新线程，而应逐步升级成：

`AGENTS.md + 正式治理文档 + Skill + Checklist`

## 7.3 环境治理

这部分必须单独拿出来，因为你们现在最危险的一条红线就是：

**本地预览 / 测试联调离线上真实数据太近。**

在合格的大型 SaaS 迭代标准里，至少必须有 3 层环境：

### `dev` 本地 / 开发环境

用途：

- 日常开发
- UI 调试
- 普通功能联调

要求：

- 默认不连生产真实数据
- 默认不作为财务基线环境
- 默认不允许直接跑生产修数脚本

### `staging` 预发布环境

用途：

- 合并后的完整联调
- 回归测试
- 多端验收
- 财务快照对比

要求：

- 结构尽量接近生产
- 数据是受控测试数据或脱敏快照
- 允许做上线前验证
- 不允许成为长期开发垃圾场

### `prod` 生产环境

用途：

- 正式使用

要求：

- 不允许做普通开发验证
- 不允许承接本地预览联调
- 不允许开放 bootstrap / repair 自动写入
- 财务口径必须冻结守护

### 财务基线环境必须单独定义

即使有 `dev / staging / prod`，财务这条线还必须单独有“基线概念”。

也就是说：

- 普通业务测试环境
- 财务口径基线

不能混为一谈。

课包、购买、权益功能开发，不应默认拿当前“已确认正确”的财务口径环境共用。

## 7.4 开发前治理

每次开发前必须先做 4 件事：

1. 确认这次改动会影响哪几个端
2. 确认会碰哪些高危表
3. 确认是否涉及财务口径
4. 确认是否需要回归小程序 / PWA / 约球

### 最少要先回答的 4 个问题

1. 这次改动只影响 Web，还是也影响小程序？
2. 会不会碰 `purchases / entitlements / entitlement_ledger / courts / membership_orders`？
3. 会不会改 `api/index.js` 或 `state.js` 这种高冲突文件？
4. 会不会影响财务页？

只要有 2 个以上回答“会”，这次改动就不是小改动，必须单独严管。

---

## 7.5 课包与财务隔离治理

这部分是对“改课包把财务改坏”这类事故的正式制度化回应。

### 规则 1：课包需求默认不得改财务口径

以后像：

- 课包合并
- 课包编辑
- 购买记录联动
- 权益展示优化

这类需求，默认只能改：

- `packages`
- `purchases`
- `entitlements`
- 对应 UI

默认**不得**顺手改：

- 财务首页口径
- 收入聚合算法
- 已入账口径
- 财务汇总来源链

如果一定要动财务：

- 必须单开一个独立任务
- 必须走独立分支
- 必须补财务快照对比

### 规则 2：非目标模块差异默认算事故预警

以后任何课包 / 权益 / 排课类需求，在交付前都必须和 `main` 做“非本需求模块对比”。

最少对比：

- 学员页
- 订场用户
- 会员
- 财务中心
- 排课表
- 约球关键入口

只要这些非目标模块出现异常差异：

- 先停
- 不交付你验收
- 不继续往上线走

### 规则 3：关键财务数字必须冻结成正式基准

像这次你已经确认过的：

- 总收入
- 课包收入
- 订场收入
- 会员储值
- 成交笔数

以后不能继续靠人记忆。

必须冻结成：

1. 一个只读基准文件
2. 一个基准接口或基准脚本
3. 一个发布前对比测试

谁改财务页，谁先对这组数。

## 7.6 代码开发治理

### 原则

一次只做一类事：

1. 功能
2. 性能
3. 修数
4. 架构拆分

不要混做。

### 为什么

因为你们现在每次最容易出问题的模式就是：

- 顺手修一点性能
- 顺手补一点财务
- 顺手改一点页面

最后看起来是一个需求，实际是三四种改动叠加，回归根本控不住。

### 具体规则

1. 改功能时不顺手做架构重构
2. 改性能时不顺手改财务口径
3. 修线上数据时不顺手发新功能
4. 同一个 PR / 同一波提交只做一件主事

---

## 7.7 合并治理

### 现在为什么难合并

你不是单纯在“合并代码”，而是在合并：

- 一个高耦合后端巨石
- 一堆共享前端状态
- 同时跨多个端的行为
- 还有主工作区历史脏改动

所以现在合并前必须增加一个步骤：

### 合并前 3 步

1. 先同步最新 `main`
2. 先解决冲突，不要拖到最后一刻
3. 先在分支上跑回归，再申请合并

### 合并后再跑一轮

因为很多问题不是分支内能发现的，而是合并后共享逻辑变了才暴露。

所以必须补一轮：

- 合并后主干回归

---

## 7.8 交付验收门槛

这部分要非常硬，不能再模糊。

以后任何环境在交给你验收前，必须先过“可验收门槛”。

### 可验收门槛

至少必须满足：

1. 能登录
2. 目标页面能正常出数据
3. 非目标高频页面不空白
4. 没有关键 `401 / 404 / 500`
5. 目标功能链路能完整点通

只要这 5 条没过：

- 不交付环境
- 不让你承担第一轮排错成本

### 为什么必须这样

因为你现在最浪费时间的地方，不只是“功能有 bug”，而是：

- 环境本身就不可验收
- 还要你自己先帮忙识别环境是不是坏的

这不合理，也不符合合格 SaaS 团队的交付标准。

## 7.9 测试治理

### 你现在需要的不是“更多测试”，而是“更对的测试”

最优先的 4 类测试：

1. 财务快照对比
2. 教学主链回归
3. 多端关键页面冒烟
4. 高危脚本 dry-run 校验

### 每次上线前最少要验什么

#### A. 财务 5 个核心数

像这次一样，必须固定核对：

- 总收入
- 课包收入
- 订场收入
- 会员储值
- 成交笔数

#### B. 教学主链

- 新建课包
- 新建购买
- 生成权益
- 排课扣课
- 编辑排课回滚

#### C. 会员主链

- 开卡
- 续充
- 作废
- 权益流水

#### D. 订场主链

- 新建订场用户
- 录入财务历史
- 价格方案引用

#### E. 多端冒烟

- 管理后台登录
- 教练端 Web 登录
- PWA 打开
- 教练微信小程序登录
- 约球关键入口

#### F. 非目标模块对比

只要本次不是财务需求，也必须对比财务页是否异常漂移。

## 7.10 发布治理

### 从今天开始，发布分成两类

#### 类型 A：功能发布

只允许包含：

- 页面逻辑
- 普通业务逻辑
- 非生产修数代码

#### 类型 B：数据修复发布

只允许包含：

- 审计结果
- 修复脚本
- 修复执行说明

### 绝对禁止

1. 功能发布顺手带修数
2. 修数发布顺手带新功能

### 发布前 checklist

1. 分支干净
2. 目标清晰
3. 财务快照已记录
4. 高危表影响已确认
5. 多端影响已确认
6. 回归已跑
7. 合并后回归已跑
8. 可验收门槛已通过
9. 非目标模块对比已通过

---

## 7.11 线上修复治理

这是你们现在最容易失控的地方。

### 以后修线上数据，必须单独走 5 步

1. 先审计
2. 再出修复计划
3. 先 dry-run
4. 人工确认影响范围
5. 再 `--write`

### 并且必须单独记录

每次修数都要有：

1. 修复原因
2. 影响表
3. 影响人数 / 影响记录数
4. 修前快照
5. 修后结果

如果没有这些记录，以后会继续出现：

- 修完不知道修了什么
- 修完又引出新问题

## 7.12 按这次事故做严格 SaaS 复盘

你给出的那段复盘，有 3 点说对了：

1. 课包与财务必须隔离
2. 不能再靠“我小心一点”
3. 必须把财务数字冻结成基准

但如果按更严格的大型 SaaS 标准来看，还不够彻底。

### 不够彻底的地方 1：只说“环境隔离”，没把环境层级讲完整

正确标准不是简单区分“测试环境”和“线上环境”，而是至少：

- `dev`
- `staging`
- `prod`

并且财务基线还要额外冻结。

### 不够彻底的地方 2：只说“课包默认不得改财务”，但没有主干与合并治理

如果主干本身还是脏的、共享大文件还是乱的，就算课包不改财务，也可能因为合并冲突把别的口径带坏。

### 不够彻底的地方 3：只说“交付前先过门槛”，但没有把门槛制度化

必须写成固定 checklist，而不是临时口头要求。

### 不够彻底的地方 4：没把“本地预览共用线上数据”上升为红线

这条必须明确：

**本地预览 / 测试联调直接共用线上真实数据，是不合格状态。**

这不是优化项，而是必须整改项。

### 更严格的最终制度化版本

如果按合格 SaaS 平台标准，最少要落成下面 6 条硬规则：

1. 课包需求默认不得改财务口径
2. 本地预览默认不得连生产真实数据
3. 必须有 `dev / staging / prod` 三层环境
4. 财务关键数字必须冻结基准
5. 交付前必须过可验收门槛
6. 非目标模块差异默认算事故预警

## 7.12A 关于数据库路线的治理判断

当前对数据库路线的判断应该正式写清楚：

### 结论

Supabase / Postgres 值得作为中期升级方向评估，但当前不应直接全量迁移。

### 原因

因为现在最优先的问题不是“换库”，而是：

1. 主干不干净
2. 环境未分层
3. 财务基线未冻结
4. 高危写入口未关闸
5. 旧链路 / 新链路边界未收口

### 正确顺序

1. 先治理主干和环境
2. 再做高敏感读模型试点
3. 再评估是否局部迁移到 Supabase / Postgres
4. 最后才考虑扩大迁移范围

### 为什么不能现在大爆炸迁移

因为很容易变成：

- 旧系统没稳住
- 新系统没迁完
- 两边一起返工

这不符合当前“先恢复健康迭代能力”的优先级。

## 7.13 性能治理

你提到的“今天能保存，过几天又慢、又保存不了了”，这通常是系统已经进入：

- 读太重
- 写太慢
- 超时 / 冲突 / 初始化副作用叠加

的状态。

### 治理原则

1. 高敏感页必须走独立读模型
2. 不再让财务页全靠大包聚合
3. 减少大范围全表扫描
4. 热点写入链必须缩短

### 先做什么

优先治理：

1. 登录链路
2. `/page-data/finance`
3. `/page-data/workbench`
4. `/schedule` 保存链路
5. 订场和会员保存链路

因为这些是最容易让你体感“系统又慢又不稳”的地方。

## 8. 建议的日常节奏

这是适合你们当前阶段的最现实节奏。

### 每天开发节奏

1. 早上先确认当天只做哪一个主需求
2. 功能前先判断影响哪几个端
3. 单独分支开发
4. 开发完成先分支内自测
5. 合并前补财务快照和高危回归
6. 合并后主干再跑一轮
7. 再上线

### 每周固定节奏

1. 固定一天做主干清洁
2. 固定一天做性能审计
3. 固定一天处理修数和历史问题，不和功能混

这会比现在“天天边开发边救火”健康得多。

按优先级：

## 10. 技术负责人一句话结论

如果后面想让 FlowTennis 进入“每天能改，但不天天炸”的状态，真正要做的不是继续堆需求，而是先把下面 4 件事工程化：

1. `main` 重新变干净
2. 高危写入口关闸
3. 功能发布和修数据分流
4. `dev / staging / prod` 环境分层
5. 多端回归和财务回归制度化

只要这 5 件事不做，你们就会继续反复经历：

- 分支能开发，最后合不上
- 合上了，不敢发
- 发了，财务又坏
- 修好了，过几天又慢

这不是个人失误，这是系统目前的自然结果。
