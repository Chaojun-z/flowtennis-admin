# FlowTennis 财务与权益统一执行计划

本文档是执行用文档，不是概念方案。

新线程、新 AI、后续开发者只需要先读本文档，再读：

- `docs/财务与权益统一规划-v2.md`
- `docs/平台核心数据字典.md`
- `docs/平台页面功能总览.md`

当前状态：

```text
规划已完成。
代码未开始改。
财务总账未实现。
历史数据未迁移。
沙盘验证未开始。
```

核心目标：

> 在不让运营重复记账的前提下，把课包、会员储值、订场、券核销、赠送、补偿、退款、冲正统一成“业务动作 -> 权益变化 -> 财务流水 -> 财务报表”。

---

## 一、执行总原则

1. 不直接重构全系统。
2. 不新增很多业务页面。
3. 不让运营去财务中心重复录账。
4. 所有财务流水只增不改。
5. 先做课程和储值这两条主线。
6. 大众点评、平台手续费、毛利、完整 SaaS 配置后置。
7. 每做一阶段，都必须有测试和可见页面。

## 四、阶段 0：沙盘验证与历史期初口径

目标：

先用真实数据验证规则，不通过不写代码。

需要做：

1. 选 10-20 个真实用户。
2. 覆盖以下场景：
   - 买课包
   - 买 10 送 2
   - 消课
   - 会员充值
   - 储值订场
   - 现场订场
   - 退款
   - 赠送课
   - 教练迟到免费
   - 大众点评券核销
3. 用 Excel 或表格跑出：
   - 实收
   - 已确认收入
   - 待确认收入
   - 剩余付费课时
   - 剩余赠送课时
   - 储值余额
4. 确定上线日。
5. 确定期初快照规则。

期初快照推荐：

```text
上线日前历史明细不强行补写财务流水。
上线日写入期初待确认余额。
上线日之后所有新动作都走 ft_financial_ledger。
```

验收：

- 10-20 个用户沙盘对得上。
- 买赠课退款规则确认。
- 历史期初方案确认。
- 财务、运营、老板都能看懂。

状态：

```text
已完成（当前只完成会员充值 / 储值订场 / 现场订场 / 代用户订场四类动作接总账，会员退款和订场退款/冲正暂未纳入本阶段）
```

## 五、阶段 1：财务总账地基

目标：

新增统一财务总账能力，但先不改所有业务流。

建议新增后端能力：

| 能力 | 说明 |
|---|---|
| `normalizeFinancialLedgerRow` | 标准化财务流水 |
| `buildFinancialLedgerEntry` | 根据业务动作创建流水 |
| `reverseFinancialLedgerEntry` | 冲正流水 |
| `summarizeFinancialLedger` | 汇总实收、确认收入、待确认收入 |
| `assertFinancialLedgerBalanced` | 等式检查 |
| `ledgerIdempotencyKey` | 防重复写入 |

建议新增常量：

```text
T_FINANCIAL_LEDGER = 'ft_financial_ledger'
```

建议新增字段：

| 字段 | 要求 |
|---|---|
| `clubId` / `tenantId` | 必须有，当前默认 `default` |
| `cashDelta` | 单位为分，整数 |
| `recognizedRevenueDelta` | 单位为分，整数 |
| `deferredRevenueDelta` | 单位为分，整数 |
| `openingDeferredRevenueDelta` | 单位为分，历史期初专用 |
| `paymentStatus` | pending / success / failed |
| `sourceType` + `sourceId` + `ledgerType` | 幂等键 |
| `productSnapshotName` | 商品名称快照 |
| `productSnapshotPrice` | 商品原价快照 |
| `productSnapshotMeta` | 商品规则快照 |

建议测试：

创建：

```text
tests/financial-ledger-rules.test.js
```

测试必须覆盖：

1. 收款流水：实收增加，待确认增加。
2. 消耗流水：确认收入增加，待确认减少。
3. 现场收款：实收和确认收入同时增加。
4. 金额必须用分，禁止小数。
5. 3000 元 / 7 节时，最后一节处理尾差。
6. 同一来源单据不能重复写流水。
7. 冲正生成反向流水，原流水标记 reversed。
8. pending 支付不计入有效汇总。
9. success 支付计入有效汇总。
10. 有历史期初时，等式按期初公式检查。

涉及文件：

| 文件 | 操作 |
|---|---|
| `api/index.js` | 新增财务总账常量、标准化函数、汇总函数、冲正函数 |
| `tests/financial-ledger-rules.test.js` | 新增测试 |

验收：

- `node tests/financial-ledger-rules.test.js` 通过。
- 不影响现有业务测试。
- 没有任何业务页面开始依赖新总账前，旧系统仍可正常运行。

状态：

```text
已完成（当前复用订场用户财务弹窗录入券核销，已覆盖大众点评订场券 / 体验课券 / 小班券的最小总账闭环；平台手续费和结算对账仍未展开）
```

## 七、阶段 3：课程课包收入确认

目标：

课包购买和排课消课自动生成财务流水。

规则：

1. 买课包：
   - `cashDelta > 0`
   - `recognizedRevenueDelta = 0`
   - `deferredRevenueDelta > 0`
2. 消耗付费课：
   - `cashDelta = 0`
   - `recognizedRevenueDelta > 0`
   - `deferredRevenueDelta < 0`
3. 消耗赠送课：
   - 三个金额都为 0
4. 买 10 送 2：
   - 付费课时 10
   - 赠送课时 2
   - 默认先扣付费课，最后扣赠送课

需要补的数据：

| 对象 | 字段 |
|---|---|
| 购买记录 | 购买课时、赠送课时、实收金额、支付渠道、商品快照 |
| 权益账户 | 剩余付费课时、剩余赠送课时 |
| 消课流水 | 本次扣的是付费课还是赠送课 |
| 财务流水 | 关联购买记录、排课记录、权益账户 |

涉及文件：

| 文件 | 操作 |
|---|---|
| `api/index.js` | 购买创建时写课包收款流水；排课消课时写收入确认流水 |
| `public/assets/scripts/pages/purchases.js` | 展示付费课时、赠送课时、财务流水入口 |
| `public/assets/scripts/pages/schedule.js` | 显示扣课来源：付费/赠送 |
| `tests/entitlement-rules.test.js` | 增加买赠课扣减规则测试 |
| `tests/schedule-rules.test.js` | 增加消课写财务流水测试 |
| `tests/financial-ledger-rules.test.js` | 增加课程收入确认测试 |

验收：

- 买课包后财务总账出现课包收款流水。
- 消课后财务总账出现课包消课流水。
- 默认先扣付费课时。
- 付费课时用完才扣赠送课时。
- 赠送课时不确认收入。
- 财务中心能查到课程收入确认明细。

状态：

## 八、阶段 4：课包退款、赠送、补偿

目标：

补齐最容易乱的特殊场景。

课包退款默认规则：

```text
建议退款金额 = 剩余付费课时 × 付费单节成交价
剩余赠送课时直接作废
已使用赠送课时只提示管理员，不自动折算扣款
```

赠送权益规则：

```text
纯赠送课不产生实收、不产生确认收入、不产生待确认收入。
使用赠送课只减少赠送课余额，收入为 0。
```

教练迟到免费规则：

```text
学员已上课 +1。
用户课时不扣。
用户收入不确认。
教练承担场地费只进教练结算，不进用户财务流水。
```

涉及文件：

| 文件 | 操作 |
|---|---|
| `api/index.js` | 增加退款、赠送、补偿的财务流水规则 |
| `public/assets/scripts/pages/purchases.js` | 增加退款入口或退款展示 |
| `public/assets/scripts/pages/schedule.js` | 教练迟到免费不扣用户权益 |
| `tests/financial-ledger-rules.test.js` | 退款、赠送、补偿测试 |
| `tests/schedule-rules.test.js` | 教练迟到免费规则测试 |

验收：

- 管理员才能退款。
- 退款必须填写原因。
- 退款不回退已确认收入。
- 已用赠送课时会提示。
- 教练迟到免费不影响用户收入。

状态：

```text
未开始
```

## 十六、历史补账方案

### 1. 当前核查结论

财务核查脚本最近一次实跑结果：

| 项目 | 结果 |
|---|---|
| 全局总账等式 | 通过 |
| 课包余额核查 | 通过 |
| 会员储值余额核查 | 通过 |
| 财务流水完整性 | 发现 126 条问题 |
| 孤儿和异常数据 | 通过 |

这说明：

1. 当前没有直接证据表明“新实时记账逻辑算错钱”。
2. 当前暴露的问题，主要是“老业务记录存在，但没有补进 `ft_financial_ledger`”。

### 2. 126 条问题的分类

| 分类 | 数量 | 结论 | 说明 |
|---|---:|---|---|
| `missing_purchase_ledger` | 48 | 历史补账 | 老课包购买记录存在，但缺少 `课包收款` 总账 |
| `missing_entitlement_financial_ledger` | 61 | 历史补账 | 老消课/退课相关记录存在，但缺少 `课包消课/课包退课` 总账 |
| `missing_membership_recharge_ledger` | 17 | 历史补账 | 老会员充值记录存在，但缺少 `会员充值` 总账 |

当前没有识别出：

- 真实时记账 bug
- 明显脚本误报
- 负余额、重复扣课、孤儿流水

### 3. 为什么先补历史账，不先做平台结算

原因很直接：

1. 现在系统主干总账已经是平的。
2. 如果老账不先补，后面做平台结算、手续费、差异对账时，核查结果会一直混着老问题，无法判断新功能是否真的稳定。
3. 先把历史账补齐，再扩平台结算，排查成本最低。

### 4. 补账策略

本阶段不做“全量重建所有历史财务流水”，先做最小可落地方案。

建议顺序：

#### 方案 A：历史补总账（优先）

针对已经存在的老业务记录，按当前统一口径补写总账：

1. 老课包购买 -> 补 `课包收款`
2. 老消课/退课 -> 补 `课包消课 / 课包退课`
3. 老会员充值 -> 补 `会员充值`

要求：

- 只补缺失流水，不重复补
- 所有补写都保留 `sourceType / sourceId`
- 补写记录必须可区分为“历史补账”
- 补写后重新跑核查脚本，目标是把 126 条完整性问题清零

#### 方案 B：期初快照（后备）

如果某些老消课明细缺失、无法可靠重建，则改成期初快照：

1. 按上线日写入每个用户的期初待确认余额
2. 旧业务记录保留查询，但不强行补齐到逐笔总账
3. 之后新发生业务全部继续走新总账

适用条件：

- 老数据字段不全
- 无法确认历史逐笔业务真实口径
- 补逐笔流水成本过高

### 5. 当前推荐口径

先按下面顺序执行：

1. 先做“历史补总账脚本”
2. 优先处理这 126 条已明确缺口
3. 补不动的历史残缺数据，再单独转期初快照

不要一开始就全改成期初快照，因为目前这 126 条问题类型已经很明确，优先补齐更利于后续追溯。

### 6. 具体执行步骤

```text
第一步：新增历史补账脚本（只补不删）
第二步：先补 48 条老购买缺失的课包收款总账
第三步：再补 61 条老消课/退课缺失的财务总账
第四步：再补 17 条老会员充值缺失的会员充值总账
第五步：重跑 npm run audit:financial
第六步：把剩余无法补齐的个案列成“期初快照清单”
```

### 7. 补账脚本约束

补账脚本必须遵守：

1. 幂等：重复执行不能重复补账
2. 只补缺失，不改已有总账
3. 金额继续用“分”整数
4. 必须带历史补账标记，方便后续筛选
5. 每补一类，都先 dry run 再正式执行

### 8. 完成标准

这个阶段完成，至少要满足：

1. 当前 126 条完整性问题大幅下降，最好清零
2. 重跑核查后，仍然保持：
   - 总账等式通过
   - 课包余额通过
   - 会员余额通过
   - 无新增异常数据
3. 输出一份“历史补账结果报告”
