## 三、不可破坏原则

1. 不直接把 CSV 每一行当成收入流水。
2. 不先写正式财务总账，必须先预览。
3. 原始每个字都要保存，包括日期原文、星期原文、时间原文、客户、收入类型、支付方式、金额、差价说明、收款人、备注。
4. Excel 里的公式原文也要保存，例如 `=220+100`、`=110*4`。
5. 能自动判断的才自动导。
6. 不确定的行必须进入人工确认清单。
7. 不覆盖已有业务数据。
8. 不随便创建新学员或新订场用户。
9. 能匹配已有用户就匹配；不能匹配就先作为历史临时客户保留。
10. 导入后必须跑 `npm run audit:financial`。

完成标准：

```text
财务核查 5 层全部通过。
共发现 0 个问题。
金额差异 0.00 元。
```

## 四、为什么不能直接导入财务总账

同样是“实际收入 500”，含义可能完全不同。

| 场景 | 正确财务含义 |
|---|---|
| 微信转账支付 | 当天实收，通常当天确认收入 |
| 小程序 | 当天实收，通常当天确认订场收入 |
| 课包划扣 | 当天不新增实收，只确认收入，并减少待确认 |
| 8折储值卡 / 9折储值卡 | 当天不新增实收，只确认收入，并减少储值余额 |
| 大众点评支付 | 核销确认收入，后续还要处理平台结算 |
| 大众点评+微信转账支付 | 要拆平台部分和微信补差部分 |
| 免费 / 赠送 / 资源置换 | 不应直接确认现金收入 |
| 待确认 / 未补差价 | 需要人工确认 |

如果直接按实际收入导入，会导致：

- 实收虚增
- 待确认收入错误
- 课包余额对不上
- 储值余额对不上
- 用户历史操作无法追溯

## 六、字段映射

| CSV 字段 | 系统对应位置 | 导入要求 |
|---|---|---|
| 日期 | `businessDate` / 业务记录日期 | 中文日期转标准日期，同时保留原文 |
| 星期 | 原始归档字段 | 可系统计算，但原文保留 |
| 时间 | 订场或排课的开始/结束时间 | 能解析则结构化，不能解析则人工确认 |
| 客户 | 学员 / 订场用户 / 临时客户 | 先匹配，不能匹配不强行新建 |
| 收入类型 | 业务类型 / `ledgerType` | 通过规则表标准化 |
| 支付方式 | 支付渠道 / 财务口径 | 决定实收、确认收入、待确认变化 |
| 应收收入 | 商品原价 / 应收金额 | 保存为分，同时保存 Excel 公式 |
| 实际收入 | 实收或确认收入来源 | 不能单独决定财务口径 |
| 差价 | 优惠 / 免费 / 待补差价 | 进入审计说明 |
| 差价说明 | 调整原因 | 进入 `reason` / `notes` |
| 收款人 | 操作人 / 收款人快照 | 保留原文，必要时匹配系统用户 |
| 备注 | 审计备注 | 必须完整保存 |

## 九、需要人工确认的行

以下情况不能自动导：

1. 支付方式为空。
2. 收入类型为空。
3. 客户为空。
4. 时间为空或无法解析。
5. 差价说明为 `待确认`。
6. 差价说明为 `未补差价`。
7. 备注包含 `赠送`。
8. 备注包含 `免费`。
9. 备注包含 `资源置换`。
10. 备注包含 `内部教学`。
11. 收入类型为 `领导订场`。
12. 收入类型为 `课程内测`。
13. 支付方式为 `大众点评+微信转账支付`。
14. 支付方式为 `课包划扣`，但找不到对应学员课包。
15. 支付方式为 `8折储值卡 / 9折储值卡`，但找不到对应订场用户储值账户。

人工确认清单每行必须显示：

- 原始行号
- 原始内容
- 系统初步判断
- 不能自动导的原因
- 建议处理方式
