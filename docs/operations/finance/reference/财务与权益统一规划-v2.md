# FlowTennis 财务与权益统一规划 v2

本文档用于确定 FlowTennis 后续财务、权益、储值、消耗、退款、补偿、对账的统一设计。

目标：

1. 让运营操作简单，不需要懂财务。
2. 让财务数据清楚、可追溯、可导出。
3. 让课包、会员储值、订场、券核销、赠送、补偿统一到同一套规则。
4. 为后续 SaaS 化预留多俱乐部、多渠道、多商品能力。

核心原则：

> 业务页面记录真实动作，系统自动生成权益变化和财务流水，财务中心只负责查询、对账、导出。

---

## 一、最终结论

FlowTennis 不应该单独做一个让运营重复录账的“财务系统”。

正确结构是：

```text
业务动作 -> 权益变化 -> 财务流水 -> 财务报表
```

也就是说：

- 学员买课包，在“购买记录”操作。
- 学员上课，在“排课表”操作。
- 用户充值会员，在“会员/订场账户”操作。
- 用户订场，在“订场记录”操作。
- 大众点评券，在“券核销”操作。
- 财务中心不录业务，只看结果。

财务中心要回答：

1. 本月实收多少钱？
2. 本月确认收入多少钱？
3. 当前还有多少预收没有确认？
4. 每一笔收入来自哪次购买、消课、订场或券核销？
5. 每个用户还剩多少课时、储值、券、赠送权益？
6. 退款、冲正、补偿有没有完整记录？

## 二、系统现状

现有系统已经有较完整的业务页面：

| 模块 | 现有页面 | 当前作用 |
|---|---|---|
| 学员 | 学员信息 | 管学员基础资料、课程关系、订场关联 |
| 课程 | 课程产品、售卖课包、购买记录、课包余额 | 管课程商品、销售、课时权益 |
| 教学 | 排课表、班次管理、学习计划 | 管上课、消课、反馈 |
| 场地 | 订场用户、会员管理、会员方案、价格管理 | 管储值会员、订场消费、场地价格 |
| 财务 | 财务中心 | 目前主要看课包收入、消课、教练结算 |
| 教练 | 教练运营、教练管理 | 管排课、工作量、结算辅助 |

现有问题：

1. 课包、储值、订场、会员、券、赠送权益没有统一财务口径。
2. 业务流水有，但缺少一张统一的财务总账。
3. 有些数据从业务表临时计算，追溯和对账不够稳定。
4. 财务中心现在不是全系统收入口径。
5. 退款、冲正、赠送、补偿、教练迟到免费课等特殊场景规则不够统一。
6. 如果未来做 SaaS，必须提前预留 `tenant_id` / `club_id`，否则后面改造成本很高。

## 三、统一概念

## 1. 三个财务数字

| 名称 | 通俗解释 |
|---|---|
| 实收金额 | 用户真实付进来的钱 |
| 已确认收入 | 服务已经发生，可以算作收入的钱 |
| 待确认收入 | 已收钱但服务还没发生，暂时不能算收入的钱 |

例子：

用户充值 5000 元会员储值：

| 动作 | 实收金额 | 已确认收入 | 待确认收入 |
|---|---:|---:|---:|
| 会员充值 | +5000 | 0 | +5000 |

用户用储值订场消费 240 元：

| 动作 | 实收金额 | 已确认收入 | 待确认收入 |
|---|---:|---:|---:|
| 储值订场 | 0 | +240 | -240 |

这表示：从原来的预收余额里拿出 240，转成当期收入。

## 2. 四个基础动作

| 动作 | 含义 | 举例 |
|---|---|---|
| 收款 | 用户真实付钱 | 买课包、会员充值、现场订场付款 |
| 消耗 | 用户使用了服务 | 上课、订场、核销券 |
| 退款 | 把未使用部分的钱退给用户 | 课包剩余课时退款、储值余额退款 |
| 冲正 | 修正录错的历史记录 | 录错用户、录错金额、重复扣课 |

退款和冲正必须分开：

- 退款是业务真实发生。
- 冲正是修错账。

## 3. 关联对象

每一条财务流水都必须能追溯到原始业务。

常见关联对象：

| 关联对象 | 用途 |
|---|---|
| 学员 | 谁买课、谁上课 |
| 订场用户 | 谁充值、谁订场 |
| 课包 | 消耗的是哪个课包 |
| 会员账户 | 扣的是哪个储值/会员余额 |
| 排课记录 | 哪一节课产生了消课 |
| 订场记录 | 哪一天几点哪个场产生了收入 |
| 券码 | 哪张大众点评券、小班券被核销 |
| 操作人 | 谁录入、谁退款、谁冲正 |

## 四、系统分层

FlowTennis 后续统一成 5 层。

| 层级 | 作用 | 举例 |
|---|---|---|
| 商品中心 | 定义卖什么 | 课包、会员卡、场地价格、券类产品 |
| 用户权益 | 记录用户还剩什么 | 课时、储值、会员权益、赠送课、券 |
| 业务动作 | 记录真实发生了什么 | 购买、充值、订场、消课、核销、退款 |
| 财务总账 | 系统自动生成金额变化 | 实收、确认收入、待确认变化 |
| 财务中心 | 查询、对账、导出 | 月报、季报、预收余额、异常检查 |

原则：

- 商品中心不记收入，只定义规则。
- 用户权益不等于收入，只说明用户还能用什么。
- 业务动作是运营操作入口。
- 财务总账只增不改，是查账地基。
- 财务中心只查询，不重复录业务。

## 五、财务总账表设计

必须新增一张独立的财务总账表。

建议表名：

```text
ft_financial_ledger
```

每一行代表一个财务事件。

这张表是整个系统的财务地基，原则是：

1. 只新增，不修改，不删除。
2. 所有金额变化都通过它追溯。
3. 任何业务动作如果影响财务，都必须写入一条或多条总账流水。
4. 冲正不能改原记录，只能生成反向流水。

## 1. 建议字段

| 字段 | 说明 |
|---|---|
| `id` | 流水 ID |
| `tenantId` / `clubId` | 俱乐部 ID，SaaS 数据隔离用 |
| `businessDate` | 业务发生日期，用于月报/季报 |
| `createdAt` | 系统写入时间 |
| `actorId` | 操作人 ID |
| `actorName` | 操作人姓名快照 |
| `userType` | `student` / `court_user` / `guest` |
| `userId` | 用户 ID |
| `userName` | 用户姓名快照 |
| `businessType` | 课程 / 场地 / 会员 / 券 / 其他 |
| `actionType` | 收款 / 消耗 / 退款 / 冲正 / 赠送 / 补偿 / 内部占用 |
| `ledgerType` | 更细的流水类型，例如课包收款、课包消课、储值订场 |
| `paymentChannel` | 微信 / 支付宝 / 现金 / 大众点评 / 小程序 / 银行转账 / 内部记账 |
| `paymentStatus` | pending / success / failed，线上支付未成功前不生效 |
| `salesChannel` | 现场 / 小程序 / 大众点评 / 转介绍 / 其他 |
| `cashDelta` | 实收金额变化，单位为分，收款为正，退款为负 |
| `recognizedRevenueDelta` | 已确认收入变化，单位为分 |
| `deferredRevenueDelta` | 待确认收入变化，单位为分 |
| `openingDeferredRevenueDelta` | 期初待确认金额，只用于历史期初快照，单位为分 |
| `entitlementDelta` | 权益变化，例如课时 +10、课时 -1、储值 -240 |
| `productId` | 商品 ID |
| `productSnapshotName` | 商品名称快照 |
| `productSnapshotPrice` | 商品原价快照，单位为分 |
| `productSnapshotMeta` | 商品规则快照，例如课时、赠送课时、有效期 |
| `sourceType` | 来源单据类型：购买记录、排课记录、订场记录、会员订单、券核销 |
| `sourceId` | 来源单据 ID |
| `reversalOfLedgerId` | 如果是冲正，关联被冲正的原流水 |
| `reversedByLedgerId` | 如果被冲正，记录冲正流水 ID |
| `status` | active / reversed |
| `reason` | 退款、冲正、赠送、补偿原因 |
| `notes` | 备注 |

## 2. 金额与精度规则

所有金额必须用“分”为单位存整数。

禁止：

- 用 `float` / `double` 存金额。
- 用元的小数直接做财务计算。

原因：

如果 3000 元买 7 节课，单节为 428.571428 元。直接四舍五入会产生 1 分钱尾差，导致总账永远对不上。

尾差处理规则：

```text
前 N-1 次按整数分摊金额确认；
最后一次消耗时，用 总实收 - 已确认金额 兜底；
确保最后累计确认收入一定等于总实收。
```

例：

```text
300000 分 / 7 节 = 42857 分，余 1 分
前 6 节每节确认 42857 分
第 7 节确认 300000 - 42857 * 6 = 42858 分
```

## 3. 金额校验关系

从全局看：

```text
累计实收 = 所有 cashDelta 加总
累计确认收入 = 所有 recognizedRevenueDelta 加总
当前待确认收入 = 所有 deferredRevenueDelta 加总
```

全局必须满足：

```text
所有 cashDelta 加总 = 所有 recognizedRevenueDelta 加总 + 所有 deferredRevenueDelta 加总
```

如果包含历史期初快照，则使用：

```text
期初待确认金额 + 上线后所有 cashDelta 加总
= 上线后所有 recognizedRevenueDelta 加总 + 当前待确认收入
```

注意：

- 现场订场、现场体验课这类“收款即确认”的业务，`cashDelta` 和 `recognizedRevenueDelta` 同时增加，`deferredRevenueDelta` 为 0。
- 内部占用、纯赠送、补偿课不影响三个金额，但仍可写审计流水，方便统计服务发生。
- 上面这个等式适用于全局，包括预收、现场收款、退款、冲正。

## 六、动作到财务流水的规则

## 1. 买课包

例：用户买 10 节送 2 节，实收 3000 元。

系统动作：

- 创建购买记录。
- 创建课包权益：付费课时 10 节，赠送课时 2 节。
- 写财务流水。

财务流水：

| 字段 | 值 |
|---|---:|
| `cashDelta` | +3000 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | +3000 |

## 2. 消课

例：买 10 节送 2 节，实收 3000。

推荐一期默认规则：

```text
付费课时和赠送课时分开管理。
默认先扣付费课时，付费课时用完后才扣赠送课时。
```

收入确认规则：

```text
付费课时单节确认收入 = 实收金额 / 购买课时
赠送课时确认收入 = 0
```

例：

```text
3000 元 / 10 节付费课 = 每节 300 元
赠送 2 节 = 每节收入 0
```

消耗 1 节付费课：

| 字段 | 值 |
|---|---:|
| `cashDelta` | 0 |
| `recognizedRevenueDelta` | +300 |
| `deferredRevenueDelta` | -300 |

消耗 1 节赠送课：

| 字段 | 值 |
|---|---:|
| `cashDelta` | 0 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | 0 |

说明：

- 这比“按 12 节平均确认”更符合运营和退款直觉。
- 用户自己购买的课时先被消耗，赠送课时最后消耗。
- 赠送课时是免费权益，不产生收入。
- 退款规则可以另行配置，不能和收入确认规则混为一谈。

## 3. 买课送课的退款

买赠课退款最容易引发争议，不能写死单一公式。

一期默认退款规则：

```text
先看付费课时还剩多少。
建议退款金额 = 剩余付费课时 × 付费单节成交价。
剩余赠送课时直接作废，不折现退款。
```

例：买 10 节送 2 节，实收 3000，默认先扣付费课。

如果用户上了 3 节，都是付费课：

```text
已确认收入 = 3 × 300 = 900
待确认收入 = 2100
建议退款 = 7 × 300 = 2100
剩余 2 节赠送课作废
```

如果用户已经使用过赠送课：

```text
系统提示：该用户已使用 X 节赠送课。
管理员人工核定实退金额。
系统不自动把赠送课折算成扣款。
```

可选退款规则：

| 规则 | 说明 |
|---|---|
| 默认规则：按剩余付费课时退 | 最简单，运营和用户都容易理解 |
| 按原价扣已上课 | 适合合同明确写了退费按原价扣除的俱乐部 |
| 手动调整实退金额 | 管理员可在系统建议金额基础上改 |

一期建议：

1. 系统给出建议退款金额。
2. 默认按“剩余付费课时”计算退款。
3. 管理员允许手动修改实退金额。
4. 修改必须填写原因。
5. 实退金额不能超过当前待确认余额，特殊情况必须走管理员审批。
6. 涉及赠送课已使用时，必须提示，不自动扣款。

退款流水：

| 字段 | 值 |
|---|---:|
| `cashDelta` | -实退金额 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | -实退金额 |

已确认收入不因为正常退款回退。

## 4. 会员充值

例：用户充值 5000。

| 字段 | 值 |
|---|---:|
| `cashDelta` | +5000 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | +5000 |

如果有赠送金额，例如充 5000 送 498：

- `cashDelta` 只记 5000。
- 赠送金额进入权益记录。
- 赠送部分不算实收。

## 5. 储值订场

例：用户用储值订场 240。

| 字段 | 值 |
|---|---:|
| `cashDelta` | 0 |
| `recognizedRevenueDelta` | +240 |
| `deferredRevenueDelta` | -240 |

同时储值余额减少 240。

## 6. 现场直接订场

例：用户现场微信支付 200 订场。

| 字段 | 值 |
|---|---:|
| `cashDelta` | +200 |
| `recognizedRevenueDelta` | +200 |
| `deferredRevenueDelta` | 0 |

因为钱和服务同一天完成，不进入预收。

## 7. 大众点评/券核销

一期简单处理：

- 大众点评体验课、订场券、小班券统一建成“券类产品”。
- 运营核销时关联学员、排课或订场。
- 核销当天确认收入。
- 一期暂按“核销即收款并确认”处理，也就是 `cashDelta` 和 `recognizedRevenueDelta` 同时增加。
- 平台真实结算、手续费、到账差异后续再做独立的平台结算能力。

建议底层预留字段：

| 字段 | 用途 |
|---|---|
| `platformGrossAmount` | 平台券面或成交金额 |
| `platformFeeAmount` | 平台手续费 |
| `platformNetAmount` | 平台预计结算金额 |
| `settlementStatus` | 未结算 / 已结算 / 差异 |

一期可以先不做平台手续费计算，但字段和模型要能扩展。

## 8. 纯赠送权益

例：送用户 1 节体验课。

财务：

| 字段 | 值 |
|---|---:|
| `cashDelta` | 0 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | 0 |

权益：

- 赠送课时 +1。

赠送课被使用时：

- 已上课 +1。
- 教练工作量 +1。
- 用户赠送课时 -1。
- 收入仍然为 0。

## 9. 教练迟到免费课

例：教练迟到，本节课免费，不扣用户课时。

处理：

| 项目 | 结果 |
|---|---|
| 学员已上课 | +1 |
| 教练工作量 | +1 |
| 用户课包余额 | 不扣 |
| 已确认收入 | 0 |
| 待确认收入 | 不变 |
| 财务流水 | 可写补偿审计流水，金额为 0 |

教练承担场地费属于“教练结算”，不混进用户收入。

严格边界：

- 用户侧财务流水只记录用户收入和用户权益。
- 教练承担场地费只进入教练结算模块。
- 不允许用教练承担费用去冲减用户收入。

## 10. 内部占场

内部占场只记录场地使用，不进收入。

| 字段 | 值 |
|---|---:|
| `cashDelta` | 0 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | 0 |

## 七、冲正规则

冲正是财务系统的审计底线，必须严格。

## 1. 冲正定义

冲正不是删除，也不是编辑。

冲正是：

> 为一条错误流水生成一条金额完全相反的新流水，从账面上抵消它。

## 2. 冲正流程

```text
第一步：找到错误的原始流水
第二步：填写冲正原因
第三步：系统生成镜像反向流水
第四步：原始流水标记为 reversed
第五步：如有需要，重新录入正确业务
```

## 3. 冲正限制

1. 一条流水只能被冲正一次。
2. 冲正必须关联原始流水。
3. 冲正必须填写原因。
4. 只有管理员可以冲正。
5. 已冲正流水不能再次退款、再次冲正、再次编辑。
6. 冲正和重新录入是两步，不能合并成一步。

禁止：

- 直接修改原始流水金额。
- 删除流水。
- 用备注写“此条作废”但不生成冲正流水。

## 八、权限设计

财务权限不是附加功能，是核心安全要求。

| 操作 | 运营 | 财务 | 管理员 | 教练 |
|---|:---:|:---:|:---:|:---:|
| 录入课包购买 | 是 | 否 | 是 | 否 |
| 录入会员充值 | 是 | 否 | 是 | 否 |
| 录入订场消费 | 是 | 否 | 是 | 否 |
| 排课/消课 | 是 | 否 | 是 | 仅自己相关 |
| 核销券 | 是 | 否 | 是 | 否 |
| 发起退款 | 否 | 否 | 是 | 否 |
| 冲正流水 | 否 | 否 | 是 | 否 |
| 赠送权益 | 是 | 否 | 是 | 否 |
| 补偿权益 | 是 | 否 | 是 | 否 |
| 查看财务总览 | 否 | 是 | 是 | 否 |
| 查看财务流水 | 否 | 是 | 是 | 否 |
| 导出报表 | 否 | 是 | 是 | 否 |
| 修改商品价格 | 否 | 否 | 是 | 否 |
| 查看学员余额 | 是 | 是 | 是 | 否 |
| 查看自己课表 | 否 | 否 | 是 | 是 |

说明：

- 财务角色默认只读，不直接改业务。
- 运营只做业务动作，不直接编辑财务流水。
- 管理员负责退款、冲正、价格规则等高风险操作。

## 九、异常检查

财务中心必须有“异常检查”能力。

一期建议检查：

| 检查项 | 触发条件 |
|---|---|
| 等式检查 | 期初待确认 + 上线后实收 != 上线后确认收入 + 当前待确认 |
| 负余额检查 | 课时余额、储值余额、券余额小于 0 |
| 孤儿流水 | 财务流水找不到来源业务单据 |
| 重复消课 | 同一学员同一排课重复扣课 |
| 重复订场扣款 | 同一订场记录重复扣储值 |
| 缺支付渠道 | 收款类流水没有支付渠道 |
| 缺关联用户 | 流水没有学员/订场用户 |
| 异常改价 | 成交价和系统价不一致但没有原因 |
| 冲正异常 | 被冲正流水再次被操作 |

异常检查不一定第一期自动定时跑，但财务中心要能一键查看。

等式检查统一使用：

```text
无历史期初：所有 cashDelta 加总 = 所有 recognizedRevenueDelta 加总 + 所有 deferredRevenueDelta 加总
有历史期初：期初待确认 + 上线后 cashDelta 加总 = 上线后 recognizedRevenueDelta 加总 + 当前待确认
```

如果按用户、按来源单据、按预收账户检查，也使用同一套等式。

## 十、并发和一致性

订场和储值扣款有并发风险。

典型问题：

- 用户余额只够订一次场，但两台手机同时下单。
- 运营重复点击保存，导致重复扣课或重复扣储值。

系统要求：

1. 扣课、扣储值、写财务流水必须是同一个原子操作。
2. 同一个来源单据只能生成一次财务流水。
3. 储值余额、课时余额不能扣成负数。
4. 后端必须用幂等键防重复，例如 `sourceType + sourceId + ledgerType`。
5. 后续如接入高并发小程序订场，需要增加版本号或锁机制。

一期如果还不是高并发场景，也必须先做：

- 后端重复提交保护。
- 余额不足校验。
- 同源单据唯一流水校验。
- 线上支付必须等微信/支付宝/小程序支付回调成功后，财务流水才生效。
- 现金、银行转账等手工收款，必须由有权限的人确认到账后才生效。

支付状态建议：

| 状态 | 含义 |
|---|---|
| `pending` | 已创建待支付，不计入财务有效金额 |
| `success` | 已到账，计入财务有效金额 |
| `failed` | 支付失败，不计入财务有效金额 |

## 十一、多租户预留

如果未来要做 SaaS，不能等到后期再改底层。

从一期开始，新增核心表必须包含：

```text
tenantId 或 clubId
```

需要包含的表：

- 财务总账 `ft_financial_ledger`
- 商品类表
- 购买记录
- 权益账户
- 权益流水
- 订场记录
- 会员账户
- 会员订单
- 券核销记录
- 用户/角色/权限

当前只有自己俱乐部时，可以统一写：

```text
clubId = default
```

但字段必须存在，后续 SaaS 扩展才不会重写大量逻辑。

## 十二、SaaS 规则边界

一期不要做复杂规则引擎。

原因：

- 规则引擎会显著增加开发复杂度。
- 当前最重要的是先把 FlowTennis 自己的账跑准。
- 等真实业务跑稳后，再把高频差异抽象成配置。

一期建议：

- 底层字段预留。
- 规则先代码固化。
- 商品、渠道、退款方式做有限配置。

后续 SaaS 再逐步配置化：

| 能力 | 一期 | 后续 SaaS |
|---|---|---|
| 商品类型 | 固定几类 | 可配置 |
| 支付渠道 | 固定枚举 | 可配置 |
| 收入确认规则 | 固定主规则 | 可配置 |
| 退款规则 | 有限配置 | 可配置 |
| 平台手续费 | 预留字段 | 完整结算 |
| 多俱乐部隔离 | 字段预留 | 完整租户管理 |

## 十三、现有页面调整

不建议新增大量页面。

应在现有页面上补齐入口和追溯。

| 现有页面 | 调整方向 |
|---|---|
| 学员信息 | 作为用户总入口，显示课包、储值、券、赠送权益汇总 |
| 购买记录 | 作为课包收款入口，补支付渠道、销售来源、退款入口、财务流水追溯 |
| 排课表 | 作为课程消耗入口，消课后自动写确认收入 |
| 订场用户 | 整理成订场账户、储值余额、订场消费流水 |
| 会员管理 | 和订场储值打通，避免两套余额 |
| 会员方案 | 只定义商品规则，不直接记收入 |
| 价格管理 | 只定义场地价格，不直接记收入 |
| 财务中心 | 重做为查询、对账、导出中心 |
| 教练结算 | 单独处理教练费用，不混入用户收入 |
| 课包余额审计页 | 保留为底层审计页，不作为日常入口 |

## 十四、财务中心规划

财务中心一期就要有基础版，不能拖到最后。

建议 Tab：

| Tab | 作用 |
|---|---|
| 财务总览 | 本月实收、确认收入、待确认余额、退款 |
| 财务流水 | 查看所有财务总账流水 |
| 收入确认明细 | 看每一笔确认收入来自哪次消课、订场、核销 |
| 预收余额 | 看每个用户、课包、会员卡还有多少未确认 |
| 异常检查 | 看负余额、孤儿流水、重复扣款、缺字段 |
| 月报/季报导出 | 给代账公司 |

一期基础版最低要求：

1. 财务总览。
2. 财务流水查询。
3. 预收余额查询。
4. 月报/季报导出。

## 十五、成本和毛利

一期财务核心先解决收入确认。

但系统要预留“确认成本”能力。

原因：

- 老板最终关心利润，不只是收入。
- 网球俱乐部最大变动成本通常是教练课时费。

建议：

1. 一期不把教练成本混进收入确认主流程。
2. 排课消课时，可以预留 `coachCostAmount` 或后续结算关联。
3. 教练结算模块独立生成成本数据。
4. 财务中心后续增加“课时毛利”：

```text
课时毛利 = 确认收入 - 教练课时成本
```

不要在一期为了毛利拖慢收入确认上线。

## 十六、历史数据处理

现有系统已经有真实学员、课包、会员、订场、消课数据，不能按全新系统处理。

推荐采用：

```text
期初快照 + 新增流水
```

不建议第一期全量迁移所有历史明细。

原因：

- 历史 Excel 和系统数据质量可能不一致。
- 全量补写历史流水工作量大，容易引入新错误。
- 一期目标是让上线后新业务准确，历史可查但不强行重算。

## 1. 期初快照规则

在财务总账上线日，为每个仍有余额或未完成权益的用户写入期初快照。

期初快照可以包括：

| 类型 | 写入内容 |
|---|---|
| 课包期初 | 当前剩余付费课时、赠送课时、对应待确认金额 |
| 储值期初 | 当前储值余额、对应待确认金额 |
| 会员期初 | 当前会员余额、到期时间、待确认金额 |
| 券期初 | 未核销券数量或状态 |

期初快照流水：

| 字段 | 说明 |
|---|---|
| `ledgerType` | `opening_balance` |
| `cashDelta` | 0 |
| `recognizedRevenueDelta` | 0 |
| `deferredRevenueDelta` | 期初待确认金额 |
| `openingDeferredRevenueDelta` | 期初待确认金额 |
| `sourceType` | `opening_snapshot` |
| `reason` | 财务总账上线期初导入 |

注意：

- 期初快照不代表当天新收款，所以 `cashDelta` 为 0。
- 为了让全局等式成立，期初快照必须单独进入 `openingDeferredRevenueDelta`，报表按“期初待确认”展示。
- 上线后的新收款、新消耗、新退款必须全部走正式财务流水。

## 2. 历史追溯方式

上线日前的历史明细：

- 仍保留在原购买记录、消课流水、订场历史、Excel 导入记录里。
- 财务总账只记录期初余额，不强行伪造历史流水。
- 如后续确实需要完整历史，可做单独迁移项目。

## 十七、历史数据沙盘验证

正式开发前，建议先拿 10-20 个真实用户做沙盘。

验证对象：

- 买课包
- 买课送课
- 消课
- 会员充值
- 储值订场
- 现场订场
- 退款
- 赠送课
- 教练迟到免费
- 大众点评券核销

每个用户用表格跑一遍：

| 用户 | 实收 | 已确认收入 | 待确认收入 | 剩余权益 | 是否能追溯 |
|---|---:|---:|---:|---|---|

目标：

- 公式跑通。
- 特殊场景不冲突。
- 运营看得懂。
- 财务能接受。

沙盘通过后再进入代码实现。

这是阶段 1 的前置条件：

> 沙盘没有跑通，不开始写财务总账代码。

## 十八、分阶段落地计划

## 阶段 1：统一财务地基

目标：

先建立可信的财务总账和基础财务中心。

范围：

0. 先完成 10-20 个真实用户沙盘验证。
1. 新增 `ft_financial_ledger` 财务总账模型。
2. 所有新增表预留 `clubId` / `tenantId`。
3. 定义动作枚举、业务类型、支付渠道、销售来源。
4. 定义冲正规则。
5. 定义权限矩阵。
6. 定义历史期初快照导入规则。
7. 财务中心基础版：总览、流水、预收余额、异常检查入口。

验收：

- 能看到统一财务流水。
- 每条流水能追溯来源单据。
- 能汇总本月实收、确认收入、待确认余额。
- 冲正不能改原记录，只能生成反向流水。

## 阶段 2：课程收入打通

目标：

课包购买和消课自动生成财务流水。

范围：

1. 购买记录生成课包收款流水。
2. 课包权益生成时记录实收分摊规则。
3. 排课消课生成课包消课流水。
4. 买课送课拆分付费课时和赠送课时，默认先扣付费课时。
5. 赠送课、补偿课金额为 0。
6. 课包退款按建议金额 + 管理员手动调整。

验收：

- 课包购买后待确认增加。
- 消课后确认收入增加、待确认减少。
- 纯赠送课不产生收入。
- 教练迟到免费不扣用户权益、不确认收入。
- 课程收入明细可追溯到购买和排课。

## 阶段 3：订场和会员收入打通

目标：

储值、会员、订场自动形成收入确认。

范围：

1. 会员充值生成实收和待确认。
2. 储值订场生成确认收入和待确认减少。
3. 现场订场生成实收和确认收入。
4. 内部占场只记使用，不进收入。
5. 会员退款按剩余储值处理。
6. 订场用户和会员余额统一口径。

验收：

- 储值余额、待确认收入、订场消费能对上。
- 现场订场不进入预收。
- 内部占场不影响收入。
- 订场收入明细可追溯到订场记录。

## 阶段 4：券类和渠道统一

目标：

大众点评、体验课券、小班券不再靠手工乱记。

范围：

1. 增加券类产品。
2. 增加券核销入口。
3. 核销关联学员、排课或订场。
4. 核销生成确认收入流水。
5. 预留平台手续费字段。

验收：

- 每张券能查到核销状态。
- 券收入能按渠道统计。
- 大众点评收入能单独筛选。

## 阶段 5：财务报表完善

目标：

让财务中心可直接给代账公司。

范围：

1. 月报导出。
2. 季报导出。
3. 收入确认明细导出。
4. 预收余额明细导出。
5. 异常检查导出。

验收：

- 代账公司需要的收入确认金额可直接导出。
- 每个报表数字可以点回明细。
- 异常数据不会被静默忽略。

## 阶段 6：SaaS 标准化

目标：

让系统可交付给其他网球俱乐部。

范围：

1. 完整多租户隔离。
2. 商品模板化。
3. 渠道配置化。
4. 退款规则配置化。
5. 角色权限配置化。
6. 操作日志和审计完善。
7. 平台结算和手续费处理。

验收：

- 新俱乐部只需配置商品、价格、渠道、角色即可使用。
- 不同俱乐部数据完全隔离。
- 报表格式统一。

---

## 十九、一期不做的内容

为了避免过度工程，一期不做：

1. 完整规则引擎。
2. 银行流水自动对账。
3. 复杂平台手续费结算。
4. 发票系统。
5. 完整成本核算。
6. 复杂毛利分析。
7. 多俱乐部后台管理台。

一期只把收入确认、预收余额、退款冲正、追溯对账做准。

## 二十、最终判断

最终方案是：

```text
业务动作清楚
权益变化清楚
财务流水不可篡改
报表可追溯
异常能发现
权限能限制
SaaS 字段先预留
规则引擎后置
```

这套方案对运营简单：

> 在购买、排课、订场、核销这些业务页面操作即可。

对财务清楚：

> 所有钱都在财务总账里，能查、能导、能追溯。

对老板有用：

> 能看本月实收、本月确认收入、当前待确认余额，后续还能看毛利。

对 SaaS 可扩展：

> 先用统一模型跑稳，再逐步配置化。
