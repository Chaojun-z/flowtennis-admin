---

## 1. 核心结论

第一阶段只允许做“可审计回滚”，不允许把财务事实从生产库里直接抹掉。

真实回滚分两类：

1. 状态恢复：把被本次操作改过的主记录恢复到操作前状态。
2. 反向冲正：对已经形成财务、权益、消费事实的流水，新增一条反向记录抵消影响。

第一阶段禁止把“回滚”理解成“直接删除所有相关记录”。

---

## 2. 第一阶段允许真实回滚的 operationType

只允许支持现有快照校验已覆盖的 5 类：

| operationType | 第一阶段是否允许执行 | 执行方式 | 前置条件 |
|---|---:|---|---|
| `court-booking` | 允许 | 对 `ft_courts.history` 新增冲正记录 | dry-run 能定位原消费行；金额、支付方式、校区、日期一致 |
| `member-booking` | 允许 | 对 `ft_courts.history` 新增冲正记录，并恢复会员余额口径 | dry-run 能定位原储值扣款行；账户未被后续异常操作污染 |
| `lesson-consume` | 允许 | 新增课包回退流水，恢复 `ft_entitlements` 余额；排课只改状态，不直接删除 | 能定位 `ft_schedule`、`ft_entitlement_ledger`、`ft_entitlements`；无后续基于该消课的二次修数 |
| `package-purchase` | 谨慎允许 | 优先作废购买记录和权益；未产生任何消课时才允许恢复到操作前快照状态 | 该课包没有后续消课、调课、手动调整、退款、修数 |
| `membership-recharge` | 谨慎允许 | 会员订单作废或冲正；会员账户余额按反向流水恢复；`ft_courts.history` 新增冲正 | 充值金额未被后续消费；没有到期清零、权益消耗、会员账户作废等后续动作 |

不在上表内的 `operationType` 第一阶段只能 dry-run 和人工复核，不能进入写模式。

## 3. 只能冲正，不能删除的记录

以下记录一旦进入生产，只能用反向记录或状态作废，不能直接删除：

1. `ft_courts.history` 中的充值、消费、退款、冲正记录。
2. `ft_entitlement_ledger` 课包消耗、回退、作废流水。
3. `ft_membership_benefit_ledger` 会员权益发放、消耗、补发流水。
4. `ft_financial_ledger` 独立财务台账记录。
5. `financePage.normalizedRows` 对应的财务展示事实来源。
6. 已经对外展示过、进入收入统计的 `ft_membership_orders`。
7. 已经产生权益或财务口径的 `ft_purchases`。
8. 已经被消课、反馈、教练确认、财务统计引用过的 `ft_schedule`。

原因很简单：这些记录都是“发生过的经营事实”。错了也要留下“错在哪里、谁冲正、什么时候冲正”的链路。

## 4. 回滚前必须生成的快照

每次真实回滚前必须至少具备 4 份材料：

1. 线上实例确认
   - 请求 `https://www.flowtennis.cn/api/diag`
   - 确认线上 `TS_ENDPOINT` / `TS_INSTANCE`
   - 本地将要写入目标必须与线上完全一致

2. 当前恢复前快照
   - 命令：`npm run snapshot:finance`
   - 用途：记录“准备回滚前”的真实生产状态
   - 保存路径写入回滚报告

3. 原操作前快照
   - 用途：提供可恢复的原始值
   - 缺少它时，更新类记录不能自动恢复，只能停止

4. 原操作后快照或 dry-run 定位报告
   - 用途：证明本次要回滚的 `operationId` / `batchId` 涉及哪些表、哪些记录
   - 命令示例：

```bash
node scripts/rollback-finance-operation-dry-run.js --snapshot <after-snapshot.json> --operation-id <operationId>
```

额外建议保留：

1. 目标记录逐条备份 JSON。
2. 财务页 `/page-data/finance` 返回值备份。
3. 回滚审批记录。
4. 回滚执行日志。

---

## 5. 回滚后如何校验

回滚后必须重新生成快照，并完成三层校验：

1. 业务表校验
   - 目标记录已被作废、恢复或新增冲正。
   - 关联余额正确，例如课包剩余课时、会员余额、权益剩余次数。
   - 不存在重复冲正。

2. 财务校验
   - 命令：

```bash
npm run snapshot:finance
npm run validate:finance-operation -- --before <rollback-before.json> --after <rollback-after.json> --operation-id <rollbackOperationId>
```

   - 对原操作的影响做反向核对：
     - 原来收入增加的，回滚后应等额减少或冲回。
     - 原来已入账增加的，回滚后应等额冲回。
     - 原来未入账增加的，回滚后应等额减少。

3. 线上展示链校验
   - `/api/diag` 仍为 `flowtennis-ue`。
   - `/server/page-data/finance` 已体现回滚后的财务变化。
   - 财务总览、收入流水、已入账流水能看到正确结果。
   - 对应业务页能看到作废/冲正/余额恢复结果。

任一环节不通过，不得宣布“已回滚完成”。

## 6. 防止重复回滚

真实执行能力必须内置幂等保护：

1. 每次回滚生成新的 `rollbackOperationId` 和 `rollbackBatchId`。
2. 每条冲正或作废记录必须写入：
   - `rollbackOfOperationId`
   - `rollbackOfBatchId`
   - `rollbackReason`
   - `rollbackApprovedBy`
   - `rollbackAt`
   - `rollbackBy`
3. 写入前先扫描目标表，发现同一个 `rollbackOfOperationId` / `rollbackOfBatchId` 已存在时立即停止。
4. `operationId` 和 `batchId` 一次只能传一个，禁止两个同时传。
5. 如果 dry-run 找不到目标记录，立即停止，禁止猜测。
6. 如果 dry-run 找到的金额合计与审批金额不一致，立即停止。
7. 如果目标操作后面还有其他依赖操作，立即停止，转人工方案。
8. 回滚报告必须记录“本次是否首次回滚”。

第一阶段建议用独立回滚审计记录保存执行结果；在审计记录落地前，至少要靠冲正记录上的 `rollbackOfOperationId` 防重复。

## 7. 审批和确认参数

真实写模式必须要求以下参数齐全：

| 参数 | 是否必填 | 用途 |
|---|---:|---|
| `--write` | 是 | 明确进入真实写模式 |
| `--operation-id` 或 `--batch-id` | 是 | 锁定唯一目标，只能二选一 |
| `--operation-type` | 是 | 必须属于第一阶段白名单 |
| `--rollback-reason` | 是 | 写入审计和冲正说明 |
| `--operator` | 是 | 实际执行人 |
| `--approved-by` | 是 | 审批人 |
| `--approval-ticket` | 是 | 审批单号、飞书审批链接或用户确认记录 |
| `--before-snapshot` | 是 | 当前恢复前快照 |
| `--source-before-snapshot` | 是 | 原操作前快照 |
| `--source-after-snapshot` | 是 | 原操作后快照或等价定位快照 |
| `--expected-amount` | 是 | 审批金额，必须与 dry-run 合计一致 |
| `--expected-ts-instance` | 是 | 必须为 `flowtennis-ue` |
| `--confirm` | 是 | 固定格式：`ROLLBACK <operationId 或 batchId>` |

生产环境额外要求：

1. 没有 `--write` 永远只 dry-run。
2. 没有审批单号或明确用户确认，禁止写。
3. 没有恢复前快照，禁止写。
4. 线上 `/api/diag` 与本地目标不一致，禁止写。

## 8. 绝对不能直接删除的表

以下表在生产回滚中绝对不能直接 `del`：

1. `ft_courts`
2. `ft_courts.history`
3. `ft_membership_accounts`
4. `ft_membership_orders`
5. `ft_membership_benefit_ledger`
6. `ft_membership_account_events`
7. `ft_purchases`
8. `ft_entitlements`
9. `ft_entitlement_ledger`
10. `ft_schedule`
11. `ft_financial_ledger`
12. `ft_students`
13. `ft_packages`
14. `ft_products`

允许的处理方式：

1. 主记录：状态作废、恢复字段、追加审计字段。
2. 流水记录：新增反向冲正。
3. 余额类记录：用操作前快照恢复，同时保留回滚审计。
4. 财务展示：通过业务事实和冲正记录自然反映，不直接改展示结果。

## 9. 执行流程设计

第一阶段真实执行流程：

1. 运行 dry-run，输出涉及表和记录。
2. 校验 `operationType` 是否在白名单。
3. 校验线上 `/api/diag` 和本地目标一致。
4. 生成当前恢复前快照。
5. 对比原操作前、原操作后、当前恢复前三份快照。
6. 检查目标操作是否已被回滚。
7. 检查目标记录是否被后续操作依赖。
8. 校验审批参数和确认文本。
9. 生成回滚计划。
10. 再次 dry-run 输出“将写入/作废/恢复”的清单。
11. 用户确认后才执行写入。
12. 写入完成后生成恢复后快照。
13. 执行财务校验和线上展示链校验。
14. 输出回滚报告。

## 10. 测试和演练流程

### 10.1 单元测试

覆盖以下场景：

1. 只传 `operationId` 成功。
2. 只传 `batchId` 成功。
3. 同时传两者失败。
4. 不传两者失败。
5. 找不到目标记录失败。
6. 非白名单 `operationType` 失败。
7. 已存在 `rollbackOfOperationId` 时失败。
8. 审批金额与 dry-run 金额不一致失败。
9. 缺少恢复前快照失败。
10. 线上实例与本地目标不一致失败。

### 10.2 本地 fixture 演练

用脱敏快照 fixture 演练：

1. `package-purchase`
2. `lesson-consume`
3. `membership-recharge`
4. `member-booking`
5. `court-booking`

每类都要验证：

1. dry-run 能定位记录。
2. 写计划不包含直接删除禁删表。
3. 冲正金额与原金额相反。
4. 回滚后快照差异符合预期。

### 10.3 staging 演练

只在 staging 实例做真实写入演练：

1. 创建一笔低金额测试业务。
2. 生成操作前、操作后快照。
3. dry-run 定位该 `operationId`。
4. 执行真实回滚。
5. 生成恢复后快照。
6. 校验业务表、财务页接口、余额字段。
7. 重复执行同一回滚，必须被幂等保护拦住。

### 10.4 生产演练

生产只允许用户明确批准后做低金额、可解释的真实业务演练：

1. 优先选 1 元散客订场或用户指定金额。
2. 先记录审批确认。
3. 生成操作前快照。
4. 完成真实业务操作。
5. 生成操作后快照。
6. 运行 dry-run。
7. 用户再次确认回滚。
8. 执行真实回滚。
9. 生成恢复后快照。
10. 校验线上财务总览、收入流水、已入账流水、业务页。

生产演练不能用虚假大额数据，不能跳过审批，不能跳过快照。
