## 1. 第一阶段只做哪些流水类型

第一阶段只覆盖当前财务页已经在算的动作。目标是让新台账复刻旧口径，不引入新财务规则。

### 1.1 一期纳入

| 流水类型 | 对应动作 | 金额变化 |
|---|---|---|
| `package_receipt` | 课包购买 | `cashDelta +`，`deferredRevenueDelta +` |
| `lesson_consume` | 排课消课、手工扣课 | `recognizedRevenueDelta +`，`deferredRevenueDelta -` |
| `lesson_return` | 取消排课退回、手工退回 | `recognizedRevenueDelta -`，`deferredRevenueDelta +` |
| `direct_course_receipt` | 直接收款课程 | `cashDelta +`，`recognizedRevenueDelta +` |
| `course_surcharge` | 课程补差、场地费补差 | `cashDelta +`，`recognizedRevenueDelta +` |
| `membership_recharge` | 会员储值、开卡、续充 | `cashDelta +`，`deferredRevenueDelta +` |
| `member_booking_consume` | 会员储值订场扣款 | `recognizedRevenueDelta +`，`deferredRevenueDelta -` |
| `guest_booking_receipt` | 散客订场现场收款 | `cashDelta +`，`recognizedRevenueDelta +` |
| `booking_refund` | 订场退款 | 按原支付方式冲减 |
| `booking_reversal` | 订场冲正 | 生成反向流水 |
| `match_fee_sync` | 约球收款同步到订场财务 | `cashDelta +`，`recognizedRevenueDelta +` |
| `match_refund_sync` | 约球退款同步到订场财务 | `cashDelta -`，`recognizedRevenueDelta -` |

### 1.2 一期暂不纳入

| 类型 | 原因 |
|---|---|
| 会员权益核销 | 不是所有权益都有实收来源，不能直接确认为收入 |
| 赠送、补偿 | 需要单独规则，不应混进实收收入 |
| 内部占用 | 当前不应影响收入 |
| 教练结算 | 是成本/结算视角，不属于收入台账第一阶段 |
| 平台手续费 | 需要支付渠道和结算规则，后置 |
| 全量历史回填 | 风险高，第一阶段只做期初差异和新增动作对账 |

## 2. 新增哪些脚本/读模型

第一阶段新增的是“旁路能力”，不改财务页读取链路。

| 类型 | 文件 | 作用 |
|---|---|---|
| 读模型 | `scripts/lib/finance-ledger-read-model.js` | 把 `ft_financial_ledger` 转成和 `financeNormalizedRows` 同形的行 |
| 对账核心 | `scripts/lib/finance-ledger-compare.js` | 对比旧口径 `financeNormalizedRows` 和新台账读模型 |
| 对账脚本 | `scripts/compare-finance-ledger-read-model.js` | 读取本地快照文件，输出新旧口径差异报告 |
| 覆盖率脚本 | `scripts/audit-finance-ledger-coverage.js` | 检查业务记录是否有对应 `operationId / batchId / ledger` |
| 快照扩展 | `scripts/lib/finance-daily-snapshot.js` | 后续实施时只增加 `ft_financial_ledger` 只读采集，不改变旧快照字段 |
| 测试夹具 | `fixtures/finance/ledger-read-model-sample.json` | 固定样本，覆盖一期流水类型 |

脚本只读要求：

1. 默认只读本地快照 JSON。
2. 不直连线上。
3. 不写业务表。
4. 不写 `ft_financial_ledger`。
5. 报告只输出差异，不自动修复。

## 4. 新旧口径比对怎么做

### 4.1 输入

对账脚本只接收本地快照：

```bash
node scripts/compare-finance-ledger-read-model.js --snapshot <snapshot.json>
```

快照内需要同时有：

1. `financePage.normalizedRows`：旧口径。
2. `tables.ft_financial_ledger.rows`：新台账。
3. 相关业务表：用于来源单据回查。

### 4.2 汇总比对

必须比对这些数字：

| 指标 | 旧口径 | 新口径 |
|---|---|---|
| 总实收 | `SUM(cashDelta)` | `SUM(cashDelta / 100)` |
| 总核销确收 | `SUM(recognizedRevenueDelta)` | `SUM(recognizedRevenueDelta / 100)` |
| 待确认收入 | `SUM(deferredRevenueDelta)` | `SUM(deferredRevenueDelta / 100)` |
| 课程实收 | 课程收款行 | `businessType=课程` 收款流水 |
| 课程已入账 | 课程消耗行 | `businessType=课程` 消耗流水 |
| 会员储值 | 会员储值收款行 | `ledgerType=membership_recharge` |
| 会员耗卡核销 | 会员订场储值扣款行 | `ledgerType=member_booking_consume` |
| 散客/约球订场 | 订场收款行 | 订场类流水 |

### 4.3 明细比对

明细按幂等键对齐：

```text
sourceType + sourceId + sourceSubId + ledgerType
```

对不上时输出四类结果：

1. `matched`：新旧都有，金额一致。
2. `amount_mismatch`：新旧都有，金额不同。
3. `missing_ledger`：旧口径有，新台账没有。
4. `missing_legacy`：新台账有，旧口径没有。

### 4.4 允许差异

允许差异必须显式写入报告：

| 差异 | 标记 |
|---|---|
| 历史已核对快照 | `verified_snapshot_gap` |
| 白名单导入增量 | `verified_import_increment` |
| 历史期初差异 | `opening_balance_gap` |
| 缺来源单据 | `missing_source` |
| 重复幂等键 | `duplicate_idempotency_key` |
| 金额尾差 | `rounding_gap` |

不允许脚本自动把差异写回数据库。

## 6. 最小可交付顺序

必须按下面顺序交付，不能跳步切页面。

1. **保护旧页面来源**  
   先补测试，证明财务页仍读 `/page-data/finance` 旧快照。

2. **台账读模型**  
   新增 `finance-ledger-read-model`，只用本地样本测试，不碰业务写入。

3. **新旧对账核心**  
   新增 compare 库，先跑固定 fixture。

4. **只读对账脚本**  
   支持 `--snapshot` 输入，输出差异报告。

5. **覆盖率审计脚本**  
   查业务动作是否有对应台账，不自动补写。

6. **每日快照加入 `ft_financial_ledger`**  
   只扩展快照采集，不改变旧财务页字段。

7. **业务动作旁路写影子流水**  
   逐类接入：先课包购买，再课包消耗，再会员储值，再订场，再约球。

8. **连续对账观察**  
   连续 7 天或 7 个样本批次对账稳定后，再写第二阶段方案。

## 7. 第一阶段验收标准

第一阶段只在以下条件同时满足时算完成：

1. 财务页没有切换来源。
2. 旧财务门禁 `npm run guard:finance` 通过。
3. 新台账读模型测试通过。
4. 新旧对账脚本能输出明确差异。
5. 覆盖率脚本能指出缺失流水。
6. 新增业务动作有 `operationId / batchId`。
7. 没有任何脚本自动修数、自动补账、自动写线上。
