# 真实财务台账写入第一阶段方案

> 本文只设计第一阶段方案，不实现。  
> 第一阶段目标：在不切换财务页、不改财务口径的前提下，把新发生的稳定业务动作同步 shadow 写入 `ft_financial_ledger`，为后续财务页切换到真实台账做准备。

## 1. 第一阶段只覆盖哪些动作

第一阶段只覆盖“线上管理后台正常录入、金额口径明确、能从单个业务源稳定推导”的动作。

| 动作 | 当前业务入口 | 当前业务事实来源 | 是否纳入第一阶段 |
| --- | --- | --- | --- |
| 课包购买收款 | `POST /purchases` | `ft_purchases` + `ft_entitlements` | 纳入 |
| 排课课包消课 | `POST /schedule`、`PUT /schedule/:id` | `ft_entitlement_ledger` | 纳入 |
| 排课取消/编辑产生的课包退回 | `PUT /schedule/:id` 取消或编辑 | `ft_entitlement_ledger` | 纳入 |
| 直接收款课程 | `POST /schedule`、`PUT /schedule/:id` | `ft_schedule` | 纳入 |
| 课程补差/场地费 | `POST /schedule`、`PUT /schedule/:id` | `ft_schedule` + 现有 `ft_financial_ledger` 记录 | 纳入并规范化 |
| 会员充值/续充 | `POST /membership-orders` | `ft_membership_orders` + `ft_courts.history` | 纳入 |
| 会员储值订场消费 | `PUT /courts/:id` 或排课储值扣款写入 `ft_courts.history` | `ft_courts.history` | 纳入 |
| 散客订场现场收款 | `POST /courts`、`PUT /courts/:id` | `ft_courts.history` | 纳入 |

第一阶段只处理新增或编辑后“当前仍有效”的业务事实，不做历史全量补账。

## 2. 每个动作对应什么 ledgerType

沿用现有 `scripts/lib/finance-ledger-read-model.js` 里的命名，不另起一套。

| 动作 | ledgerType | cashDelta | recognizedRevenueDelta | deferredRevenueDelta |
| --- | --- | ---: | ---: | ---: |
| 课包购买收款 | `package_receipt` | `+实收金额` | `0` | `+实收金额` |
| 排课课包消课 | `lesson_consume` | `0` | `+本次核销金额` | `-本次核销金额` |
| 排课退回课包课时 | `lesson_return` | `0` | `-本次退回金额` | `+本次退回金额` |
| 直接收款课程 | `direct_course_receipt` | `+实收金额` | `+实收金额` | `0` |
| 课程补差/场地费 | `course_surcharge` | `+补差金额` | `+补差金额` | `0` |
| 会员充值/续充 | `membership_recharge` | `+充值实收` | `0` | `+充值实收` |
| 会员储值订场消费 | `member_booking_consume` | `0` | `+扣款金额` | `-扣款金额` |
| 散客订场现场收款 | `guest_booking_receipt` | `+实收金额` | `+实收金额` | `0` |

金额统一以“分”为单位写入 `ft_financial_ledger`，展示层再转回元。

## 3. 幂等键怎么设计，防止重复流水

第一阶段必须使用稳定幂等键，禁止用随机 UUID 当财务流水主键。

统一规则：

```text
idempotencyKey = sourceType + "|" + sourceId + "|" + sourceSubId + "|" + ledgerType
ledgerId = "ledger-v1-" + sha1(idempotencyKey).slice(0, 24)
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `sourceType` | 来源类型，例如 `purchase`、`schedule`、`entitlement_ledger`、`membership_order`、`court_history` |
| `sourceId` | 主业务记录 ID，例如购买 ID、排课 ID、会员订单 ID、订场用户 ID |
| `sourceSubId` | 同一主业务记录下的子流水 ID，例如 `ft_courts.history.id`、`ft_entitlement_ledger.id`；没有则为空 |
| `ledgerType` | 本条财务流水类型 |

各动作建议：

| 动作 | sourceType | sourceId | sourceSubId |
| --- | --- | --- | --- |
| 课包购买收款 | `purchase` | `purchase.id` | 空 |
| 课包消课/退回 | `entitlement_ledger` | `entitlementLedger.id` | `scheduleId` 可选 |
| 直接收款课程 | `schedule` | `schedule.id` | `direct_receipt` |
| 课程补差/场地费 | `schedule` | `schedule.id` | `field_fee` |
| 会员充值/续充 | `membership_order` | `membershipOrder.id` | 空 |
| 会员储值订场消费 | `court_history` | `court.id` | `historyRow.id` |
| 散客订场现场收款 | `court_history` | `court.id` | `historyRow.id` |

同一个幂等键再次写入时，只允许覆盖同一条 ledger，不允许新增第二条。

## 4. 写入失败如何处理

第一阶段是 shadow 写入，不能因为财务台账写入失败导致正常业务无法保存。

处理规则：

1. 业务表先按现有流程写入成功。
2. 业务表写入失败时，不写 `ft_financial_ledger`。
3. shadow ledger 写入失败时：
   - 不回滚已成功的业务写入；
   - API 返回业务成功，同时带 `financialLedgerShadowWarning`；
   - 服务端记录 `operationId`、`idempotencyKey`、`sourceType`、`sourceId`、错误信息；
   - 后续可用同一幂等键从业务源重放补写。
4. 同一业务动作重试时，幂等键相同，只会补齐或覆盖同一条 ledger。
5. 如果同一次请求里会产生多条 ledger，允许部分失败，但必须在返回和日志里列出失败项。

第二阶段之后，才能讨论“财务台账失败是否阻断业务保存”。第一阶段禁止阻断。

## 5. 如何和现有业务写入保持一致

一致性原则：ledger 不能自己计算一套新业务事实，只能从已经成功保存的业务记录推导。

具体要求：

1. 共用现有 `operationTrace`：
   - `operationId`
   - `batchId`
   - `operationType`
   - `operationAt`
   - `operationBy`
2. 金额来源必须和现有财务聚合一致：
   - 课包购买用 `purchase.amountPaid`
   - 消课金额用现有 `financeRecognizedAmountForConsumeRow` 同口径
   - 会员充值用 `membershipOrder.rechargeAmount`
   - 订场用 `ft_courts.history.amount`
   - 课程补差用 `schedule.fieldFeeAmount`
3. 校区、客户、支付方式、备注等展示字段，只做快照，不参与新口径计算。
4. 编辑业务记录时，使用同一个幂等键覆盖同一条 shadow ledger。
5. 作废业务记录时，不删除 ledger，只把对应 ledger 标记为不可用或写入反向流水；第一阶段优先标记不可用，反向冲正留到第二阶段统一设计。
6. 已经存在的 `course_surcharge` 写入逻辑第一阶段只做规范收口，不能改它当前影响财务页的行为。

## 6. 如何先 shadow 写入，不切换财务页

第一阶段只写 shadow ledger，不让财务页读它做总览或流水。

shadow 标记建议：

```text
ledgerVersion = "shadow-ledger-v1"
ledgerMode = "shadow"
readModelEnabled = false
```

上线顺序必须是：

1. 先确认线上财务页仍走现有 `/page-data/finance` 口径。
2. 确认旧前端 fallback 不会因为 `ft_financial_ledger` 有 shadow 行而切成“只读 ledger”。
3. 如果存在 fallback 风险，必须先加 shadow 排除保护，但仍不改变财务页口径。
4. 再开启 shadow 写入。
5. 每日或每批次用对比脚本验证：
   - 现有财务页归一化流水；
   - shadow ledger 反算流水；
   - 两边金额和条数差异。

第一阶段禁止：

1. 不把 `ft_financial_ledger` 切成财务页唯一来源。
2. 不替换 `/page-data/finance` 当前聚合逻辑。
3. 不修改财务总览、收入流水、已入账流水口径。
4. 不做历史补账后直接宣称财务页已切换。

## 7. 哪些动作暂不纳入

以下动作第一阶段暂不写真实 ledger：

1. 历史导入、修数脚本、repair/cleanup/finalize/archive 类脚本。
2. `courts/import`、`courts/migrate-legacy`、`courts/migrate-finance-legacy`。
3. 约球 Postgres 到 TableStore 的财务同步。
4. 购买记录编辑、删除、作废后的完整冲正口径。
5. 会员订单编辑、删除、作废后的完整冲正口径。
6. 订场退款、冲正、代用户订场待结算。
7. 会员权益赠送、权益消耗、学员权益流水。
8. 手动课包调整 `manual-adjust`。
9. 历史存量 `ft_courts.history`、`ft_purchases`、`ft_entitlement_ledger` 的全量回填。
10. 财务页读模型切换、财务基线升级、日报口径升级。

这些动作要等第一阶段 shadow 对平后，再按单独方案逐项纳入。

## 8. 验收测试清单

### 8.1 静态检查

1. 没有修改财务页展示口径。
2. 没有让 `/page-data/finance` 改读 `ft_financial_ledger`。
3. 没有新增生产导入或修数脚本。
4. 没有硬编码密钥、Token、数据库连接串。

### 8.2 单动作测试

每个纳入动作至少测一笔：

1. 业务记录写入成功。
2. 生成 1 条预期 ledger。
3. `ledgerType` 正确。
4. `cashDelta`、`recognizedRevenueDelta`、`deferredRevenueDelta` 正确。
5. `operationId` 或 `batchId` 和业务记录一致。
6. 重复提交或重试后，ledger 仍只有 1 条。
7. shadow ledger 写入失败时，业务记录仍成功，返回 warning。

### 8.3 财务口径不变测试

1. 操作前跑一次财务快照。
2. 执行业务动作。
3. 操作后跑一次财务快照。
4. 现有财务页变化必须和未引入 ledger 前一致。
5. shadow ledger 对比结果只作为旁路报告，不参与页面展示。
6. `npm run guard:finance` 仍通过。

### 8.4 对账测试

对每个动作验证：

1. 从业务源生成的 shadow ledger 数量正确。
2. 从 shadow ledger 反算的归一化流水，能和现有 `financeNormalizedRows` 对上。
3. 差异报告能指出具体 `idempotencyKey`。
4. 金额误差不得超过 0.01 元。

### 8.5 回滚与恢复测试

1. 删除或作废业务记录时，不物理删除 ledger。
2. 使用同一幂等键重放补写，不产生重复行。
3. ledger 写入失败后，能从业务源按 `operationId` 或 `idempotencyKey` 找回并补写。
4. 出现对账差异时，能定位到具体业务源记录和 ledger 行。

## 9. 第一阶段完成标准

同时满足以下条件才算第一阶段完成：

1. 新发生的纳入动作都有 shadow ledger。
2. shadow ledger 不影响现有财务页。
3. 同一业务动作重复执行不会产生重复 ledger。
4. 写入失败不会破坏业务写入。
5. 对比报告能证明 shadow ledger 和现有财务归一化流水一致。
6. 暂不纳入动作没有被顺手接入。
