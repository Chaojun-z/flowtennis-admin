# 教学售卖链路治理说明

这份文档只解决一件事：

- 以后这个项目里的教学售卖逻辑，到底以什么为准

---

## 一、当前生效口径

当前教学售卖唯一有效主链路：

`售卖课包 packages -> 购买记录 purchases -> 课包余额 entitlements -> 排课消课 schedule`

解释：

- `售卖课包` 负责定义卖什么、怎么卖、怎么用
- `购买记录` 负责记录成交事实
- `课包余额` 负责承接学员可用课时
- `排课` 负责实际消课

这条链路就是后续新增需求的默认落点，也就是：

- 活跃主链：`packages / purchases / entitlements / entitlement_ledger / schedule`
- 不再把 `products / classes / plans` 当成新增业务入口

---

## 二、当前三类对象的治理分层

### 1. 活跃主链

- 页面：`售卖课包`、`购买记录`、`权益账户`、`排课表`
- 接口：`/packages`、`/purchases`、`/entitlements`、`/entitlement-ledger`、`/schedule`
- 口径：新增教学售卖、购课、消课、余额、履约，默认都走这里

### 2. 历史兼容页面

- `课程产品`
- `班次管理`
- `学习计划`

口径：

- 页面还在，主要为了旧数据维护、核对、追溯
- 不再作为新需求的页面设计起点

### 3. 历史兼容接口

- `/products`
- `/classes`
- `/plans`

口径：

- `/plans` 只保留读取与按班次自动生成，不允许独立写入
- `/products`、`/classes` 目前仍保留写能力，用于历史页面维护和旧链路过渡
- 在没有确认 UI 已彻底脱离前，不主动冻结 `/products`、`/classes`

---

## 三、停用口径

下面 3 个模块暂时停用，不再作为新增功能依赖：

- `课程产品 products`
- `班次管理 classes`
- `学习计划 plans`

这里的“停用”定义是：

- 历史数据保留
- 旧代码暂时保留
- 可以兼容读取
- 不能再作为新需求的设计起点
- 不能再往里面继续加业务规则

---

## 四、后续开发红线

以后新增或修改下面这些需求时：

- 课程售卖
- 购课
- 消课
- 学员剩余课时
- 教学履约
- 排课推荐课包
- 课包有效期、教练、校区、时段限制

默认只能从这几个对象继续扩展：

- `packages`
- `purchases`
- `entitlements`
- `entitlement_ledger`
- `schedule`
- `students`

不要再新增任何“必须先有课程产品 / 班次 / 学习计划”的前置依赖。

---

## 五、允许保留的旧模块用途

`products / classes / plans` 目前只允许承担这几种用途：

- 历史数据兼容
- 老页面只读展示
- 老逻辑平滑过渡
- 数据核对和追溯

不允许承担：

- 新售卖规则入口
- 新排课前置条件
- 新数据模型源头
- 新联动规则中心

---

## 六、实施原则

为了避免误伤线上数据，这次和后续都遵守下面 4 条：

1. 不先删库、不先删历史数据
2. 先隐藏旧入口，再去掉新链路依赖
3. 新功能先接 `售卖课包 -> 购买记录 -> 课包余额`
4. 等新链路稳定后，再评估是否物理清理旧模块

---

## 七、给后续线程的明确指令

如果你是新线程或新接手的人，先按下面顺序判断：

1. 这个需求是不是教学售卖或教学履约问题
2. 如果是，先看 `packages / purchases / entitlements / schedule`
3. 除非明确是历史兼容修复，否则不要先去 `products / classes / plans`
4. 如果你的方案又把新逻辑接回 `products / classes / plans`，先停下，重新评估

---

## 八、当前建议的系统认知

业务上可以把系统理解成两层：

- 现行层：`packages / purchases / entitlements / schedule`
- 历史兼容层：`products / classes / plans`

后续目标不是继续强化历史兼容层，而是逐步把它边缘化。

---

## 九、Phase 3 清理门槛

只有同时满足下面条件，才进入第三阶段物理清理评估：

1. 学员页、购买记录页、排课页的日常操作已经不再依赖 `products / classes / plans`
2. 可见管理员页面的聚合加载和背景加载不再把 `products / classes / plans` 当作活跃主链依赖
3. 历史兼容页面已经明确是只读/兼容查看口径，不再承接新增业务入口
4. 历史数据追溯仍可通过 `packages / purchases / entitlements / schedule` 加上兼容字段完成
5. 确认不存在必须依赖旧表写入的线上运营动作

第三阶段评估项：

- 是否物理删除 `products / classes / plans` 页面残壳
- 是否冻结 `/products`、`/classes` 写接口
- 是否继续保留 `/plans` 查询接口
- 是否需要补历史字段迁移或只读审计导出

在第三阶段评估完成前，禁止直接删表、删接口、删历史数据。
