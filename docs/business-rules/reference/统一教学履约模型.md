结论：**先不要直接改教练端页面。**  
现在最薄弱的是底层数据关系和统一校验。如果先改页面，只会把错误展示得更清楚，但不会解决“这里改了那里没改”的问题。

我看了现有底层，系统已经有这些表：

```text
课程产品 products
售卖课包 packages
购买记录 purchases
权益账户 entitlements
权益流水 entitlement_ledger
学员 students
班次 classes
学习计划 plans
排课 schedule
课后反馈 feedbacks
教练 coaches
校区 campuses
订场 courts
```

目前方向是对的，但还没有形成一个“统一教学履约模型”。

---

**核心原则**

以后系统里必须明确：

```text
课程产品 = 课程模板
售卖课包 = 可以卖给学员的商品
购买记录 = 学员买了一次
权益账户 = 学员还剩多少课
权益流水 = 每一次扣课/退课的证据
排课 = 真正发生的一节课
反馈 = 这节课上完后的记录
```

最关键一句：

```text
课时余额只能由权益流水计算，不能前端随便改。
```

---

**我建议的主链路**

标准链路应该是：

```text
课程产品
  ↓
售卖课包
  ↓
购买记录
  ↓ 自动生成
权益账户
  ↓ 排课时选择/推荐
排课表
  ↓ 自动写入
权益流水
  ↓ 同步影响
权益账户余额 / 学习计划 / 班次进度 / 教练运营 / 学员详情
```

也就是说，**排课表是教学履约的核心入口**。  
只要排了一节有效课，就必须明确：

- 谁上课
- 上什么课
- 哪个教练
- 哪个校区
- 哪个场地
- 消耗哪个权益账户
- 消耗几节课
- 是否需要课后反馈

---

**现在最大的风险点**

1. **多人班次和单个权益账户冲突**

现在排课逻辑偏向“一节课绑定一个权益账户”。  
但实际班次可能有多个学员，每个学员应该扣自己的课包。

正确做法应该是：

```text
一条排课
  对应多个学员
  每个学员各自绑定一个权益账户
  每个学员各自产生一条权益流水
```

否则团课、多人私教、训练营都会出错。

2. **课包卖出后还能随便改规则**

售卖课包一旦产生购买记录，核心字段就不能随便改：

- 课程类型
- 课时数
- 有效期
- 可用教练
- 可用校区
- 可用时间段
- 人数限制

否则历史购买和新规则会混在一起。

建议规则：

```text
未售出课包：可以完整编辑
已售出课包：只能停用、改备注、改展示名；不能改核心规则
```

3. **课程产品、课包、班次的职责需要分清**

课程产品不是课包。  
课程产品只定义“这是什么课”，比如：

```text
成人私教
青少年团课
训练营
```

售卖课包才定义：

```text
多少钱
多少节
什么时候能买
什么时候能用
哪些教练可用
哪些校区可用
```

班次是教学组织，不应该直接承担售卖和余额逻辑。

4. **班次进度、学习计划、权益余额存在重复**

现在班次有 `usedLessons`，学习计划也有 `usedLessons`，权益账户也有 `usedLessons`。  
这很容易不一致。

建议定义权威来源：

```text
权益余额：以权益流水为准
班次进度：以排课记录统计为准
学习计划：由班次 + 排课 + 反馈生成展示
```

不要让三个地方都能独立改课时。

5. **教练、校区、学员改名/删除影响不完整**

目前已经有一部分联动，但还不够。比如：

- 教练改名后，课包里的可用教练也要处理
- 校区删除前，要检查课包、权益、排课、班次、学员是否还在用
- 学员改名后，购买、权益、排课、反馈都要同步
- 已经产生流水的数据不能直接删除，只能停用/作废

---

**统一校验规则**

我建议后续开发先做一套统一规则，不要每个页面各写各的。

## 1. 课程产品

允许：

- 新建
- 编辑名称、类型、备注
- 未被使用时删除

禁止：

- 已被班次或课包使用后直接删除
- 已被使用后随便改课程类型导致历史数据混乱

## 2. 售卖课包

保存时必须校验：

- 课程产品存在
- 课时数 > 0
- 价格不能小于 0
- 有效期合法
- 可购买日期合法
- 可使用日期合法
- 可用时间段合法
- 可用教练存在
- 可用校区存在
- 人数限制 > 0

已售出后：

- 不能改核心规则
- 可以停用
- 可以改备注
- 可以改展示名称，但历史购买记录是否同步要明确

## 3. 购买记录

新增购买时必须校验：

- 学员存在
- 课包存在且启用
- 购买日期在售卖期内
- 实收金额合法
- 保存购买记录后，必须自动生成权益账户

购买记录产生消耗后：

- 不能改学员
- 不能改课包
- 不能改购买日期
- 不能直接删除
- 只能作废，但有消耗流水时不能作废

## 4. 权益账户

权益账户不能手工直接改余额。

只能通过：

```text
排课扣课
取消排课退课
管理员调整流水
```

每次变化都必须写流水。

需要状态：

```text
正常
已用完
已过期
已作废
```

## 5. 排课表

排课是最关键的校验点。

保存排课时必须校验：

- 开始时间、结束时间完整
- 结束时间晚于开始时间
- 教练存在
- 校区存在
- 场地存在
- 学员存在
- 班次存在
- 课程类型匹配
- 教练时间不能冲突
- 学员时间不能冲突
- 场地时间不能冲突
- 跨校区间隔不足要提醒
- 每个学员必须有可用权益账户
- 权益账户剩余课时足够
- 权益账户可用校区匹配
- 权益账户可用教练匹配
- 权益账户可用时间匹配
- 权益账户人数限制匹配

多人课必须变成：

```text
排课 A
- 学员 1：扣权益账户 X，1 节
- 学员 2：扣权益账户 Y，1 节
- 学员 3：扣权益账户 Z，1 节
```

不能再只存一个 `entitlementId`。

## 6. 课后反馈

反馈必须绑定具体排课。

有反馈后，排课不能再随便改这些字段：

- 学员
- 班次
- 权益账户
- 上课时间
- 校区
- 场地
- 教练
- 课程类型

否则反馈和真实课程对不上。

**管理端统一方案**

管理端建议按“业务中台”重新理解，不是单页堆字段。

## A. 商品与权益

包含：

```text
课程产品
售卖课包
购买记录
权益账户
权益流水
```

作用：管卖课、管余额、管扣课依据。

## B. 教学管理

包含：

```text
学员信息
班次管理
学习计划
排课表
课后反馈
```

作用：管教学过程。

## C. 教练运营

包含：

```text
教练今日课表
教练周/月工作量
未反馈课程
跨校区风险
时间冲突
```

作用：管教练执行情况。

这三块的数据要互相串，但职责不能混。

**开发计划**

## 第一阶段：数据关系冻结

目标：先把规则定死，不改大页面。

要做：

- 梳理所有表字段
- 明确每个字段的来源
- 明确哪些字段是快照，哪些字段要同步
- 明确哪些字段禁止修改
- 明确删除、停用、作废规则
- 写一份字段关系文档

产出：

```text
数据关系说明
字段字典
修改/删除规则
核心校验清单
```

## 第二阶段：后端统一校验

目标：先保证不会产生脏数据。

要做：

- 把课包校验统一到后端
- 把购买生成权益统一到后端
- 把排课扣课统一到后端
- 把取消排课退课统一到后端
- 把教练/校区/学员引用检查补全
- 增加数据完整性测试

这一阶段先不要重点改 UI。

## 第三阶段：重做排课扣课模型

目标：支持多人课、团课、训练营。

要做：

- 排课支持多个学员
- 每个学员选择自己的权益账户
- 保存排课时生成多条权益流水
- 取消排课时逐条退回
- 编辑排课时严格判断哪些能改、哪些不能改

这是最核心的一步。

## 第四阶段：管理端页面统一

目标：让管理员能看懂整体链路。

要做：

- 学员详情展示：购买记录、权益账户、排课、反馈
- 权益账户展示：余额、有效期、消耗流水
- 排课详情展示：每个学员扣了哪个课包
- 班次详情展示：学员列表、课时进度、历史排课、反馈情况
- 教练运营展示：今日课表、未反馈、风险

## 第五阶段：教练端重构

目标：教练只看跟自己上课有关的信息，不看财务敏感信息。

教练端可看：

- 今日/本周课表
- 时间
- 校区
- 场地
- 学员
- 班次
- 课程类型
- 剩余课时
- 反馈状态

教练端不可看：

- 课包价格
- 实收金额
- 支付方式
- 购买流水

## 第六阶段：上线前数据体检

上线前必须做一个“数据体检脚本”，只检查，不自动乱改。

检查内容：

- 排课没有学员
- 排课没有校区/场地
- 排课没有权益账户
- 多人排课只绑定一个权益账户
- 权益余额为负
- 权益账户没有购买记录
- 购买记录没有权益账户
- 课包引用了不存在的课程产品
- 课包引用了不存在的教练/校区
- 学员改名后快照不一致
- 已反馈排课仍被修改过核心字段

有问题先出报告，再决定怎么修。

---

**我的推荐执行顺序**

不要从页面开始。  
建议按这个顺序：

```text
1. 数据关系文档
2. 后端统一规则
3. 多学员排课扣课模型
4. 管理端联动展示
5. 教练端工作台
6. 数据体检和上线验收
```

这样做的原因很简单：  
**管理端是数据源，教练端只是使用视角。管理端不稳，教练端一定会乱。**

我建议下一步先产出一份正式文档：

```text
FlowTennis 教学履约与权益账户统一需求方案
```

里面固定：

- 表关系
- 字段字典
- 页面职责
- 校验规则
- 开发阶段
- 验收标准
