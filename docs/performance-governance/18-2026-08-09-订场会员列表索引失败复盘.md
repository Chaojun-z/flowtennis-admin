# 订场用户 / 会员管理 1 秒加载失败复盘与后续禁令

## 1. 结论

本次“订场用户 / 会员管理首屏 1 秒加载”尝试，在性能目标上失败。

已经做到：

1. 新建行级列表索引表。
2. 完成生产首轮重建。
3. 和旧事实口径完成 5 类场景对账。
4. 确认默认首屏能显示最新业务排序下的数据。
5. 确认没有用当前页数量冒充 total。

没有做到：

1. 首屏稳定 1 秒内返回。
2. 校区筛选、日期筛选、搜索、翻页稳定 1 秒内返回。
3. 避免每次请求远程扫描整张行级索引表。

因此这次方案不能作为最终上线方案。

## 2. 本次实际做了什么

新增生产表：

1. `ft_court_account_list_index`
2. `ft_court_account_list_index_tasks`

写入结果：

1. `ft_court_account_list_index` 写入 776 条列表行。
2. `ft_court_account_list_index_tasks` 写入首轮重建完成标记。
3. 未写入、未修改订场、会员、财务、课包、权益、上课记录等业务事实表。

对账结果：

| 场景 | 对账结果 | facts total | index total |
| --- | --- | --- | --- |
| 默认首屏 | 一致 | 776 | 776 |
| 校区筛选 | 一致 | 727 | 727 |
| 日期筛选 | 一致 | 31 | 31 |
| 搜索 | 一致 | 2 | 2 |
| 会员管理 | 一致 | 53 | 53 |

## 3. 为什么失败

失败原因不是口径对账失败，而是读取架构仍然慢。

本次实现的请求链路是：

1. 从 `ft_court_account_list_index_tasks` 读取完成标记。
2. 从 `ft_court_account_list_index` 远程扫描全部 776 条索引行。
3. 在服务端内存里做筛选、排序、统计、分页。
4. 返回当前页。

问题在第 2 步：

`每次请求仍然需要跨网络远程扫描整张索引表。`

这比直接扫原始事实表安全，但不等于快。实际测试中，远程扫描 776 条索引行仍可能达到数秒甚至更久。

## 4. 本次暴露的错误判断

错误判断：

`以为 776 条行级索引很小，远程全表扫描也能稳定 1 秒内。`

实际结果：

`跨网络 TableStore 全表扫描即使只有 776 条，也不能作为 1 秒首屏方案。`

以后禁止再把“行级索引 + 每次全扫”包装成 1 秒方案。

## 5. 必须保留的正确部分

本次仍有部分正确经验可以保留：

1. 不能先分页再筛选。
2. 不能先取 pageSize 条再排序。
3. total 必须来自完整筛选结果。
4. 首屏默认排序必须有业务含义，不能依赖 TableStore 主键扫描顺序。
5. 详情抽屉不能用列表轻字段反推，必须单个回源拿完整详情。
6. 新读模型或索引必须有完成标记，防止半成品启用。
7. 新旧口径对账不通过，不得启用新读链路。

## 6. 后续禁止事项

后续任何线程处理订场用户 / 会员管理 / 高敏感列表性能时，禁止：

1. 禁止每次请求远程扫描整张 `ft_court_account_list_index` 后承诺 1 秒。
2. 禁止每次请求远程扫描原始事实表后承诺 1 秒。
3. 禁止为了快减少业务筛选条件。
4. 禁止用当前页数量冒充 total。
5. 禁止用 TableStore 主键扫描顺序当默认最新排序。
6. 禁止用列表轻字段反推详情抽屉。
7. 禁止跳过新旧口径对账。
8. 禁止只测热缓存最好一次就宣布成功。

## 7. 后续可行方向

如果用户目标仍是 1 秒内，下一版必须改变读取方式。

推荐方向：

1. 快照包
   - 把完整列表结果提前打包成少量快照记录。
   - 请求时读取少量固定快照包，而不是扫描 776 条索引行。

2. 分片快照
   - 按校区、日期区间、会员类型等稳定维度拆快照。
   - 常用筛选直接读对应快照分片。

3. 预排序页
   - 对默认排序预先生成第 1 页、第 2 页等页包。
   - 首屏直接读第 1 页包，同时读取对应 total/summary。

4. 搜索索引
   - 搜索不能靠每次全量扫描字符串匹配。
   - 如果搜索必须 1 秒内，应使用专门搜索索引或搜索快照。

## 8. 正确上线门槛

下一版上线前必须同时满足：

1. 默认首屏 3 次均在用户目标内。
2. 校区筛选 3 次均在用户目标内。
3. 日期筛选 3 次均在用户目标内。
4. 搜索 3 次均在用户目标内。
5. 翻页 3 次均在用户目标内。
6. 新旧口径对账通过。
7. 详情抽屉完整数据回源通过。
8. 新增 / 修改 / 删除写链同步策略明确。
9. 同步失败补偿策略明确。
10. 半成品快照不会被启用。

## 9. 对当前生产表的处理建议

当前已创建的两张表只属于新读链路实验表：

1. `ft_court_account_list_index`
2. `ft_court_account_list_index_tasks`

处理建议：

1. 不要把它们当作最终 1 秒方案。
2. 不要让页面只依赖它们做远程全表扫描。
3. 后续如果做快照包，可以把它们作为重建输入之一，但仍必须重新对账。
4. 未经明确确认，不要删除生产表，也不要清空生产表。

1. 本方案是否避免请求时远程全表扫描事实表？
2. 本方案是否避免请求时远程全表扫描行级索引表？

任一答案为否，就不要进入代码实现。
