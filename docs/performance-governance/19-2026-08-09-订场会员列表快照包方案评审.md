# 订场用户 / 会员管理 1 秒加载：快照包方案评审

## 1. 结论

目标可以继续做，但不能沿用“每次请求远程扫描 776 条索引行”的方案。

下一版必须改成：

`事实表 -> 行级读模型 -> 快照包 -> 页面列表接口`

其中：

1. 事实表仍然是唯一业务源。
2. 行级读模型只负责把单个订场用户 / 会员的列表字段算准。
3. 快照包负责把列表首屏和筛选所需数据提前打包好。
4. 页面请求只读少量固定快照包，不再远程全表扫描事实表，也不再远程全表扫描行级索引表。

## 2. 为什么这版比上次靠谱

上次失败点：

`请求时仍然远程扫描整张 ft_court_account_list_index。`

这次必须改掉这个点：

1. 请求时不扫 `ft_courts`。
2. 请求时不扫会员、财务、权益事实表。
3. 请求时不扫 `ft_court_account_list_index` 全表。
4. 请求时只按固定 id 读取少量快照包。
5. 快照包读入后，在服务端内存里完成完整筛选、排序、统计、分页。

这才有机会稳定进入 1 秒。

## 3. 核心表设计

### 3.1 行级读模型表

表名：

`ft_court_account_list_index`

用途：

1. 每个订场用户 / 会员一行。
2. 保存列表展示需要的轻字段。
3. 不保存详情抽屉完整明细。
4. 不作为业务事实源。

状态：

1. 已有实验表。
2. 不能直接当最终 1 秒方案。
3. 后续可以作为快照包重建输入。

### 3.2 快照包表

表名建议：

`ft_court_account_list_snapshot`

用途：

1. 保存已经打包好的完整列表轻数据。
2. 保存默认排序下的结果。
3. 保存筛选项、统计所需字段。
4. 保存快照完成标记。

建议记录类型：

| id 示例 | 类型 | 用途 |
| --- | --- | --- |
| `active:meta` | 元信息 | 当前可用快照版本、总行数、分片数、生成时间、状态 |
| `active:chunk:000` | 数据包 | 第 1 个列表数据包 |
| `active:chunk:001` | 数据包 | 第 2 个列表数据包 |
| `active:delta` | 增量包 | 快照生成后新增 / 修改 / 删除的少量变化 |
| `building:meta` | 构建中元信息 | 新快照构建中，不对外启用 |
| `building:chunk:000` | 构建中数据包 | 新快照数据，未完成前不启用 |

### 3.3 快照任务表

表名建议：

`ft_court_account_list_snapshot_tasks`

用途：

1. 记录快照重建任务。
2. 记录失败原因。
3. 支持补偿重跑。
4. 支持人工排查。

## 4. 页面请求怎么走

列表接口：

`/page-data/court-account-list-view`

请求流程：

1. 读取 `active:meta`。
2. 根据 meta 里的 chunk 数量，按固定 id 读取 `active:chunk:*`。
3. 读取 `active:delta`。
4. 合并基础快照和增量包。
5. 在完整集合上筛选。
6. 在筛选后集合上排序。
7. 计算筛选后的 total 和顶部统计。
8. 最后分页返回当前页。

关键点：

`筛选、排序、统计发生在分页前。`

所以不会重演线索池“先分页后筛选 / total 错”的问题。

## 5. 每天新增 / 修改数据怎么办

新增或修改订场用户 / 会员时，不能只写事实表。

正确写链：

1. 原业务事实表照常写入。
2. 同步重算受影响的单个行级读模型。
3. 把这个变化写入 `active:delta` 增量包。
4. 标记快照需要后台合并重建。
5. 后台任务把 delta 合并进新的完整快照。
6. 新快照完整写完并对账通过后，原子切换 `active:meta` 到新版本。

这样做到：

1. 新增数据不会等到夜间任务才出现。
2. delta 包失败时有任务记录。
3. 快照没合并完成时，列表仍能读 `active` 快照 + `delta`，不返回旧数据。
4. 半成品 `building` 快照不会被页面使用。

## 6. 删除或作废数据怎么办

删除 / 隐藏 / 作废订场用户或会员时：

1. 原业务事实表按原逻辑处理。
2. 行级读模型标记为 deleted / hidden / voided。
3. `active:delta` 记录该 id 的删除或隐藏状态。
4. 页面合并快照时先应用 delta。
5. 筛选前先剔除不该展示的记录。
6. 后台合并重建后，完整快照里不再包含该记录。

## 7. 搜索怎么保证 1 秒

搜索不能再靠远程扫描事实表。

第一版可行方案：

1. 快照包里保存搜索所需轻字段：
   - 姓名
   - 手机
   - 微信名
   - 会员标签
   - 订场账户 id
2. 请求时读取快照包后在内存搜索。
3. 数据量当前 776 条，内存搜索可控。

如果后续数据量继续上涨，例如几万条，再升级为专门搜索索引。

## 8. 日期筛选怎么保证口径

日期筛选必须继续沿用旧口径：

1. 从事实源或行级读模型中提前保存日期筛选所需字段。
2. 快照包不能删掉日期筛选必须依赖的字段。
3. 日期筛选时先在完整集合上筛选。
4. 筛选后再计算 total 和顶部统计。
5. 最后分页。

禁止：

1. 只看当前页日期。
2. 为了快删掉退款、冲正、会员扣款等影响金额统计的口径。

## 9. 详情抽屉怎么处理

详情抽屉不走快照包。

用户点击某个订场用户 / 会员详情时：

1. 使用单个 id 请求详情。
2. 后端回源事实表。
3. 返回完整订场历史、会员详情、权益流水等详情数据。

快照包只服务列表，不反推详情。

## 10. 如何避免半成品启用

快照必须使用双版本切换：

1. 当前线上可读版本叫 `active`。
2. 正在生成的新版本叫 `building`。
3. `building` 写 chunk 时，页面完全不读。
4. 所有 chunk 写完后，先做校验。
5. 校验通过后，才把 `active:meta` 指向新版本。
6. 校验失败，不切换。

页面只认：

`active:meta.status = done`

其它状态全部不启用。

## 11. 如何对账

上线前必须做 5 类对账：

1. 默认首屏
2. 校区筛选
3. 日期筛选
4. 搜索
5. 会员管理

每类都要比：

1. total 是否一致。
2. 首条 id 是否一致。
3. 当前页 id 顺序是否一致。
4. 顶部统计是否一致。
5. 关键金额是否一致。

对账不通过：

1. 不写 `active:meta`。
2. 不启用快照。
3. 不提交。

## 12. 性能验收

必须实测：

| 场景 | 次数 | 目标 |
| --- | --- | --- |
| 默认首屏 | 3 次 | 每次 1 秒内 |
| 校区筛选 | 3 次 | 每次 1 秒内 |
| 日期筛选 | 3 次 | 每次 1 秒内 |
| 搜索 | 3 次 | 每次 1 秒内 |
| 翻页 | 3 次 | 每次 1 秒内 |

如果某一项超过 1 秒：

1. 不能说完成。
2. 必须继续定位。
3. 如果定位不出安全方案，就停止。

## 13. 首批实施边界

只做：

1. 订场用户列表。
2. 会员管理列表。
3. 列表读取链路。
4. 快照包读取。
5. 快照重建和校验。
6. 写链增量同步。

不做：

1. 不改会员业务口径。
2. 不改订场业务口径。
3. 不改财务口径。
4. 不改课包口径。
5. 不改权益口径。
6. 不改上课记录口径。
7. 不改事实表写入含义。
8. 不调用 `/load-all`。
9. 不碰经营分析。

## 14. 风险和控制

### 14.1 风险：delta 越积越多

控制：

1. delta 数量超过阈值后强制后台合并。
2. 合并成功后清空 delta。
3. 合并失败继续读 active + delta，不返回旧数据。

### 14.2 风险：快照包太大

控制：

1. 构建时按大小拆 chunk。
2. 单个 chunk 不塞满。
3. 页面请求按 meta 读取固定 chunk。

### 14.3 风险：写链漏同步

控制：

1. 列出所有订场 / 会员主写入口。
2. 每个入口补同步测试。
3. 新增写入口必须触发快照 delta。

### 14.4 风险：旧口径和新口径不一致

控制：

1. 快照只从已对账读模型生成。
2. 上线前跑固定样本。
3. 上线前跑完整统计对账。

## 15. 是否建议现在直接写代码

不建议直接写业务代码。

建议执行顺序：

1. 先清理或隔离上一轮失败实验代码。
2. 保留失败复盘文档。
3. 用户确认本方案。
4. 再按最小范围实现快照包。
5. 实测 5 类场景各 3 次。
6. 达不到 1 秒，不提交。

## 16. 给非技术决策的一句话

上次做的是“整理了一份清单，但每次还要把整份清单从远程数据库搬回来”。

下一版要做的是“提前把清单压成几个包，页面只拿包，不再一条条搬”。

只有这样才值得继续冲 1 秒。
