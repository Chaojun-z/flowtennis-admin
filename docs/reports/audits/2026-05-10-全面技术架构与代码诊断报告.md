# FlowTennis 全面技术架构与代码诊断报告

> 版本：2026-05-10  
> 目标读者：技术负责人、外部架构顾问、接手开发、其他 AI  
> 文档目标：让一个没有上下文的新技术，看完后能判断当前系统的真实架构、风险源、为什么会频繁误伤线上数据，以及后续应该怎么升级。

---

## 1. 先说结论

FlowTennis 现在不是一个“功能很多但还能稳步迭代”的系统，而是一个：

- 业务已经很重
- 数据已经上生产
- 代码和数据边界还没真正切开
- 开发、修数、导数、上线共用一套主干代码和同一批线上表

的系统。

这意味着：

1. 改一个小功能，不一定只影响这个功能。
2. 改课包、排课、会员、订场，可能顺手影响财务口径。
3. 上线动作和修复动作没有真正隔离。
4. 现在继续高频叠加需求，边际风险会越来越高。

如果目标是未来做 SaaS、多俱乐部、多权限、多租户，当前状态**不适合直接横向扩张**。  
必须先做一次“架构止血 + 数据边界收口 + 发布机制升级”。

## 3. 项目现状总览

### 3.1 产品形态

当前仓库实际承载了 6 类东西：

1. 管理后台 Web
2. 教练端 Web 登录视图
3. 教练端 PWA 外壳
4. 教练端微信小程序
5. 约球小程序 / 约球子系统
6. 一批直接操作线上数据的审计 / 修复 / 导入脚本

也就是说，这不是单纯的“后台项目”，而是：

- 业务系统
- 多终端客户端集合
- 小程序客户端
- PWA 外壳
- 半独立约球子系统
- 运维修复工具箱

混在一个仓库里。

### 3.2 当前技术栈

- 前端：原生 HTML + CSS + JavaScript 单页应用
- 后端：Node.js + Vercel Serverless Function
- 主存储：阿里云 TableStore
- 约球模块：PostgreSQL
- 本地开发：Express 包一层 Vercel 风格 handler
- 测试：Node 脚本测试 + 少量 Python 测试

### 3.3 当前部署方式

- GitHub 推送后由 Vercel 自动部署
- 小程序直接请求线上 `https://www.flowtennis.cn/api`
- 仓库内脚本通过 `.env` 直接连接真实 TableStore / Postgres

结论：

- 运行环境简单
- 部署方便
- 但“开发、发布、修数、导数”的隔离很弱

## 4. 当前代码结构

### 4.1 关键文件分布

当前代码的真实核心集中在这些文件：

- 后端主入口：`api/index.js`
- 前端主页面：`public/index.html`
- 前端全局状态：`public/assets/scripts/core/state.js`
- 前端 API 封装：`public/assets/scripts/core/api.js`
- 前端页面脚本：`public/assets/scripts/pages/*.js`
- 小程序核心页面：`wechat-miniprogram/miniprogram/pages/schedule/schedule.js`
- 运维修复脚本：`scripts/*.js`、`scripts/*.py`
- 测试：`tests/*.test.js`、`tests/*.test.py`

### 4.2 体量信号

当前几个关键文件的体量：

- `api/index.js`：5591 行
- `public/index.html`：671 行
- `public/assets/scripts/core/state.js`：504 行
- `public/assets/scripts/pages/courts.js`：1218 行
- `public/assets/scripts/pages/coachops.js`：1151 行
- `public/assets/scripts/pages/schedule.js`：758 行
- 小程序 `schedule.js`：1909 行

这说明：

1. 后端是单文件巨石。
2. 前端虽然做了按页拆分，但仍然是共享全局状态的单页模式。
3. 小程序也已经进入高复杂度状态。

### 4.3 结构判断

这不是标准前后端分层项目，更不是成熟 SaaS 常见的：

- 前端组件化
- 后端模块化
- 领域服务分层
- 数据访问层独立
- 统一迁移体系

当前更接近：

- 单页 Web 巨石
- 单入口 API 巨石
- 多张业务表直接拼装页面
- 多条业务链同时写同一批主数据表

## 5. 当前运行架构

### 5.1 Web 管理后台

- 静态资源由 `public/` 提供
- 浏览器统一走 `/api/*`
- `public/assets/scripts/core/api.js` 用 `fetch('/api' + path)` 调用接口
- 前端通过 `state.js` 维护全局数据数组：
  - `students`
  - `courts`
  - `packages`
  - `purchases`
  - `entitlements`
  - `entitlementLedger`
  - `financialLedger`
  - `membership*`
  - `schedule`
  - `classes`
  - `coaches`
  - `campuses`

前端本质不是“每页一套独立数据”，而是“多个页面共享一批全局数据容器”。

### 5.2 后端 API

后端所有核心逻辑几乎都在 `api/index.js` 内，包括：

- 登录鉴权
- TableStore 读写封装
- Postgres 约球逻辑
- 业务校验
- 购买与权益生成
- 排课与扣课
- 订场财务
- 会员账户与会员订单
- 页面聚合接口
- 初始化 / 补种子 / 修复逻辑

结论：

- 入口统一，开发快
- 但职责过多，影响范围极大

### 5.3 微信小程序

小程序配置文件直接写死：

- `API_BASE_URL: 'https://www.flowtennis.cn/api'`

这意味着小程序默认直连线上 API，而不是天然区分测试环境和正式环境。

### 5.4 教练端 PWA

仓库中有：

- `public/manifest.webmanifest`
- `public/service-worker.js`

说明当前教练端不仅有 Web 登录视图，还有 PWA 包装形态。

这意味着：

- 同一套 Web 代码
- 多一种安装和缓存外壳
- 仍然共用同一后端和同一数据口径

### 5.5 约球子系统

约球并不是一个普通页面，而是：

- 有独立 `match_*` Postgres 表
- 有自己的报名 / 到场 / AA / 退款链路
- 又会把财务结果同步写回订场侧

所以它当前是“半独立系统”，不是完全隔离产品。

## 6. 当前数据架构

### 6.1 主存储分裂为两套

当前实际不是单数据库架构，而是双存储并存：

#### A. TableStore

承载主业务：

- 学员
- 课包
- 购买
- 权益
- 排课
- 订场
- 财务流水
- 会员
- 校区
- 教练
- 用户账号

#### B. PostgreSQL

承载约球模块：

- `match_users`
- `match_posts`
- `match_registrations`
- `match_attendance`
- `match_bookings`
- `match_fee_records`
- `match_fee_splits`
- `match_operation_logs`
- `match_replacements`

### 6.2 核心业务表

从业务上看，主要分 3 组：

#### 教学履约链

- `ft_students`
- `ft_products`
- `ft_packages`
- `ft_purchases`
- `ft_entitlements`
- `ft_entitlement_ledger`
- `ft_classes`
- `ft_plans`
- `ft_schedule`
- `ft_feedbacks`

#### 订场 / 会员链

- `ft_courts`
- `ft_financial_ledger`
- `ft_membership_plans`
- `ft_membership_accounts`
- `ft_membership_orders`
- `ft_membership_benefit_ledger`
- `ft_membership_account_events`

#### 基础配置

- `ft_users`
- `ft_coaches`
- `ft_campuses`
- `ft_price_plans`

### 6.3 当前主业务口径

仓库文档和代码都在强调当前治理口径：

`packages -> purchases -> entitlements -> schedule`

也就是：

1. 定义可售课包
2. 产生购买记录
3. 自动生成权益账户
4. 排课时消课

但现实情况是，系统仍保留了大量历史兼容链路：

- `products`
- `classes`
- `plans`
- 订场财务历史
- 会员账户财务历史
- 历史收入导入

所以当前是“新链路治理中 + 旧链路仍在线”。

## 7. 当前权限模型

### 7.1 账号模型非常初级

当前主要是：

- `admin`
- `editor`

再叠加：

- `coachName`
- `coachId`
- `matchPermissions`

这不是 SaaS 时代标准的权限模型，更像“单店内部账号 + 部分教练视角裁剪”。

### 7.2 当前权限本质

当前权限主要是：

1. 管理员是否能看和改全部
2. 教练是否只能看自己相关数据
3. 约球是否有单独 `match_ops / match_finance`

### 7.3 当前没有真正具备的能力

目前缺少：

- 租户级权限
- 店级数据隔离
- 财务专岗权限域
- 细粒度行级权限
- 基于组织的资源归属控制
- 权限配置后台

结论：

当前权限不是“可扩展的 SaaS 权限体系”，只是“单业务内部角色裁剪”。

## 9. 当前线上数据是怎么被改动的

这是本次诊断最关键的一部分。

### 9.1 线上数据改动入口不止一个

当前线上主数据可能被下面几类入口改写：

1. 管理后台页面操作
2. API 初始化逻辑
3. 自动修复逻辑
4. 历史导入脚本
5. 手工修复脚本
6. 约球财务同步逻辑

### 9.2 API 启动初始化会做写入

`api/index.js` 的 `init()` 不是纯初始化内存，而是可能直接对数据表做写入：

- 建表
- 默认用户 bootstrap
- 默认校区 bootstrap
- 默认价格方案同步
- `bootstrapMabaoFinanceSeed()`
- `repairImportedLedgerDuplicates()`

也就是说：

**服务启动不是纯只读动作，而可能是写生产数据动作。**

### 9.3 Seed/修复逻辑会改教学与财务底座

`bootstrapMabaoFinanceSeed()` 会涉及：

- `ft_students`
- `ft_products`
- `ft_packages`
- `ft_purchases`
- `ft_entitlements`
- `ft_entitlement_ledger`

这解释了为什么：

“改课包功能”看起来没碰财务，但财务结果还是变了。

因为：

- 财务页依赖 `purchases / entitlements / entitlement_ledger`
- 这些表会被启动 bootstrap / repair 影响

### 9.4 修复脚本可直接写线上

仓库 `scripts/` 下有大量脚本：

- 审计
- 导入
- 查找
- 修复
- 合并
- 补单
- 恢复

很多脚本具备共同特征：

1. `dotenv.config()` 直接读 `.env`
2. `new TableStore.Client(...)` 直接连生产表
3. 部分脚本 `process.argv.includes('--write')` 后直接执行写入

这说明：

当前仓库内自带一整套“可直接改线上数据”的工具链。

这不是坏事，但在没有严格流程隔离时，会极大放大风险。

### 9.5 约球模块也会反向写订场财务

约球逻辑虽然在 Postgres，但会同步写入 `match-court-finance` 对应的订场财务历史。

这说明系统里已经存在：

- 一个功能域的数据，写入另一个功能域的财务链路

如果边界不清晰，就会越来越难控。

## 10. 为什么会出现“改小功能却把线上收入改坏”

这是用户最关心的问题，必须单独讲清楚。

### 10.1 不是单点 bug，而是机制问题

当前反复出现事故，不是因为某一个函数刚好写错了，而是因为：

**多个业务域共用同一批核心表和同一批派生口径。**

### 10.2 真实原因拆开看有 6 层

#### 原因 1：财务不是独立账本

财务页不是只读 `ft_financial_ledger`。

它还依赖：

- `purchases`
- `entitlements`
- `entitlement_ledger`
- `courts`
- `membership_orders`
- `membership_benefit_ledger`

所以改教学数据，财务汇总也可能变。

#### 原因 2：初始化/修复逻辑能改真实业务表

服务启动阶段和热实例修复阶段，都可能改：

- 课包
- 购买
- 权益
- 权益流水

这会造成“你以为只是发代码，实际上是重新碰了线上业务底账”。

#### 原因 3：开发、修数、导数共用同仓和同环境

当前不是：

- 开发代码仓
- 运维修复仓
- 数据迁移仓

分离，而是全放在一起。

结果就是：

- 功能代码和修复代码耦合
- 上线和修数心理边界模糊

#### 原因 4：后端单文件巨石，共享函数过多

`api/index.js` 同时处理：

- 路由
- 校验
- 领域规则
- 数据读写
- 初始化
- 修复

任何局部改动都可能波及共享逻辑。

#### 原因 5：缺少严格发布闸门

当前没有看到：

- GitHub Actions / CI 工作流
- 上线前自动对账闸门
- 财务快照 diff 阻断机制
- staging 环境的强制演练流程

结果就是：

- 有测试，但测试不等于发布闸门
- 能合并，不代表适合上线

#### 原因 6：缺少真正的环境隔离

当前本地开发、小程序、修复脚本、线上 API，都围绕同一套线上模型和强耦合表结构转。

一旦测试环境和线上环境没有被制度性切开，事故就会反复发生。

## 11. 当前测试与质量保障现状

### 11.1 优点

当前测试数量不少，覆盖了：

- 排课规则
- 课包/权益规则
- 会员规则
- 财务页视图
- 约球规则
- 页面加载策略

说明团队并不是“完全裸奔开发”。

### 11.2 但测试形态偏轻

当前很多测试属于：

- 源码字符串断言
- 规则函数断言
- 单文件逻辑断言

它们适合守住：

- 文案
- 某个函数规则
- 某个接口是否存在

但不擅长守住：

- 真实线上数据快照回归
- 多表联动后的财务结果
- 部署后初始化副作用
- 脚本误写线上

### 11.3 当前缺的关键测试能力

缺少：

1. 生产快照回放测试
2. 财务总账前后对比测试
3. 上线前数据校验流水线
4. staging 全链路演练
5. 修复脚本 dry-run 结果自动校验

结论：

当前测试能守住“代码层面的小回归”，守不住“生产数据层面的系统性误伤”。

## 12. 当前运维与发布现状

### 12.1 当前优点

- 部署简单
- 本地启动容易
- 直接 Vercel 发布
- 单仓统一维护

2. 没有明确 staging 环境规范

5. 没有多租户环境管理基础

### 12.3 结果

当前是一个“能持续开发，但不能安全高频上线”的形态。

## 13. 当前架构为什么不适合直接做 SaaS

如果要做 SaaS，至少要满足：

1. 租户隔离
2. 数据隔离
3. 权限隔离
4. 财务隔离
5. 配置隔离
6. 环境隔离
7. 发布隔离

但当前状态有明显缺口：

### 13.1 没有租户主轴

当前核心表没有统一围绕 `tenantId / clubId / organizationId` 建模。

系统更多是：

- 单店
- 多校区

而不是：

- 多租户
- 多俱乐部
- 多组织

### 13.2 校区不等于租户

现在有 `campus`，但 `campus` 只是业务地点，不是租户边界。

不能把：

- 马坡
- 十里堡

当成未来 SaaS 的组织隔离模型。

### 13.3 权限模型不够

当前是角色裁剪，不是租户级 RBAC/ABAC。

### 13.4 财务链路不够独立

SaaS 最怕的不是页面 bug，而是：

- A 客户的数据串到 B 客户
- A 客户的财务被 B 客户逻辑误伤

当前还远没有到可以承载这种要求的程度。

## 14. 现阶段最危险的 10 个问题

按严重度排序：

### P0-1：生产启动逻辑具备写数据能力

后果：

- 发版不是纯代码替换
- 有机会触发真实数据变更

### P0-2：财务口径依赖多业务表拼装，不是独立台账

后果：

- 改教学、会员、订场，可能一起动财务结果

### P0-3：修复脚本与功能代码共仓、共环境、可直写生产

后果：

- 发布和修数边界模糊

### P0-4：缺少发布前财务快照对账闸门

后果：

- 只有出事故后才知道收入变了

### P0-5：单文件后端巨石

后果：

- 功能之间高耦合
- 影响半径不可控

### P1-1：没有统一租户模型

后果：

- 无法安全演进 SaaS

### P1-2：前端仍共享大量全局状态

后果：

- 页面间联动复杂，难定位回归

### P1-3：历史兼容链路仍在线且可写

后果：

- 新旧模型并存，口径不稳

### P1-4：测试偏规则级，缺少生产数据级回归

后果：

- 能防代码小错，防不住真实账务事故

### P1-5：小程序默认连线上 API

后果：

- 客户端联调环境隔离弱

---

## 15. 升级方向总原则

后续升级不能再按“继续加页面、继续补逻辑”推进，而必须先收口下面 5 条原则：

1. **开发与生产隔离**
2. **业务账与财务账隔离**
3. **功能上线与数据修复隔离**
4. **读模型与原始表隔离**
5. **单租户代码路径与多租户架构演进兼容**

---

## 16. 建议升级路线

### 第一阶段：止血期（1~3 天）

目标：先防止再出现“改一个功能把线上财务改坏”。

必须立刻做：

1. 生产环境禁用一切 seed/bootstrap/自动 repair 写入开关。
2. 所有修复脚本默认只读，写入必须显式参数 + 审批。
3. 上线前增加“财务快照对比”。
4. 功能发布与修复脚本执行分开。
5. 小程序和本地开发明确区分测试 API 与正式 API。

### 第二阶段：稳态改造期（1~2 周）

目标：让系统进入“可以持续安全迭代”的状态。

要做：

1. 把 `api/index.js` 先按领域拆层：
   - auth
   - students
   - packages/purchases/entitlements
   - schedule
   - courts/finance
   - memberships
   - matches
   - bootstrap/ops
2. 把财务页改为独立读模型，不再直接拼多张原始业务表。
3. 建立 staging 环境和固定演练数据。
4. 建立发布前自动校验：
   - 收入总额
   - 购买数
   - 权益余额
   - 会员余额
5. 把高风险脚本收口到单独 `ops/` 目录，并补执行说明。

### 第三阶段：架构升级期（2~6 周）

目标：为 SaaS 做真正的基础准备。

要做：

1. 明确租户主轴：`tenantId / clubId`
2. 所有核心表补租户维度设计
3. 权限体系升级为可扩展 RBAC
4. 财务台账独立建模
5. 多环境配置治理
6. 新功能默认按后端读模型模式开发

### 17.1 代码层

## 18. 关于约束机制的正式判断

当前系统不是“规则太少”，而是：

**规则存在于很多地方，但没有形成稳定、统一、可重复触发的约束机制。**

现在的约束主要散落在：

- 线程里的提示词
- 某些冻结决策文档
- 口头共识
- 开发当时的临时记忆

这在长期由 AI 辅助开发的模式下是不够的。

### 合格的约束机制应该分 4 层

#### 第 1 层：`AGENTS.md`

作用：

- 仓库级最高优先级硬规则
- 新线程进入仓库就必须先吃到

适合放：

- 红线
- 禁止事项
- 发布前必须做什么
- 哪类需求默认不得碰财务
- 本地预览不得默认连生产

#### 第 2 层：正式治理文档

作用：

- 沉淀已冻结方向
- 作为外部技术负责人 / 其他 AI 的统一事实依据

适合放：

- 架构诊断
- 财务隔离规则
- 环境治理
- 性能治理
- 前端标准化

#### 第 3 层：Skill

作用：

- 把“这类任务应该怎么做”变成固定流程
- 让 Codex 不靠短期记忆，而靠标准流程自我约束

适合放：

- FlowTennis 总治理 Skill
- 性能治理 Skill
- 标准页改造 Skill
- 财务安全 Skill

#### 第 4 层：Checklist

作用：

- 作为交付前的最后闸门
- 防止“规则知道了，但上线前没真正执行”

适合放：

- 财务回归清单
- 多端冒烟清单
- 发布前检查清单
- 合并前检查清单

### 结论

对你们现在这种长期由 Codex 主导迭代的模式，最稳的不是继续堆长提示词，而是：

`AGENTS.md + 正式治理文档 + Skill + Checklist`

四层一起生效。

## 19. 关于是否迁移 Supabase / Postgres 的正式判断

结论先说：

**值得作为中期升级方向认真评估，但不适合现在立刻全量迁移。**

### 为什么值得评估

当前很多结构性问题，都和现有存储能力及使用方式有关：

1. 高敏感页依赖多表原始大包
2. 后台复杂筛选、排序、聚合代价高
3. 财务读模型和报表能力不适合继续长期靠前端拼装
4. 多租户、权限、审计、报表更适合关系型数据库路线

从长期看，Postgres / Supabase 更适合承接：

- 复杂读模型
- 报表
- 物化视图
- 多租户
- RLS 权限
- 后续 SaaS 演进

### 为什么不适合现在大爆炸全迁

因为当前真正的问题还没先治理完：

1. 主干还不干净
2. 环境还没分层
3. 财务基线还没冻结
4. 高危写入口还没关闸
5. 现有业务边界还没收口

在这个阶段直接全迁，风险很高，容易变成：

- 旧系统没稳住
- 新系统没迁完
- 两边一起乱

### 正确路线

#### 第一阶段：先治理，不迁

先完成：

- 主干清场
- 环境分层
- 财务基线
- 生产写入口关闸
- 高敏感页读模型方向锁定

#### 第二阶段：局部试点迁移

优先迁：

- 高敏感页读模型
- 财务读模型
- 新增报表能力
- 新子系统

而不是一开始就迁整条教学主链。

#### 第三阶段：再决定是否扩大迁移

等试点证明：

- 性能更稳
- 开发效率更高
- 权限和多租户更容易做
- 回归机制已经成熟

再判断是否逐步迁：

- `purchases`
- `entitlements`
- `membership_*`
- `financial_*`

### 结论

Supabase / Postgres 迁移是一个**中期架构升级议题**，不是当前最优先的止血动作。

## 20. 对技术负责人最重要的判断

如果只给技术负责人一句结论，那就是：

**当前最大问题不是“代码脏”，而是“生产数据边界没有被工程机制锁死”。**

所以后续优先级必须是：

1. 先锁生产数据
2. 再稳发布
3. 再拆边界
4. 最后再做 SaaS 扩张

如果顺序反了，结果只会是：

- 功能越来越多
- 数据事故越来越频繁
- 修数时间越来越长
- 团队对系统越来越不信任

## 23. 最终结论

FlowTennis 当前已经不是“是否需要写更多功能”的阶段，而是“必须先把工程底座补上”的阶段。

短期目标不是做得更花，而是做到 3 件事：

1. 改功能不再误伤线上财务
2. 上线前就能发现数据异常
3. 架构开始朝多租户、多权限、财务隔离方向演进

只要这 3 件事没做到，继续高频堆功能，成本会越来越高。
