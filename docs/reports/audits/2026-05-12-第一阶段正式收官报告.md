# FlowTennis 第一阶段正式收官报告

> 日期：2026-05-12  
> 结论：第一阶段可以正式收官  
> 目标：把系统从“高频误伤线上数据、财务口径漂移、环境混乱、预发布不可用”的状态，拉回到“可验收、可回归、可继续迭代”的状态。

---

## 1. 第一阶段正式结论

第一阶段已经完成，当前可以正式收官。

这里的“收官”不是指系统已经变成最终完美架构，而是指：

1. 最危险的问题已经先收住了
2. staging / preview 已经能承担真实验收
3. 财务与线上数据不再主要靠人工记忆和肉眼判断
4. 后续可以切换到新的总领导线程，进入第二阶段

---

- 已建立财务基准数字
- 已建立财务回归脚本

- 约球桥接边界已收口

### B. 主干与治理

- `AGENTS.md` 已落地
- 主干清场方案已完成
- `codex/match-real-launch` 已明确封存，不再作为回主干来源
- `thread26-staging-latest` 已明确为当前正式收官候选

### C. 环境与验收

- `dev / staging / prod` 骨架已建立
- Preview / staging 已可登录
- staging 首轮脱敏导入链已跑通
- 真实 staging 数据源已接入

### D. 页面与数据闭环

- 学员管理：可验收
- 排课表：可验收
- 订场用户：可验收
- 会员管理：可验收
- 财务中心：可验收
- 线索池：可验收
- 教练网页 / PWA：登录恢复
- 教练小程序：反馈保存闭环恢复
- 约球小程序：登录、权限、资料授权闭环收口

### E. 结构治理

- `api/index.js` 已完成多批解耦
- `plans` 旧链已大幅退场
- `scripts` 已完成多批物理迁移与分流

---

## 3. 第一阶段解决了哪些关键问题

### 以前的问题

- 改一个小功能，经常把财务或线上数据改坏
- staging / preview 不能用，或者混着生产数据用
- 生产登录、高危写入、初始化脚本风险很高
- Web / 小程序 / 约球等多端问题一旦出现，很难快速定位
- 仓库脚本和功能开发混在一起，工作区长期脏乱

### 现在的状态

- 财务有基准和回归门禁
- staging 能承接真实验收
- 线上最危险的默认自动写入已收口
- 主要页面都能在 staging 里验
- 多端关键登录闭环已恢复
- 旧教学链已开始系统性退场

---

## 4. 第一阶段没有完成什么

第一阶段收官，不代表后面没有事做。

当前仍未完成的主要是第二阶段任务：

1. `api/index.js` 继续解耦，直到真正健康
2. `products / classes` 活跃依赖继续压缩
3. `scripts` 最终迁移收尾
4. 约球子系统继续独立化
5. 旧链路最终物理退场
6. 性能治理与前端标准化进入正式执行

---

## 5. 当前总健康度判断

如果按“系统能否健康、可持续、安全地继续迭代”来算：

- 第一阶段完成度：`100%`
- 整体长期健康化完成度：`约 80%`

这意味着：

- 第一阶段任务目标已经完成
- 但距离“长期非常健康、结构非常清楚、彻底不再反复出问题”还有后续工作

---

## 6. 第二阶段建议主线

第二阶段不再以“环境和验收能不能跑”为重点，而应转向：

1. 继续压缩旧教学链
2. 继续拆 `api/index.js`
3. 继续清理 `scripts`
4. 再决定性能治理与前端标准化谁先做

建议第二阶段的总口径是：

> 先继续收结构债，再做性能专项和前端专项。

---

## 7. 收官后必须继承的硬约束

以下约束必须带到下一阶段：

1. 非生产默认不得连生产真实数据
2. 财务改动必须先过基准与回归门禁
3. 修数 / 导入 / 功能开发必须分流
4. 不允许重新把新逻辑接回 `products / classes / plans`
5. 不允许再用 `codex/match-real-launch` 当开发主线
6. 不允许绕过 staging 直接拿 production 当验收环境

---

## 8. 最终一句话

第一阶段正式收官。  
系统已经从“高风险、容易乱炸、验收环境不可信”的状态，推进到了“有门禁、有基线、有 staging、有主要页面验收能力”的状态。  
下一阶段可以切换到新的总领导线程，继续做长期健康化改造。
