## 1. 本次结论

当前排课管理慢的证据已经成立：

1. `ft_schedule` 排课投影扫描 3 次平均约 `13.39s`。
2. `ft_courts` 订场用户表扫描 3 次平均约 `28.38s`。
3. `ft_entitlement_ledger` 权益流水扫描 3 次平均约 `12.20s`。
4. 当前排课页首屏仍要求加载 `campuses / students / courts / schedule / coaches / coachProposals / lifecycleMetricsPage`。
5. 保存、取消、删除链路代码里仍存在读取权益、权益流水、订场用户、会员账户等重表的路径。

所以本次性能治理不是“给页面加一个加载兜底”，而是必须把排课列表、详情、保存后刷新从全量读链里拆出来。

## 4. 当前慢链路判断

### 4.1 首屏

当前排课首屏仍会拉：

`campuses + students + courts + schedule + coaches + coachProposals + lifecycleMetricsPage`

其中 `schedule / courts / entitlement_ledger` 任意一个进入首屏链路，都会把用户体验拖到多秒甚至几十秒。

### 4.2 翻页

当前前端翻页如果只是本地分页，翻页本身不一定重新请求后端；但代价是第一页必须先等全量大包加载完成。

长期正确方向：

`翻页应由后端按筛选条件返回下一页，不再要求首屏先拿全量排课。`

### 4.3 查看详情

当前排课详情依赖前端已有全量数据上下文。用户点“查看详情”时，如果全量上下文还没准备好，就会继续等。

长期正确方向：

`详情应按 scheduleId 单独读取 ScheduleDetailView。`

### 4.4 保存、取消、删除

代码只读审计确认：

1. 新增排课会读取权益、教练、用户；涉及储值时会读取订场用户、学员、会员账户。
2. 取消排课会读取反馈、权益流水；涉及储值时会读取订场用户、学员、会员账户。
3. 删除排课会读取权益流水和反馈，并回滚权益、课时、储值等相关链路。

本次没有执行真实保存计时，因为不能为了测性能写生产数据。保存耗时必须在 staging 或脱敏样本上单独测。

## 6. 后续对账必须检查

每个样本后续至少检查：

1. 列表字段：日期、时间、校区、场地、教练、学员、课程类型、状态。
2. 详情字段：和列表同源，不出现另一套状态或名称。
3. 学员详情：能找到对应上课记录。
4. 课包权益：扣课、退课、余额一致。
5. 权益流水：能按 `scheduleId` 对上。
6. 教练端：教练本人日程和后台一致。
7. 财务：不该变化时不变化；该变化时按财务口径变化。
