# 飞书排课表自动同步落地方案

> 版本：2026-07-22
> 状态：落地方案
> 定位：把飞书排课表的新增、修改、删除变更同步到 FlowTennis 管理后台排课系统。

## 1. 目标

实现一条稳定链路：

1. 运营继续维护飞书排课表。
2. 系统自动读取飞书排课表。
3. 飞书表新增课程时，系统自动新增排课。
4. 飞书表修改课程时，系统自动修改对应排课并通知运营群。
5. 飞书表删除课程时，系统通知运营群，运营通过手机确认链接决定是否取消系统排课。
6. 管理后台手动新增的排课不受飞书表同步影响。

## 3. 不新增机器人

本方案只使用现有两个能力：

1. `网球兄弟排课助手`
   - 企业自建应用。
   - 负责读飞书表格、同步系统排课。
2. 现有运营群机器人 webhook
   - 只负责把同步结果发到运营群。
   - 不负责读取表格。
   - 不负责接收群回复。

第一版不做“群里回复同意删除”。删除确认通过手机可打开的系统确认链接完成。

## 4. 自动运行方式

不使用 Vercel Cron。

使用 GitHub Actions 定时触发系统同步接口：

| 项 | 规则 |
|---|---|
| 运行时间 | 北京时间 08:00、18:00 |
| 运行频率 | 每天 2 次 |
| GitHub cron | `0 0-16 * * *` |
| 触发方式 | GitHub Actions 请求系统 cron 接口 |
| 系统接口 | `GET /api/cron/feishu-schedule-sync` |
| 鉴权 | 请求头带 `CRON_SECRET` |

说明：GitHub Actions 的 cron 使用 UTC 时间，`0 0,10 * * *` 对应北京时间 08:00、18:00。

### 6.1 表格结构

| 区域 | 含义 |

| B 列 | 星期 |
| C 列 | 时段 |
| D-G | 场地占用 |
| 后续每 4 列 | 一个教练的课程、场馆、场地号、学员 |

示例：

| 教练区域 | 字段 |
|---|---|

| 林铭教练 | 课程、场馆、场地号、学员 |

| 岳克舟教练 | 课程、场馆、场地号、学员 |

兼容场地列写法：

| 飞书表写法 | 系统识别 |

### 6.2 时间合并

飞书表以 30 分钟为一格。

同一节课跨多个 30 分钟格时，系统必须合并为一节排课。

示例：

| 飞书表表现 | 系统排课 |
|---|---|
| 晓哲教练 12:00-12:30、12:30-13:00、13:00-13:30 为同一连续课程 | 创建 1 节 12:00-13:30、1.5 小时排课 |

不能按每个 30 分钟单独创建排课。

### 6.3 课程类型

飞书课程文本需要映射到系统课程类型：

| 飞书文本示例 | 系统口径 |
|---|---|
| 成人私教【正式】 | 私教课 / 正式课 |
| 青少年私教【正式】 | 私教课 / 正式课 |
| 成人私教【体验】 | 体验课 |
| 青少年私教【体验】 | 体验课 |

如果课程类型无法识别，不自动创建，通知运营群处理。

### 6.4 学员名称

支持基础别名匹配：

1. 忽略大小写。
2. 忽略空格。
3. 忽略英文点号。
4. 忽略中文/英文括号内的课次备注。

示例：

| 飞书表 | 系统可能名称 | 处理 |
|---|---|---|
| wjing | W.Jing | 可识别为同一学员 |
| 李先生（2） | 李先生 | 可识别为李先生，括号数字作为课次备注 |
| 将来 | 赵新阳 | 按已确认别名匹配 |
| 锤锤 | 是锤锤呀 | 按已确认别名匹配 |
| 李俊泽 | 李俊泽（L¡） | 按已确认别名匹配 |
| william弟弟 / willliam弟弟 | william | 使用 william 的学员档案和课包 |
| 晨曦 | 曦曦🐳 | 按已确认别名匹配 |

正式课匹配不到学员时，不自动创建学员，不自动创建排课，通知运营群。

体验课匹配不到学员时，不走临时学员流程，必须走第 6.7 节正式体验课链路。

### 6.5 括号数字

括号数字表示课包使用第几节课。

示例：

| 飞书表 | 含义 |
|---|---|
| 李先生（2） | 李先生的课包使用第 2 节 |
| 晨曦、朋友（2） | 曦曦🐳 1v2 课程，使用曦曦🐳课包第 2 节 |
| 德德（使用小林课包 2） | 用小林课包第 2 节排课，备注写明德德使用小林课包 2 |

系统扣课以系统课包余额为准，括号数字只做辅助校验。

如果飞书课次和系统判断明显不一致，系统不强行修正课包，通知运营群。

### 6.6 1v2 学员规则

以飞书表学员字段为准拆分多个名字，但泛称“朋友”不是稳定学员身份，不能误匹配到系统里名称包含“朋友”的其他人。

| 场景 | 系统处理 |
|---|---|
| 只有主学员有对应课包 | 只创建主学员排课，消耗主学员课包 |
| 飞书写了两个明确学员名，且两个学员都有同类型课包 | 创建包含两个学员的排课，各自消耗对应课包 |
| 飞书写“晨曦、朋友（2）” | 只创建曦曦🐳排课，消耗曦曦🐳课包 |
| 飞书写“德德（使用小林课包 2）” | 创建德德排课，先把小林课包授权给德德使用，再扣小林课包，并备注“德德使用小林课包 2” |
| 飞书写“王老板”亲子小班 | 只使用王老板一个档案，1-3 人亲子同行不单独建档 |
| 无法判断谁有课包 | 不自动创建，通知运营群 |

示例：

`晨曦、朋友（2）`：

1. 只创建曦曦🐳的排课。
2. 不把“朋友”当作独立学员搜索。
3. 不误匹配到系统里其他名称含“朋友”的学员。

### 6.7 体验课正式链路

体验课不能创建“临时学员”，也不能绕过课包和财务流程。

飞书表识别为体验课时，必须按系统现有正式流程处理：

1. 先查历史学员。
2. 历史学员不存在，再查线索池。
3. 线索池存在时，先把线索标记为课程转化，成交类型为 `课程`。
4. 创建或关联正式学员档案。
5. 购买体验课课包。
6. 用体验课课包创建排课并核销。
7. 收入、待入账、已入账、课包核销、学员历史、教练课时统计、经营分析同步更新。

体验课价格和支付方式：

| 飞书课程 | 体验课包 | 金额 | 支付方式 |
|---|---|---:|---|
| 成人私教【体验】 | 成人1v1私教体验课 | 239 | 大众点评券码 |
| 青少年私教【体验】 | 青少年1v1私教体验课 | 199 | 大众点评券码 |

飞书表不要求填写具体大众点评券码编号，系统只记录支付方式为 `大众点评券码`。

体验课自动处理规则：

| 场景 | 系统处理 |
|---|---|
| 历史学员已存在，且可唯一匹配 | 直接购买体验课包，再创建并核销体验课排课 |
| 历史学员不存在，线索池可唯一匹配 | 标记线索课程转化，创建学员档案，购买体验课包，创建并核销体验课排课 |
| 历史学员和线索池都不存在 | 不自动创建，发群通知人工补线索或确认建档 |
| 同名学员或同名线索存在多条 | 不自动处理，发群通知人工选择 |
| 表格只有昵称，无法判断成人/青少年 | 不自动购买课包，发群通知人工确认 |
| 已有未核销体验课包 | 优先使用已有可用体验课包，不重复购买 |
| 已有体验课包类型和飞书课程类型不一致 | 不自动处理，发群通知人工确认 |
| 体验课包商品缺失或价格不是 239/199 | 不自动处理，发群通知检查产品配置 |
| 体验课时长不是 1 小时 | 不自动购买和核销，发群通知运营确认 |
| 已有同时间、同教练、同学员排课 | 不重复创建，发群通知疑似重复 |

专项课 / 初阶训练课自动处理规则：

| 场景 | 系统处理 |
|---|---|
| 初阶训练课、零基础训练营、专项课已明确学员，且已有对应可扣课包 | 直接创建排课并核销对应课包 |
| 初阶专项课没有可扣课包，但系统存在匹配的 199 元单次专项课包商品 | 先给每个缺课包学员购买专项课包，再创建排课并核销 |
| 发接发与实战练习没有可扣课包，但系统存在匹配的 260 元单次专项课包商品 | 先给每个缺课包学员购买专项课包，再创建排课并核销 |
| 多人专项课只有部分学员有课包 | 不只排部分学员；能补包则补齐后一起排，不能补齐则通知运营 |
| 私教正式课没有课包 | 不自动购买课包，必须已有课包、已确认单次付费、已确认赠送，或通知运营 |

体验课链路必须复用现有系统能力：

1. 线索转学员使用现有线索转化逻辑。
2. 购买体验课包使用现有购买课包逻辑。
3. 排课核销使用现有排课保存和权益扣减逻辑。
4. 财务展示使用现有财务读模型，不单独写一套体验课财务口径。

体验课财务口径：

1. 购买体验课包时，形成收入流水。
2. 体验课排课核销时，形成已入账流水。
3. 若购买和上课在同一轮同步中完成，总收入、待入账、已入账都必须按现有财务口径刷新。
4. 不允许只创建排课、不创建购买记录。
5. 不允许把体验课作为 `direct` 直接收款排课绕过课包。

体验课购买日期：

1. 默认使用排课日期作为购买日期和业务归属日期。
2. 如果系统现有购买流程强制使用当天，则记录同步来源和排课日期，财务仍按系统现有口径展示。
3. 不为飞书同步单独新增一套财务日期口径。

## 7. 同步规则

### 7.0 上线基线和存量排课处理

自动同步以当前飞书排课表文档为同步范围，不再只看未来课程。

每次同步按以下规则处理：

| 范围 | 处理规则 |
|---|---|
| 飞书文档内课程 | 全部纳入差异对比 |
| 已经开始或已经结束的历史课程 | 可自动绑定完全匹配的系统排课；不自动补建、不自动修改；异常发群通知 |
| 还没开始的未来课程 | 可按新增/修改规则自动处理 |
| 飞书文档删除已绑定课程 | 生成删除确认链接，运营确认后再取消系统排课 |

上线第一轮和重大规则变更分两步：

1. 先执行 dry-run，只读飞书表和系统排课，输出差异报告，不写数据。
2. 运营确认差异报告后，再开启正式同步。

正式同步对文档内课程的处理：

| 场景 | 系统处理 |
|---|---|
| 飞书表有课，系统已有完全匹配排课 | 绑定同步关系，不重复创建 |
| 飞书表有未来课，系统没有匹配排课 | 按新增规则自动创建 |
| 飞书表有历史课，系统没有匹配排课 | 不自动补建，发群通知人工确认 |
| 飞书表有课，系统有疑似匹配但不完全一致 | 不自动绑定、不自动创建，发群通知人工确认 |
| 系统有手动排课，飞书表没有同步关系 | 不处理，继续保持手动排课 |

完全匹配至少要求：

1. 日期一致。
2. 开始和结束时间一致。
3. 教练一致。
4. 学员一致。
5. 课程类型一致。
6. 场馆和场地一致。

删除判断从第一轮正式同步完成后的快照开始生效。

也就是说：

1. 飞书表在上线前已经删除过的课，系统不会自动知道，也不会自动取消。
2. 只有已建立同步关系的课程，从飞书表删除后才会生成删除确认任务。
3. 历史课程涉及消课、收入和教练课时统计，不做自动补建或自动修改，必须人工确认后专项处理。

### 7.1 新增

飞书表出现新的可识别课程：

1. 系统生成稳定同步 ID。
2. 检查是否已存在同一同步 ID 的排课。
3. 检查是否疑似重复：同日期、同时间、同教练、同学员、同场地。
4. 正式课无重复且信息完整时，调用系统排课创建逻辑。
5. 体验课无重复且满足第 6.7 节前置条件时，按“学员档案 -> 购买体验课包 -> 排课核销”完整链路处理。
6. 创建成功后记录同步关系。
7. 通知运营群。

### 7.2 修改

飞书表中已同步课程发生变化：

1. 找到对应系统排课。
2. 判断变更字段：时间、教练、课程类型、场馆、场地、学员。
3. 如果系统排课仍可编辑，调用系统排课更新逻辑。
4. 如果已有课后反馈或权益风险导致不可直接改，通知运营群。
5. 如果修改会导致课程性质变化，不自动处理，通知运营群人工确认。
6. 修改成功后通知运营群。

课程性质变化包括：

1. 正式课改体验课。
2. 体验课改正式课。
3. 成人体验课改青少年体验课。
4. 1v1 改 1v2，或 1v2 改 1v1。
5. 需要改动已购买课包、已核销权益或财务流水的变化。

### 7.3 删除

飞书表中已同步课程消失：

1. 系统不直接删除。
2. 创建一条待确认任务。
3. 运营群发送确认链接。
4. 运营在手机打开链接，点击确认。
5. 系统执行取消排课。
6. 取消成功后通知运营群。

删除第一版默认是“取消排课”，不是物理删除。

体验课删除也必须走人工确认流程：

1. 飞书删除体验课时，不自动取消排课。
2. 先发群通知和手机确认链接。
3. 运营确认后，系统按现有取消排课逻辑处理。
4. 如涉及体验课购买记录作废、财务收入回滚、已入账冲销，不自动处理，发群提示人工核对。
5. 已上课、有课后反馈、已核销且存在财务风险的体验课，不允许自动取消。

## 8. 系统手动排课不受影响

系统排课需要标记来源：

| 来源 | 说明 | 飞书同步是否管理 |
|---|---|---|
| `feishu-sheet` | 飞书表同步创建或绑定的排课 | 是 |
| `manual` | 管理后台手动创建的排课 | 否 |

飞书同步只处理 `feishu-sheet` 来源的排课。

如果系统里手动新增了一节课，飞书表同步不能因为表格里没有它就取消或删除它。

## 9. 待确认任务

删除确认链接用于手机操作。

| 项 | 规则 |
|---|---|
| 确认方式 | 运营群消息里的系统链接 |
| 页面形式 | 极简确认页，不需要进入完整后台 |
| 默认动作 | 取消排课 |
| 有效期 | 48 小时 |
| 过期后 | 不再执行，重新通知或等待下次同步 |

确认页至少展示：

1. 日期和时间。
2. 教练。
3. 学员。
4. 课程类型。
5. 场馆和场地。
6. 风险提示。
7. 确认取消按钮。
8. 忽略本次变更按钮。

## 10. 群通知

统一使用现有运营群机器人 webhook。

### 10.1 新增成功

通知内容：

1. 已同步新增排课。
2. 日期、时间、教练、学员、课程类型、场地。
3. 系统排课 ID。

### 10.2 修改成功

通知内容：

1. 已同步修改排课。
2. 修改前后差异。
3. 系统排课 ID。

### 10.3 删除待确认

通知内容：

1. 飞书表检测到删除。
2. 待处理课程信息。
3. 确认链接。
4. 忽略链接。

### 10.4 同步失败

通知内容：

1. 失败原因。
2. 飞书 sheet 名称和单元格位置。
3. 建议运营如何修正。

## 11. 数据记录

需要保存同步关系和快照。

### 11.1 同步关系

记录字段：

| 字段 | 说明 |
|---|---|
| `id` | 同步记录 ID |
| `source` | 固定为 `feishu-sheet` |
| `spreadsheetToken` | 飞书表 token |
| `sheetId` | sheet ID |
| `sheetTitle` | sheet 名称 |
| `sourceKey` | 稳定同步键 |
| `scheduleId` | 系统排课 ID |
| `lastFingerprint` | 上次内容指纹 |
| `status` | active / pending_delete / ignored / error |
| `lastSyncedAt` | 最近同步时间 |

### 11.2 快照

每次同步后保存当前飞书表识别出的课程列表，用于下次判断新增、修改、删除。

## 12. 风险保护

必须遵守：

1. 不直接写数据库创建排课。
2. 新增、修改、取消必须复用系统排课接口或同等业务逻辑。
3. 找不到学员、教练、课包时不自动处理。
4. 疑似重复排课不自动创建。
5. 飞书删除不直接删除系统排课。
6. 管理后台手动排课不受飞书同步影响。
7. 所有密钥只放环境变量。
8. 体验课必须走正式学员、正式购买、正式核销链路。
9. 体验课自动链路必须校验财务总览、收入流水、已入账流水、学员历史和教练课时统计是否同步变化。
10. 无历史学员、无线索或匹配不唯一时，必须停止自动写入并发群通知。
11. 找不到场馆、场地或教练时，不自动创建基础资料，必须发群通知。
12. 体验课删除、体验课课程性质变化、涉及财务回滚的变化，必须走人工确认。
13. 历史课程可自动绑定完全匹配排课，但不自动补建、不自动修改。
14. 删除判断只能对已建立同步关系的飞书课程生效。

## 13. 实施步骤

### 第一步：只读解析

1. 读取飞书表。
2. 解析每个 sheet。
3. 输出识别出的课程列表。
4. 不写系统排课。

### 第二步：同步关系和快照

1. 建同步记录。
2. 建快照记录。
3. 识别新增、修改、删除。
4. 只输出 dry-run 结果。
5. 输出上线基线差异报告。
6. 运营确认后才允许开启正式同步。

### 第三步：自动新增

1. 只处理信息完整、无冲突的新课程。
2. 正式课调用系统排课创建逻辑。
3. 体验课先复用线索转学员和购买课包逻辑，再调用系统排课创建和权益核销逻辑。
4. 成功后记录同步关系。
5. 失败发群通知。

### 第四步：自动修改

1. 只修改已绑定的飞书同步排课。
2. 可安全修改时自动修改。
3. 不可安全修改时发群通知。

### 第五步：删除确认

1. 飞书删行后生成待确认任务。
2. 群里发确认链接。
3. 手机确认后执行取消排课。
4. 群里通知处理结果。

### 第六步：GitHub Actions

1. 增加 GitHub 定时任务。
2. 北京时间 08:00、18:00 各触发一次。
3. 调用系统同步接口。

## 15. 暂不做

第一版暂不做：

1. 群里直接回复“同意删除”。
2. 无历史学员且无线索时自动创建学员档案。
3. 自动创建课包产品或售卖课包。
4. 自动物理删除系统排课。
5. 写回飞书表状态列。
6. 多校区多表统一管理。

以上能力等第一版稳定后再评估。
