## 1. 背景

当前 FlowTennis 的会员、订场、财务、排课、场地占用数据有一部分在第三方系统中产生。

第三方系统不提供官方开放接口，但后台页面自身存在可读取的内部接口。FlowTennis 需要通过这些数据完成：

1. 会员余额和充值记录补齐。
2. 订场用户消费历史补齐。
3. 会员余额订场的已入账确认。
4. 散客订场、退款、券码订场的财务补齐。
5. 第三方锁场与 FlowTennis 排课、场地使用的兼容。

本需求不采用一次性全量导入。所有历史数据必须按月份分批处理，先做小范围试点，再逐月回溯。

## 2. 总目标

建立一套可追溯、可预检、可分批、可回滚的第三方数据导入机制，并在稳定后建设第三方同步中心，支持后续每日自动同步和运营确认。

核心原则：

1. 不清空 FlowTennis 旧数据。
2. 不直接覆盖财务事实。
3. 不把锁场直接等同于订场。
4. 不把会员余额扣款重复算成现金收入。
5. 不让排课占场和锁场占场重复计算。
6. 每条导入数据必须保留第三方原始记录、来源、批次号、去重键和处理状态。

## 4. 旧数据处理原则

旧数据不清除，统一兼容。

| 旧数据类型 | 处理方式 |
|---|---|
| FlowTennis 已有订场用户 | 保留，通过手机号和第三方客户匹配 |
| FlowTennis 已有会员账户 | 保留，通过手机号、会员账户、余额差异做匹配 |
| FlowTennis 已有充值记录 | 保留，用第三方订单号和金额日期做去重 |
| FlowTennis 已有排课 | 保留，用日期、场地、时间段和第三方锁场匹配 |
| FlowTennis 已有财务流水 | 保留，导入前做差异预检，不直接覆盖 |
| 不兼容数据 | 进入异常池，不写入财务和余额 |

旧数据和第三方数据的关系分为：

| 关系 | 说明 | 处理 |
|---|---|---|
| 完全匹配 | 手机号、日期、金额、订单或时段能对上 | 标记已匹配，不重复导入 |
| 部分匹配 | 手机号相同，但金额、时间或备注不同 | 进入待确认 |
| 第三方新增 | FlowTennis 没有对应记录 | 可按规则导入 |
| FlowTennis 独有 | 第三方没有对应记录 | 保留，不删除 |

## 5. 第一批数据处理流程

### 5.1 拉取数据

第一批拉取以下数据：

| 数据 | 第三方来源 | 用途 |
|---|---|---|
| 会员列表 | 会员管理接口 | 会员账户、余额、有效期 |
| 会员充值流水 | 充值流水/财务充值接口 | 会员储值收入 |
| 订场订单 | 订场订单接口 | 散客订场、会员订场 |
| 支付明细 | 支付明细接口 | 判断支付方式和实收 |
| 退款明细 | 退款接口 | 冲减收入、余额和已入账 |
| 锁场报表 | 锁场报表接口 | 排课占场、内部占用、代订场 |

### 5.1.1 第三方接口调用注意事项

场小二后台页面使用的是内部接口，不是公开开放 API。后续抓取数据时必须记录以下踩坑经验：

| 场景 | 正确做法 | 错误做法 / 风险 |
|---|---|---|
| 登录后调用后台接口 | 请求头使用 `token`、`Token` 或 `TOKEN` 传登录返回的 token | 不要使用 `Authorization: Bearer <token>`，该写法会被第三方判定为未登录 |
| 会员列表接口 | `POST /merchantmanage/recharge/userList` | 不要只看页面数量，必须保存接口原始返回 |
| 会员流水接口 | `POST /merchantmanage/recharge/userRechargePage`，按 `userId` 分页抓取 | 只导会员名单无法得到充值次数、充值金额、赠送金额、消耗和余额变化 |
| 会员流水导出 | 第三方导出有并发限制，需要串行导出并检查文件内容 | 如果并发导出，会返回 JSON 错误：`您商户已经有账号正在导出文件，请稍后操作`，文件后缀可能仍是 `.xls` |
| 导出文件校验 | 每个 `.xls` 必须先判断是真 Excel 还是 JSON 错误，再进入解析 | 不能按扩展名直接当 Excel 读，否则会混入失败文件 |

会员流水字段以第三方“流水明细”为准，核心字段包括：

| 字段 | 用途 |
|---|---|
| 订单号 | 幂等去重、绑定订场/充值来源 |
| 时间 | 充值或消耗发生时间 |
| 业务 | 判断会员、订场、其他业务 |
| 交易类型 | 区分收入、支出、导入开卡、扣费、锁场、会员扣费 |
| 金额变动 | 拆分总额、本金变动、赠送变动 |
| 商品说明 | 解析订场日期、场地、时段 |
| 备注 | 辅助判断人工扣费、陪打、导入开卡等 |
| 余额 | 作为每笔流水后的余额校验 |

### 5.2 预检报告

| 报告项 | 说明 |

| 可自动导入 | 系统高置信可处理的数据 |
| 待确认 | 需要运营判断的数据 |

| 场地占用差异 | 排课、锁场、内部占用是否重复 |

## 6. 数据分类规则

### 6.1 会员充值

| 条件 | 处理 |
|---|---|
| 有手机号、有订单号、有充值金额、状态有效 | 自动导入会员充值 |
| 有赠送金额 | 写入赠送金额，但不计入现金收入 |
| 订单退款或作废 | 生成退款/作废冲减 |
| 找不到手机号 | 进入异常池 |

财务口径：

1. 充值本金计入会员储值收入。
2. 赠送金额不计入总收入。
3. 充值后形成待履约收入。

### 6.2 小程序用户自助订场

| 条件 | 处理 |
|---|---|
| 微信支付 | 散客订场收入 |
| 余额支付 | 会员余额消耗 |
| 混合支付 | 拆成现金收款和余额消耗两条流水 |
| 已取消、已退款 | 不计有效订场，按退款规则处理 |

### 6.3 会员余额订场

会员余额订场必须同时影响：

1. 会员储值余额减少。
2. 已入账收入增加。
3. 待履约收入减少。
4. 总收入不变。

禁止把会员余额扣款再次计入现金收入。

### 6.4 锁场报表

锁场必须先分类，不能直接当作订场订单。

| 锁场场景 | 处理方式 | 财务影响 | 场地占用影响 |
|---|---|---|---|
| 排课锁场 | 匹配 FlowTennis 排课，绑定为课程占场 | 默认无新增场地费 | 算占用，但不能重复 |
| 内部使用 | 记内部占用 | 无收入 | 算内部占用 |
| 运营替会员余额订场 | 匹配会员并扣余额 | 已入账增加，待履约减少，总收入不变 | 算会员订场占用 |
| 运营替散客微信转账订场 | 记散客订场，支付方式为微信转账/人工收款 | 计场地收入 | 算散客订场占用 |
| 运营替散客大众点评券码订场 | 记散客订场，支付方式为大众点评券码 | 按平台结算金额计收入 | 算散客订场占用 |
| 备注不清楚 | 进入待确认 | 不入账 | 可暂存占用候选 |

排课锁场特别规则：

1. 第三方场地名称需要先标准化：
   - `室内1号` = `1号场`
   - `室内2号` = `2号场`
   - `室内3号` = `3号场`
   - `室内4号` = `4号场`
2. 如果 FlowTennis 已有同日期、同场地、时间重叠的排课，第三方锁场只作为外部占用证据。
3. 第三方锁场按半小时一格展开，FlowTennis 排课可按 1 小时、1.5 小时、2 小时等区间匹配；只要日期、标准化场地和时间区间有重叠，即进入排课匹配候选。
4. 备注中包含 `私教课`、`上课`、学员名或教练名时，如果第三方备注中的任意教练/学员名能和 FlowTennis 排课中的教练/学员名对上，且时间区间重叠，可判定为高置信排课匹配。
5. 只有时间和场地重叠，但姓名无法确认时，进入低置信匹配，需人工确认。
6. 教练代订场不能自动归为排课。例如备注为 `晓哲 定场`、`某教练 定场` 时，即使出现教练名，也应进入人工确认；这类通常是内部教练 8 折订场，通过微信转账给运营，由运营代订场。
7. 不新增订场消费。
8. 不新增场地收入。
9. 除非排课明确标注单独支付场地费，否则私教课排课不单独计算场地费。
10. 私教课课时费默认已包含场地使用，不再拆出场地收入。

锁场备注初步分类规则：

| 备注特征 | 初步分类 | 自动处理 |
|---|---|---|
| `私教课`、`上课`、备注中教练/学员名能匹配排课 | 排课占场 | 高置信匹配后可自动绑定排课 |
| `清洗场地`、`打扫`、`维修` | 内部占用 | 可自动标记内部占用 |
| `免费`、`小鹿训练`、内部训练 | 内部占用候选 | 可预判为内部占用，必要时人工确认 |
| `定场`、`订场`，且备注中出现教练名 | 教练/运营代订场 | 必须人工确认支付方式和金额 |
| `畅打`、`4人畅打` | 活动/畅打占场 | 必须人工确认是否已有活动收款 |
| `陪打` | 订场陪打或课程候选 | 必须人工确认 |
| `大众点评`、`券`、`团购`、`核销` | 第三方券码订场 | 必须人工确认券码和结算金额 |

### 6.5 退款

| 条件 | 处理 |
|---|---|
| 有退款单号和原订单号 | 自动匹配原订单 |
| 原订单是现金订场 | 冲减场地收入 |
| 原订单是会员余额订场 | 恢复会员余额，冲减已入账 |
| 原订单是会员充值 | 冲减会员储值收入和待履约 |
| 找不到原订单 | 进入异常池 |

## 7. 去重规则

每条第三方记录都必须生成去重键。

| 数据类型 | 去重键 |
|---|---|
| 会员充值 | 第三方充值订单号 |
| 订场订单 | 第三方订单号 |
| 支付明细 | 第三方支付流水号 |
| 退款明细 | 第三方退款单号 |
| 锁场记录 | 来源 + 日期 + 场馆 + 场地 + 开始时间 + 结束时间 + 客户手机号 + 锁场类型 |
| 排课锁场匹配 | FlowTennis 排课 ID + 第三方锁场去重键 |

重复记录不得再次写入财务、会员余额或订场历史。

## 7.1 数据落地模型

第三方导入不得用临时脚本直接写业务表。必须先经过以下数据区：

| 数据区 | 用途 |
|---|---|
| 第三方原始数据池 | 原样保存第三方返回数据，不因业务处理删除 |
| 导入批次表 | 记录每次导入范围、状态、报告、操作人 |
| 待确认/异常池 | 存放运营需要处理的数据 |
| 业务写入结果表 | 记录本批次写入了哪些 FlowTennis 业务记录 |

每条原始记录必须至少包含：

| 字段 | 说明 |
|---|---|
| `sourceSystem` | 第三方系统标识 |
| `sourceType` | 会员、充值、订场、支付、退款、锁场 |
| `sourceId` | 第三方订单号、流水号或生成去重键 |
| `rawPayload` | 第三方原始 JSON |
| `batchId` | 导入批次 |
| `syncStatus` | 已拉取、已匹配、待确认、已写入、异常 |
| `createdAt` | 拉取时间 |

### 7.2 固定写入顺序

写入顺序必须固定：

1. 保存第三方原始数据。
2. 生成预检报告。
3. 做客户和手机号匹配。
4. 做会员余额和充值匹配。
5. 做订场订单匹配。
6. 做锁场和排课匹配。
7. 做财务影响预计算。
8. 人工确认异常。
9. 正式写入业务表。
10. 生成写入后验收报告。

禁止先写财务，再处理会员余额、退款或锁场归类。

### 7.3 回滚机制

回滚必须按 `batchId` 执行。

| 数据 | 回滚方式 |
|---|---|
| 第三方原始数据 | 不删除，保留原始证据 |
| 业务导入数据 | 按 `batchId` 作废或撤销绑定 |
| 财务流水 | 不物理删除，用负向流水冲正 |
| 会员余额 | 生成反向调整或按批次恢复 |
| 场地占用 | 按批次撤销绑定 |
| 待确认记录 | 恢复为待确认或已暂停 |

核心原则：

1. 财务和余额不得直接删除。
2. 已完成批次回滚后必须生成回滚报告。
3. 回滚后必须重新核对会员、订场、财务、排课、场地占用。

### 7.4 第三方数据变化处理

第三方数据导入后仍可能变化，例如补退款、补锁场、改备注。

处理规则：

1. 历史月份导入后仍允许补充修正。
2. 每次自动同步必须回看最近 3 至 7 天。
3. 已导入记录如果第三方发生变化，进入“变更待确认”。
4. 不得静默覆盖已入账数据。
5. 涉及财务变化时，必须生成独立冲正或调整流水。

## 8. 第三方同步中心

### 8.1 页面目标

第三方同步中心用于运营处理自动同步后的不确定数据，不依赖 Codex 人工参与。

### 8.2 页面入口

建议入口：

> 管理后台 / 场地运营 / 第三方同步中心

### 8.3 页面结构

| 区域 | 内容 |
|---|---|
| 同步概览 | 本次同步时间、范围、数据量、自动处理量、待确认量、异常量 |
| 批次列表 | 每个导入批次的状态和报告 |
| 待确认列表 | 锁场、疑似重复、支付方式不明、客户不明 |
| 异常列表 | 缺字段、冲突、无法匹配、金额不一致 |
| 已处理记录 | 可追溯查看处理结果 |

### 8.4 运营确认动作

运营对待确认记录可以选择：

1. 绑定到某节排课。
2. 标记为内部使用。
3. 标记为会员订场并选择会员。
4. 标记为散客订场，支付方式为微信转账。
5. 标记为散客订场，支付方式为大众点评券码。
6. 标记为忽略，不导入。
7. 标记为待老板确认。
8. 补充备注或更正金额。

### 8.4.1 运营确认字段

待确认页面必须展示和记录：

| 字段 | 用途 |
|---|---|
| 第三方原始备注 | 运营判断业务来源 |
| 系统推荐分类 | 系统预判类型 |
| 置信度 | 高、中、低 |
| 运营最终选择 | 最终业务归类 |
| 支付方式 | 微信转账、大众点评券码、会员余额、内部等 |
| 金额 | 运营确认金额 |
| 绑定对象 | 会员、订场用户、排课或内部占用 |
| 确认人 | 审计 |
| 确认时间 | 审计 |
| 确认备注 | 复盘依据 |

### 8.5 自动化边界

以下数据可以自动处理：

| 数据 | 自动条件 |
|---|---|
| 会员充值 | 有订单号、手机号、金额、状态有效 |
| 小程序自助订场 | 有订单号、支付方式、金额、状态有效 |
| 退款 | 有退款单号、原订单号 |
| 会员余额订场 | 有余额支付标识并能匹配会员 |
| 排课锁场 | 场地标准化后一致，时间区间重叠，且备注中的任意教练/学员名能匹配 FlowTennis 排课 |

以下数据必须人工确认：

| 数据 | 原因 |
|---|---|
| 运营个人收款锁场 | 第三方系统不体现真实支付来源 |
| 教练代订场 | 例如 `晓哲 定场`，通常是教练 8 折微信转账给运营，第三方系统不体现真实支付来源 |
| 大众点评券码锁场 | 需要确认券码和结算金额 |
| 备注不清楚的锁场 | 无法判断业务类型 |
| 客户手机号缺失 | 无法可靠归属 |
| 金额与财务流水不一致 | 可能影响财务 |
| 场地时间冲突 | 可能重复占用 |

## 9. 批次状态

每个导入批次必须有状态。

| 状态 | 含义 |
|---|---|
| 已拉取 | 已从第三方拿到原始数据 |
| 已预检 | 已生成预检报告 |
| 待确认 | 存在需要运营处理的数据 |
| 可写入 | 已满足写入条件 |
| 写入中 | 正在写入 FlowTennis |
| 已完成 | 写入和验收完成 |
| 已暂停 | 发现问题，暂停处理 |
| 已回滚 | 已按批次回滚 |

## 9.1 权限和责任人

| 动作 | 允许角色 |
|---|---|
| 拉取第三方数据 | 系统自动、管理员 |
| 查看预检报告 | 管理员、运营、财务 |
| 确认普通异常 | 运营 |
| 确认支付方式和券码金额 | 运营、财务 |
| 确认财务异常 | 财务、老板 |
| 正式写入 | 管理员 |
| 回滚批次 | 老板、超级管理员 |
| 开启自动同步 | 老板、超级管理员 |

## 9.2 上线模式

第三方同步中心必须分三档上线：

| 模式 | 说明 |
|---|---|
| 只读模式 | 只拉数据和报告，不写入业务 |
| 半自动模式 | 高确定性自动写入，异常人工确认 |
| 自动模式 | 历史规则稳定后，低风险数据自动写入 |

上线顺序必须从只读模式开始，不得直接开启自动模式。

## 10. 验收口径

每个批次必须验收以下内容：

| 验收项 | 要求 |
|---|---|
| 会员余额 | FlowTennis 会员余额和第三方余额差异可解释 |
| 充值收入 | 会员储值收入等于有效充值本金 |
| 赠送金额 | 赠送不进入现金收入 |
| 会员订场 | 已入账增加，待履约减少，总收入不变 |
| 散客订场 | 进入场地收入 |
| 大众点评券码 | 按平台结算或人工确认金额计入 |
| 退款 | 有独立负向流水，不直接改原流水 |
| 排课占场 | 与排课匹配后不重复占用 |
| 内部使用 | 不计收入，只计内部占用 |
| 场地利用率 | 同一场地同一时段只算一次 |
| 异常池 | 未确认数据不得进入财务和余额 |

金额通过标准：

| 验收项 | 通过标准 |
|---|---|
| 充值本金 | 第三方 = FlowTennis，允许误差 0.01 元 |
| 赠送金额 | 只进赠送，不进收入 |
| 会员余额 | 每个会员差异为 0，或有人工确认原因 |
| 现金收入 | 微信、转账、券码收入必须能追溯来源 |
| 已入账 | 会员余额订场只增加已入账，不增加总收入 |
| 退款 | 必须能找到原订单；找不到不自动入账 |
| 场地占用 | 同一日期、场地、时段不得重复计算 |

## 11. 第一批试点验收标准

2026-07-01 至 2026-07-15 批次完成后，必须输出：

1. 第三方原始数据拉取报告。
2. 自动分类报告。
3. 待确认数据处理报告。
4. 写入前后会员余额对比。
5. 写入前后财务总览对比。

7. 写入前后场地占用对比。

## 12. 风险与处理

| 风险 | 处理 |
|---|---|
| 第三方接口改版 | 保留接口健康检查和失败告警 |
| 锁场备注不规范 | 进入待确认，不自动入账 |
| 运营个人收款不可见 | 必须由运营确认支付方式和金额 |
| 大众点评券码结算金额不明 | 先按人工确认金额，不自动推断 |
| 历史数据和现有数据重复 | 依赖去重键和预检报告 |
| 会员余额不一致 | 暂停写入，先出差异清单 |
| 财务口径重复计算 | 写入前后跑财务守恒校验 |
| 排课和锁场重复占用 | 匹配排课后只保留一个占用事实 |

## 13. 非目标

本阶段不做：

1. 一次性全量导入。
2. 直接清空旧数据。
3. 未经预检直接写生产。
4. 把所有锁场自动当订场收入。
5. 把会员余额扣款重复算入总收入。
6. 让运营通过 Codex 处理每日数据。
