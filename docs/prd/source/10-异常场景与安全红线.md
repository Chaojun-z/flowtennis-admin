# 异常场景与安全红线

> 版本：2026-07-02
> 状态：PRD 内置安全红线正本
> 定位：给接手 AI、开发、测试和运营使用的事故预防清单。本文回答“什么情况必须停、不能怎么做、正确处理证据是什么”。

## 0. 使用规则

1. 本文是 PRD 正本的一部分，不再依赖 PRD 外部散文档。
2. 任何需求只要命中本文 P0 / P1 红线，必须先按本文检查，再实施或验收。
3. 没有完成本文要求的证据，不得回复“已完成”“已上线”“已生效”“100%正确”。
4. 不确定是否命中红线时，按命中处理。
5. 自动化测试没有覆盖的项，必须写人工验收证据；不能把人工未核对的项说成已通过。

## 1. 风险等级

| 等级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 可能误写生产、影响财务、破坏权益余额、导致跨校区 / 跨教练越权、造成线上不可恢复数据错误 | 先停；确认范围；准备回滚 / 快照 / dry-run；完成证据后才能继续 |
| P1 | 可能导致核心页面口径不一致、关键字段错显、导出错误、约球费用错误、教练端错看数据 | 必须补测试或人工验收；不得只看单页面 |
| P2 | UI、文案、低风险字段展示、非核心筛选体验问题 | 按影响页面验收；如涉及统一字段仍按 P1 |

## 2. 生产数据红线

### 2.1 触发条件

只要任务包含以下任一动作，即命中生产数据红线：

1. 生产导入、线上修数、补账、恢复数据、批量删除、批量替换、批量合并。
2. 写入或修改 `purchases`、`entitlements`、`entitlement_ledger`、`courts`、`membership_orders`、`membership_accounts`、`membership_benefit_ledger`、`financial_ledger`。
3. 执行 `scripts/repair-*`、`scripts/cleanup-*`、`scripts/finalize-*`、`scripts/archive-*` 或任何会写生产的脚本。
4. 修改生产环境变量、启动逻辑、bootstrap / repair 类自动写入。

### 2.2 禁止动作

1. 禁止只相信本地 `.env` 判断生产目标。
2. 禁止把历史旧实例 `flowtennis` 作为生产导入、线上核对或生产修数目标。
3. 禁止只查数据库就宣布线上生效。
4. 禁止在没有 dry-run / 快照 / 回滚依据时执行批量写入。
5. 禁止把修数脚本和普通功能开发混在同一个交付里。

### 2.3 必须证据

生产写入前必须记录：

| 证据 | 要求 |
---|---|
| 线上读取实例 | 请求 `https://www.flowtennis.cn/api/diag`，确认线上真实 `TS_ENDPOINT` 和 `TS_INSTANCE` |
| 本地写入实例 | 输出本地即将写入的 `TS_ENDPOINT` 和 `TS_INSTANCE` |
| 实例一致性 | 本地写入目标必须和线上读取目标完全一致 |
| dry-run | 批量写入前必须有 dry-run 或待写入清单 |
| 回滚依据 | 有快照、批次号、操作日志或恢复方案 |

生产写入后必须核对三段链路：

| 链路 | 必须核对 |
|---|---|
| 写入表 | 目标表里数据存在、数量正确、金额正确、状态正确 |
| 页面接口 | 线上 `/api/page-data/...` 或对应线上 API 已返回新数据 |
| 前端展示 | 用户实际看的页面字段已变化 |

## 3. 财务红线

### 3.1 触发条件

以下对象任一发生新增、修改、作废、退款、导入、回滚，都命中财务红线：

- `ft_purchases`
- `ft_entitlements`
- `ft_entitlement_ledger`
- `ft_courts.history`
- `ft_membership_orders`
- `ft_membership_accounts`
- `ft_membership_benefit_ledger`
- `ft_financial_ledger`
- 财务快照 / 财务基线

### 3.2 禁止动作

1. 禁止页面临时扫描业务表重算财务总览。
2. 禁止只更新业务表，不检查财务总览、收款流水、入账流水。
3. 禁止把会员充值直接计入已入账。
4. 禁止把课包购买直接全部计入已入账。
5. 禁止退款、作废、冲正直接改掉原流水；必须保留负向流水或作废追溯。
6. 禁止没有核对口径就升级财务基线。

### 3.3 正确口径

| 动作 | 总收入 | 待履约 | 已入账 |
|---|---|---|---|
| 课包购买 | 增加 | 增加 | 不直接增加 |
| 课包消课 | 不重复增加 | 减少 | 增加 |
| 会员充值 | 增加 | 增加 | 不直接增加 |
| 会员储值消费 / 权益消耗 | 不重复增加 | 减少 | 增加 |
| 订场现金消费 | 按有效订场收入进入 | 按口径处理 | 按履约进入 |
| 退款 / 作废 / 冲正 | 按负向或废弃流水处理 | 回退 | 回退 |

### 3.4 必须证据

1. 业务表变化证据。
2. 财务总览变化证据。
3. 收款流水变化证据。
4. 入账流水变化证据。
5. 若是生产导入，还必须有线上 API / 页面核对结果。
6. 涉及财务代码变更时，至少运行 `npm run guard:finance`；发布级变更运行 `npm run guard:release`。

当前已存在命令：

- `npm run guard:finance`
- `npm run snapshot:finance`
- `npm run finance:latest-snapshot`
- `npm run validate:finance-operation`
- `npm run verify:finance-page`

## 4. 课包、购买、权益红线

### 4.1 触发条件

1. 新增、编辑、作废购买记录。
2. 新增、编辑、作废权益账户。
3. 排课消课、取消消课、手工调整课包余额。
4. 合并课包、停售课包、修复课包余额。

### 4.2 禁止动作

1. 禁止购买成功但不生成权益。
2. 禁止消课但不写 `entitlement_ledger`。
3. 禁止页面自己计算剩余课时后当事实保存。
4. 禁止作废购买但权益仍可继续排课。
5. 禁止手工调整余额没有操作人、时间、原因和流水。
6. 禁止修改已售课包核心规则后影响历史订单含义。

### 4.3 必须证据

| 场景 | 证据 |
|---|---|
| 新增购买 | `ft_purchases` 有记录；`ft_entitlements` 自动生成；学员详情能看到权益 |
| 消课 | `ft_schedule` 状态正确；`ft_entitlement_ledger` 有负向流水；权益余额减少 |
| 取消排课 | 排课状态为已取消；已扣权益已回退；财务影响已回退或说明不涉及 |
| 作废购买 | 购买 `status=voided`；关联权益不可用；流水有作废追溯 |
| 课包合并 | 源课包有合并状态；历史购买、权益、排课仍可追溯 |

可用测试示例：

- `node tests/entitlement-rules.test.js`
- `node tests/package-merge-rules.test.js`
- `node tests/purchase-drawer-view.test.js`
- `node tests/purchases-page-entitlement-ledger-limit.test.js`

## 5. 订场、会员、场地财务红线

### 5.1 触发条件

1. 新增、导入、合并、删除订场用户。
2. 修改 `ft_courts.history`。
3. 开卡、续充、充值、作废会员订单。
4. 修改会员账户状态、余额、权益流水。
5. 约球费用同步到订场或财务。

### 5.2 禁止动作

1. 禁止合并订场用户后丢失历史消费。
2. 禁止会员充值只在会员页显示，财务页没有同步。
3. 禁止会员订单作废后账户、权益、财务不回退。
4. 禁止订场收入写入业务表但经营分析 / 财务不变化且没有解释。
5. 禁止把会员储值金额和会员消费金额重复计入累计消费。

### 5.3 必须证据

| 场景 | 证据 |
|---|---|
| 订场用户导入 / 修改 | 列表、详情、消费历史、财务、经营分析均能对上 |
| 会员开卡 / 续充 | 会员账户、会员订单、订场历史、权益流水、财务收款均存在 |
| 会员消费 | 余额减少；消费历史存在；已入账按口径变化 |
| 会员清零 / 延长 | 账户状态变化；`membership_account_events` 有事件 |
| 订场用户合并 | 源用户标记 inactive / merged；目标用户保留历史和财务 |

可用测试示例：

- `node tests/court-finance.test.js`
- `node tests/court-account-read-model-guard.test.js`
- `node tests/membership-rules.test.js`
- `node tests/membership-view.test.js`
- `node tests/membership-renewal-count.test.js`

## 6. 客户生命周期与数据口径红线

### 6.1 触发条件

1. 修改线索池、普通学员、正式学员、订场用户、会员管理。
2. 修改来源、校区、负责人、姓名、手机号、客户阶段。
3. 修改经营分析、转化与留存、顶部卡片、导出字段。

### 6.2 禁止动作

1. 禁止线索池和经营分析同一指标各算一套。
2. 禁止普通学员只从 `students` 表筛选后宣称全量普通学员。
3. 禁止正式学员由人工状态决定，而不看购买 / 权益事实。
4. 禁止姓名作为唯一客户识别依据。
5. 禁止同一手机号冲突时自动按姓名合并。
6. 禁止页面展示字段名和 05 / 06 定义冲突。

### 6.3 必须证据

1. 同一客户在线索、学员、订场、会员页面姓名、手机号、来源、校区、负责人一致。
2. 普通学员和正式学员当前视图互斥。
3. 线索池顶部指标和转化与留存同源一致。
4. 页面展示值等于统一读模型结果。

## 7. 权限、校区、教练红线

### 7.1 触发条件

1. 修改登录、账号管理、角色、校区范围、教练绑定。
2. 修改页面接口的数据裁剪。
3. 修改教练端 Web、教练小程序、教练反馈。
4. 修改约球管理权限。

### 7.2 禁止动作

1. 禁止只靠前端隐藏菜单作为权限边界。
2. 禁止校区管理员写入其他校区数据。
3. 禁止教练看到其他教练课程。
4. 禁止教练提交其他教练课程反馈。
5. 禁止教练端返回完整财务、会员、订场用户数据。

| 场景 | 证据 |

| 校区管理员 | 列表、详情、聚合、写接口均按 `campusIds` 裁剪 |
| 教练端 | 只返回本人课程、本人学员、安全权益投影 |
| 账号停用 | `status=inactive` 不能登录 |
| 约球权限 | `match_ops` 和 `match_finance` 可拆分验证 |

## 8. 约球红线

### 8.1 触发条件

1. 发布、取消、修改约球活动。
2. 报名、取消报名、转让名额。
3. 确认到场、生成 AA、确认收款、退款、结清。
4. 约球费用同步到订场或财务。

### 8.2 禁止动作

1. 禁止取消报名后仍计入有效人数。
2. 禁止到场名单和费用分摊对象不一致。
3. 禁止费用确认没有 `match_fee_splits`。
4. 禁止取消、退款、转让没有 `match_operation_logs`。
5. 禁止约球财务动作绕过 `match_finance`。

### 8.3 必须证据

1. 活动状态流转正确。
2. 报名人数等于有效报名记录。
3. 到场名单决定费用分摊。
4. 费用分摊合计等于最终费用。
5. 收款、退款、取消均有日志。

可用测试示例：

- `node tests/match-api.test.js`
- `node tests/match-page-view.test.js`
- `node tests/miniprogram-match-ops-closure.test.js`
- `npm run test:match-real`（只在需要真实链路验证时使用）

## 9. 展示字段与导出红线

### 9.1 禁止动作

1. 禁止页面展示原始 ISO 时间、内部 ID、流水 ID、导入批次、调试字段，除非是审计页。
2. 禁止列表、详情、抽屉、导出字段口径不一致。
3. 禁止同一字段在不同页面叫不同名字。
4. 禁止页面本地写死下拉字典，绕开统一字典。

### 9.2 必须证据

1. 列表字段和详情字段对齐。
2. 导出字段和页面字段对齐。
3. 日期格式符合 06 定义。
4. 字典来自统一定义。

可用测试示例：

- `node tests/business-taxonomy.test.js`
- `node tests/business-dictionary-global.test.js`
- `node tests/lead-field-standards.test.js`
- `node tests/standard-components-global.test.js`

## 10. 必须停下来的情况

出现以下任一情况，接手 AI 必须停止继续写入或上线判断：

1. 线上 `/api/diag` 与本地写入目标不一致。
2. 生产写入没有 dry-run、批次号、快照或回滚依据。
3. 财务页、业务页、页面接口任一段核对不一致。
4. 校区管理员或教练出现越权读写。
5. 同一指标跨页面数字不一致。
6. 权益余额、会员余额、财务金额无法解释。
7. 连续两次修复后同类测试仍失败。
8. 需求要求删除、覆盖、恢复核心表，但没有明确用户同意。
9. 需要线上敏感信息但没有安全渠道。

停止后必须汇报：

1. 已经确认的事实。
2. 哪一条红线被触发。
3. 已经完成的核对证据。
4. 还缺什么证据。
5. 建议下一步，不得继续猜测写入。

## 11. 事故恢复最低要求

恢复或回滚前必须有：

1. 恢复前备份。
2. 影响对象清单。
3. 影响客户 / 订单 / 权益 / 会员账户 / 财务流水数量。
4. 回滚脚本 dry-run。
5. 回滚后业务表核对。
6. 回滚后页面接口核对。
7. 回滚后前端展示核对。
8. 回滚后财务总览、收款流水、入账流水核对。

没有以上证据，不得宣布事故恢复完成。
