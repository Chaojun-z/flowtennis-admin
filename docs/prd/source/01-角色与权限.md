## 1. 权限系统目标

FlowTennis 不是单店单后台系统，而是多端、多校区、多业务链路系统。权限设计必须同时回答 5 个问题：

1. 这个人能不能登录某个端。
2. 这个人能看到哪些页面。
3. 这个人能看到哪些校区、哪些教练、哪些客户和哪些财务数据。
4. 这个人能不能写入、作废、导入、合并、重置、清空等高风险数据。
5. 后续新增“老板、校区店长、财务、运营、合伙人”等岗位时，能不能在不推翻现有系统的情况下扩展。

权限判断必须以服务端为最终边界。前端隐藏菜单、隐藏按钮只用于减少误操作，不能作为安全依据。

## 2. 端与账号体系

| 端 | 使用人 | 登录主体 | 当前账号来源 | 权限重点 |
|---|---|---|---|---|
| 管理后台 Web | 总部、店长、运营、财务、管理员 | `ft_users` 管理账号 | 账号密码登录，JWT 7 天有效 | 页面、数据范围、写入边界、高风险操作 |
| 教练端 Web/PWA | 教练 | `ft_users` 教练账号 | 账号密码登录，绑定 `coachId` | 只看本人课程、学员、反馈和提案 |
| 教练端微信小程序 | 教练 | `ft_users` 教练账号 + `wechatOpenId` | 先账号密码绑定，再微信登录 | 只看本人日程和本人可提交内容 |
| 约球小程序 | 用户 | 约球用户身份，不等同 `ft_users` | 微信登录 / 约球用户表 | 用户报名、取消、到场、费用 |
| 约球管理后台能力 | 管理员 / 约球运营 / 约球财务 | `ft_users` + feature permission | 管理后台账号 | `match_ops`、`match_finance` |

登录方案要求：

1. 管理后台和教练端 Web 使用 `/auth/login`，提交 `username/password`。
2. 登录成功后服务端返回 JWT 和归一化后的用户资料。
3. 停用账号 `status=inactive` 不允许登录。
4. 教练微信小程序使用 `/auth/wechat-bind` 绑定微信，再用 `/auth/wechat-login` 登录。
5. 管理员可在账号管理中解绑教练微信和服务号绑定。
6. 约球小程序用户身份和管理后台 `ft_users` 不混用；管理后台操作约球需要 `match_ops` 或 `match_finance`。

## 3. 当前权限底座字段

`ft_users` 是全平台管理账号与教练账号的事实表。

| 字段 | 类型 | 必填 | 说明 | 生成 / 维护方式 |
|---|---|---|---|---|
| `id` | string | 是 | 登录账号 ID；也是账号主键 | 管理员创建，创建后不允许随意变更 |
| `name` | string | 是 | 账号显示名 | 管理员维护 |
| `phone` | string | 否 | 手机号；可用于约球关联或联系 | 管理员维护，需校验手机号格式 |
| `password` | hash | 是 | 密码哈希 | 创建、重置、改密时由服务端加密 |
| `role` | enum | 是 | 当前底层只支持 `admin` / `editor` | 服务端归一化 |
| `systemType` | enum | 是 | `management` / `coach` | 由 `role` 推导；`admin` 为管理端，`editor` 为教练端 |
| `dataScope` | enum | 是 | `all` / `campus` / `coach` | 服务端归一化 |
| `campusIds` | string[] | 否 | 可见 / 可管理校区 ID 列表 | `dataScope=campus` 时必填 |
| `coachId` | string | 教练账号必填 | 绑定教练业务身份 | `role=editor` 时必须绑定 |
| `coachName` | string | 教练账号必填 | 绑定教练名称快照 | 由教练资料或账号名带出 |
| `featurePermissions` | string[] | 否 | 功能权限点，目前用于约球 | 服务端归一化 |
| `permissions` | string[] | 否 | 兼容字段，同步 `featurePermissions` | 服务端写入 |
| `matchPermissions` | string[] | 否 | 兼容字段，同步约球权限 | 服务端写入 |
| `matchOps` | boolean | 否 | 是否有约球运营权限 | 由 `featurePermissions` 推导 |
| `matchFinance` | boolean | 否 | 是否有约球财务权限 | 由 `featurePermissions` 推导 |
| `status` | enum | 是 | `active` / `inactive` | 管理员启停 |
| `wechatOpenId` | string | 否 | 教练小程序微信绑定 | 教练绑定 / 管理员解绑 |
| `officialAccountOpenId` | string | 否 | 服务号提醒绑定 | 系统绑定 / 管理员解绑 |

当前服务端归一化规则：

| 输入 | 归一化结果 |
|---|---|
| `role` 不是 `editor` | 统一视为 `admin` |
| `role=editor` | 强制 `dataScope=coach`，`systemType=coach` |
| `role=admin` 且 `dataScope=campus` | 只保留 `campusIds` 中的校区范围 |
| `role=admin` 且没有校区限制 | 默认为 `dataScope=all` |
| `role=admin` | 默认拥有 `match_ops`、`match_finance` |
| `role=editor` | 不默认拥有约球管理权限 |

## 4. 当前角色与未来可扩展角色

当前代码底层只落地两类 `role`：`admin` 和 `editor`。PRD 层需要保留更完整岗位模型，后续扩展时不能把所有岗位继续塞进 `admin`。

### 4.1 当前可执行角色

| PRD 角色 | 当前字段表达 | 使用端 | 数据范围 | 当前定位 |
|---|---|---|---|---|
| 总部管理员 | `role=admin` + `dataScope=all` | 管理后台 | 全平台 | 全量配置、账号、数据、财务和高风险操作 |
| 校区管理员 / 店长 | `role=admin` + `dataScope=campus` + `campusIds` | 管理后台 | 指定校区 | 管理本校区运营、学员、排课、订场、会员 |
| 教练 | `role=editor` + `dataScope=coach` + `coachId` | 教练端 Web / 小程序 | 本人相关数据 | 查看本人课程、本人学员、本人反馈和提案 |

### 4.2 未来推荐扩展角色

新增岗位时，不建议再新增一堆互相冲突的 `role` 值，而应增加 `roleKey` 或岗位模板，再映射到底层权限能力。

| 未来角色 | 建议 `roleKey` | 默认数据范围 | 页面能力 | 写入能力 |
|---|---|---|---|---|
| 老板 / 投资人 | `owner` | `all` 或指定项目 | 经营、财务、转化、教练人效只读 | 默认不可写，高风险需二次授权 |
| 超级管理员 | `super_admin` | `all` | 全部 | 全部，含账号和基础配置 |
| 总部运营 | `hq_ops` | `all` | 客户、教学、订场、会员、经营 | 常规业务写入，不含财务修正和账号权限 |
| 校区店长 | `campus_manager` | `campus` | 本校区客户、教学、订场、会员、基础经营 | 本校区常规业务写入 |
| 财务 | `finance` | `all` 或 `campus` | 财务总览、收款流水、入账流水、导出 | 默认只读；手工调整需独立权限 |
| 运营 | `operator` | `all` 或 `campus` | 线索、学员、排课、订场、会员 | 常规业务写入，不含作废、导入、合并 |
| 教练 | `coach` | `coach` | 教练工作台、日程、反馈 | 只允许本人课程反馈和提案 |
| 只读审计 | `readonly` | `all` 或 `campus` | 指定页面只读 | 不允许写入 |
| 合伙人 | `partner` | 指定校区 / 项目 | 项目经营摘要、分账相关只读 | 默认不可写 |

兼容要求：

1. 新增 `roleKey` 后，原 `role=admin/editor` 不得立即废弃。
2. 服务端应先根据 `roleKey` 生成动作权限、页面权限和数据范围，再兼容旧字段。
3. 旧账号没有 `roleKey` 时，按当前 `role/dataScope/campusIds/coachId` 解释。
4. 财务、账号、批量导入、作废、合并、清空等高风险操作必须拆成独立权限点，不应只靠 `admin` 判断。

## 5. 数据范围规则

### 5.1 全部校区 `dataScope=all`

适用对象：总部管理员、超级管理员、老板、总部财务。

规则：

1. 可读取全部校区、全部教练、全部客户、全部教学和订场会员数据。
2. 可进入全局经营分析和财务总览。
3. 能否写入高风险数据仍要看动作权限，不等于所有动作都无条件可做。

### 5.2 指定校区 `dataScope=campus`

适用对象：校区管理员、校区店长、校区运营、校区财务。

规则：

1. `campusIds` 必须非空。
2. 列表、详情、聚合接口都必须按授权校区裁剪。
3. 一个业务对象如果能直接取到 `campus/campusIds`，按自身字段判断。
4. 一个业务对象如果没有直接校区字段，必须通过关联对象推导校区。
5. 推导不到校区时，常规业务写入默认拒绝；总部管理员可按全局规则处理。

校区推导优先级：

| 对象 | 校区推导来源 |
|---|---|
| 学员 | `students.campus`，或其排课、购买、权益关联校区 |
| 线索 | `leads.campus`，或关联学员、订场用户、会员账户校区 |
| 排课 | `schedule.campus`，或班次、学员关联校区 |
| 班次 | `classes.campus`，或班次排课校区 |
| 课包 | `packages.campusIds`；无校区配置时视为全局商品 |
| 购买 | 学员校区、课包 `campusIds`、生成权益校区 |
| 权益 | 学员校区、购买校区、课包 `campusIds` |
| 权益流水 | 权益、购买、排课、学员推导校区 |
| 订场用户 | `courts.campus`、订场历史、会员账户关联校区 |
| 会员账户 | 关联订场用户校区 |
| 会员订单 | 会员账户、订场用户、订单目标校区 |
| 会员权益流水 | 会员账户、订单、订场用户校区 |
| 财务流水 | 学员、订场用户、排课、会员订单、业务来源校区 |
| 教练 | 教练资料校区，或其排课 / 班次关联校区 |

### 5.3 教练本人 `dataScope=coach`

适用对象：教练账号。

规则：

1. 必须绑定 `coachId`，同时保留 `coachName` 作为展示和兼容匹配。
2. 教练只能看到本人相关排课、班次、学员、学习计划、课后反馈、教练提案。
3. 教练端不返回订场用户、会员、完整财务、完整购买明细。
4. 教练可见的课包权益、购买记录必须是安全投影，只展示教学履约必要字段，不展示完整财务敏感字段。
5. 教练提交反馈、教案、请假 / 调整建议时，必须校验课程是否属于本人。

## 6. 页面与功能权限

### 6.1 管理后台页面

| 模块 | 总部管理员 | 校区管理员 | 教练账号 | 未来财务角色 | 未来只读角色 |
|---|---|---|---|---|---|
| 线索池 | 全部 | 授权校区 | 不可见 | 可配置只读 | 可配置只读 |
| 普通学员 / 正式学员 | 全部 | 授权校区 | 只通过教练端看本人相关 | 可配置只读 | 可配置只读 |
| 排课管理 / 排课日历 | 全部 | 授权校区 | 教练端本人课表 | 可配置只读 | 可配置只读 |
| 教练课时统计 / 教练人效 | 全部 | 授权校区 | 本人统计 | 可配置只读 | 可配置只读 |
| 课包产品 / 会员方案 / 价格方案 | 全部维护 | 当前建议只读或不可维护全局规则 | 不可见 | 不可见 | 只读 |
| 订场用户 / 会员管理 | 全部 | 授权校区 | 不可见 | 可配置只读 | 可配置只读 |
| 财务总览 / 收款 / 入账 | 全部 | 授权校区汇总或不开放，按角色决定 | 不可见 | 核心页面 | 只读 |
| 经营分析 | 全部 | 授权校区 | 不可见 | 可配置只读 | 只读 |
| 教练管理 / 校区管理 / 账号管理 | 全部 | 不应维护账号权限和全局校区 | 不可见 | 不可见 | 不可见 |
| 约球活动 | 需要 `match_ops` | 需要 `match_ops` | 不可见 | 只看财务需 `match_finance` | 不可见 |

### 6.2 约球功能权限

| 权限点 | 含义 | 默认拥有者 | 可做动作 |
|---|---|---|---|
| `match_ops` | 约球运营权限 | 当前 `admin` 默认拥有 | 活动管理、报名管理、订场信息、取消活动、到场确认 |
| `match_finance` | 约球财务权限 | 当前 `admin` 默认拥有 | 费用确认、分摊、收款、退款、约球财务查看 |

要求：

1. 约球运营和约球财务必须可拆分。
2. 只有 `match_ops` 不应能确认财务收款。
3. 只有 `match_finance` 不应能随意修改活动基础信息。
4. 管理后台账号进入约球管理时必须先判断 `featurePermissions`。

## 7. 写入权限与高风险操作

写入权限分两层：

1. 动作权限：这个角色能不能做这个动作。
2. 数据范围：这个动作的目标数据是否属于他的校区或本人范围。

### 7.1 总部管理员专属动作

以下动作只能由总部管理员或未来 `super_admin` 执行：

| 动作 | 原因 |
|---|---|
| 创建、更新账号，修改角色、校区范围、功能权限 | 会改变全平台数据边界 |
| 重置账号密码、停用账号、解绑微信 | 涉及账号安全 |
| 新增、编辑、删除校区资料 | 影响全平台校区口径 |
| 新增、编辑、删除全局课包规则、会员方案、价格方案 | 影响销售和履约规则 |
| 订场导入、批量删除、合并、历史迁移 | 涉及财务历史和客户合并 |
| 作废购买记录、作废会员订单、课包余额手工调整 | 影响权益和财务 |
| 财务流水手工调整、财务快照升级 | 影响收入口径 |
| 清空测试数据、初始化批量数据 | 高破坏性操作 |

### 7.2 校区管理员可写动作

校区管理员只允许写自己授权校区内的常规业务数据。

| 数据域 | 可写动作 | 必须校验 |
|---|---|---|
| 线索 | 新增、编辑、跟进 | 线索目标校区或关联客户校区在 `campusIds` 内 |
| 学员 | 新增、编辑 | 学员校区在 `campusIds` 内；编辑旧记录和新记录都要校验 |
| 排课 | 新增、编辑、取消 | 排课 `campus` 在 `campusIds` 内；改校区时旧校区和新校区都要校验 |
| 班次 | 新增、编辑、停用 | 班次校区在 `campusIds` 内 |
| 购买记录 | 新增、编辑常规字段 | 学员、课包、购买、权益能归属到授权校区 |
| 订场用户 | 新增、编辑 | 订场用户校区和历史记录目标校区在 `campusIds` 内 |
| 会员订单 | 开卡、续充、充值 | 会员账户和订场用户属于授权校区 |
| 会员权益消耗 | 消耗、补发、调整常规权益 | 会员账户和订单属于授权校区 |

### 7.3 教练可写动作

| 动作 | 条件 |
|---|---|
| 提交 / 编辑课后反馈 | `schedule.coachId` 或 `schedule.coach` 匹配当前教练 |
| 提交教练提案 / 教案 | 课程属于当前教练 |
| 查看本人日程 | 课程属于当前教练 |
| 微信绑定 / 改密码 | 当前登录账号本人 |

教练不得直接新增学员、改购买、改权益、改会员、改财务。

## 8. 账号管理页面需求

账号管理页是权限系统的操作入口。

### 8.1 列表字段

| 字段 | 说明 |
|---|---|
| 账号 ID | `id` |
| 姓名 | `name` |
| 手机号 | `phone` |
| 角色 | `admin` / `editor`，后续展示 `roleKey` |
| 系统类型 | `management` / `coach` |
| 数据范围 | 全部校区 / 指定校区 / 教练本人 |
| 可见校区 | `campusIds` 对应校区名 |
| 绑定教练 | `coachId/coachName` |
| 约球权限 | `match_ops`、`match_finance` |
| 状态 | `active` / `inactive` |
| 微信绑定 | 已绑定 / 未绑定 |
| 服务号绑定 | 已绑定 / 未绑定 |

### 8.2 创建账号

必填：

1. 账号 ID
2. 姓名
3. 初始密码
4. 角色
5. 如果是教练账号，必须选择绑定教练。
6. 如果数据范围是指定校区，必须选择至少一个校区。

创建结果：

1. 密码只存哈希，不存明文。
2. `role=editor` 自动变为 `systemType=coach`、`dataScope=coach`。
3. `role=admin` 默认 `systemType=management`。
4. 约球权限写入 `featurePermissions/permissions/matchPermissions` 三个兼容字段。

### 8.3 更新账号

允许更新：

1. 姓名
2. 手机号
3. 角色
4. 绑定教练
5. 数据范围和校区
6. 状态
7. 约球权限
8. 微信 / 服务号解绑

禁止规则：

1. 非总部管理员不能更新账号。
2. 教练账号没有绑定教练时不允许保存。
3. 指定校区范围没有选择校区时不允许保存。
4. 停用账号后不能登录，但历史业务数据保留。

## 9. 接口权限返回

| 场景 | HTTP 状态 | 返回 |
|---|---|---|
| 未登录 | `401` | `{ error: "未登录" }` 或登录态失败信息 |
| 登录失败 | `401` | `{ error: "账号或密码错误" }` |
| 登录失败过多 | `429` | `{ error: "登录失败次数过多，请稍后再试" }` |
| 账号停用 | `403` | `{ error: "账号已停用" }` 或 `{ error: "该账号已停用" }` |
| 管理端无权限 | `403` | `{ error: "无权限" }` |
| 约球运营无权限 | `403` | `{ error: "无约球运营权限" }` |
| 约球财务无权限 | `403` | `{ error: "无约球财务权限" }` |
| 缺必填字段 | `400` | 明确说明缺哪个字段 |
| 操作对象不存在 | `404` | 明确说明对象不存在 |

## 10. 权限验收用例

### 10.1 登录与账号

| 用例 | 预期 |
|---|---|
| active 管理账号用正确密码登录 | 返回 token 和 `systemType=management` |
| inactive 管理账号登录 | 拒绝，提示账号停用 |
| 教练账号登录 | 返回 `systemType=coach`、`dataScope=coach`、`coachId` |
| 教练微信未绑定直接微信登录 | 拒绝，提示先绑定教练账号 |
| 教练微信绑定后微信登录 | 返回同一教练账号 token |
| 非管理员访问账号列表 | `403` |

### 10.2 校区权限

| 用例 | 预期 |
|---|---|
| 校区管理员 A 只绑定顺义校区 | 只能看到顺义线索、学员、排课、订场、会员、财务汇总 |
| 校区管理员 A 访问马坡单条排课 | 拒绝或不返回该数据 |
| 校区管理员新增排课但 `campus=马坡` | 拒绝 |
| 校区管理员编辑顺义排课改成马坡 | 拒绝 |
| 总部管理员查看全部校区 | 不裁剪 |

### 10.3 教练权限

| 用例 | 预期 |
|---|---|
| 教练甲查看课表 | 只返回教练甲相关课程 |
| 教练甲查看学员 | 只返回教练甲课程、班次、计划关联学员 |
| 教练甲提交教练乙课程反馈 | 拒绝 |
| 教练账号请求财务页 | 不返回财务数据 |

### 10.4 高风险操作

| 用例 | 预期 |
|---|---|
| 校区管理员重置他人密码 | 拒绝 |
| 校区管理员作废购买记录 | 默认拒绝 |
| 校区管理员批量导入订场数据 | 默认拒绝 |
| 总部管理员执行高风险动作 | 通过动作权限后，还需保留审计字段 |
| 财务角色只读财务页 | 能查看，不能手工调整 |

## 11. 复原实现检查清单

交接方按本文复原权限系统时，必须逐项确认：

1. `ft_users` 字段齐全。
2. 登录返回用户资料已经做服务端权限归一化。
3. 前端和后端的权限归一化口径一致。
4. 所有列表、聚合、页面数据接口都调用服务端数据范围裁剪。
5. 教练端数据经过本人范围裁剪和安全投影。
6. 账号管理只有总部管理员可用。
7. 约球运营和约球财务权限可拆分。
8. 高风险写入动作不只依赖“前端隐藏按钮”。
9. 校区管理员写入时校验目标校区，而不是只校验登录角色。
10. 任何新增角色必须映射到页面权限、动作权限、数据范围三张表。
