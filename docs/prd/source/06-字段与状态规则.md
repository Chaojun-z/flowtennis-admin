# 字段与状态规则

> 版本：2026-07-02
> 状态：PRD 内置字段与状态第一事实源
> 定位：定义全平台核心字段、字段来源、字段影响范围、状态枚举、状态流转、写入校验、展示规则。历史核心数据字典内容已迁入本文；后续以本文为准。

## 0. 05 与 06 的边界

| 文档 | 回答的问题 | 典型内容 | 不负责什么 |
|---|---|---|---|
| `05-全平台数据口径.md` | “这个指标 / 字段口径怎么算？” | 指标 ID、指标名、分子、分母、去重规则、时间口径、排除规则、权威来源、使用页面 | 不展开每张业务表的全部字段、不定义表单校验细节 |
| `06-字段与状态规则.md` | “这些字段怎么存、怎么填、状态怎么流转？” | 表字段、字段来源、必填规则、枚举、状态、状态流转、禁止写法、展示格式 | 不重新定义指标公式、不替代 05 的统计口径 |

使用原则：

1. 需要算人数、金额、转化率、复购率、留存率，看 05。
2. 需要建表、做表单、写接口、定义状态、做字段校验，看 06。
3. 同一个业务含义同时涉及统计和字段时，05 定义“怎么算”，06 定义“字段怎么保存和流转”。
4. PRD 对外交付时，不能再要求对方额外阅读 PRD 外的散文档。

这份文档是给“真正要读懂数据结构的人”看的。

它不讲页面，不讲培训话术，只讲 5 件事：

1. 系统有哪些核心表
2. 每张表的关键字段是什么
3. 每个字段是怎么来的
4. 哪些字段是手填，哪些是自动生成，哪些是快照
5. 每个字段会影响哪里

## 一、阅读说明

为了避免文档过大，这份数据字典只覆盖：

- 真正驱动业务的核心表
- 会跨页面联动的关键字段
- 新人最容易搞混的字段

不重点展开的内容：

- 纯 UI 展示字段
- 临时搜索条件
- 非核心备注类字段的所有细枝末节

字段来源说明统一用这 4 类：

- `手填`：前端由人录入
- `自动生成`：后端创建时自动写入
- `快照复制`：从上游对象复制过来，保存当时状态
- `系统计算`：根据规则、流水或状态推导出来

## 二、全平台统一读模型字段

以下字段不是某个页面自己解释的字段，而是全平台统一口径。客户中心、教学中心、产品与定价、财务中心、经营分析、基础设置中只要涉及同一业务含义，都必须按这里的定义读取，不允许页面各自重写一套规则。

全平台指标计算口径以 [05-全平台数据口径.md](05-全平台数据口径.md) 为准。本文只解释核心表、字段、状态和校验规则，不替代指标公式。

前端统一访问器：

- `customerLifecycleRowsForRecord`

- `customerLifecycleByMembershipAccountId`
- `customerLifecycleSource`
- `customerLifecycleCampus`
- `customerLifecycleOwner`
- `customerLifecycleStudentStage`
- `customerLifecycleCourtStage`

| 字段 | 中文解释 | 来源 | 是否关键 | 影响范围 |

| `studentPackageStatusTag` | 课包状态标签：未买过课包、课包有余额、课包即将耗尽、课包已用完 | 系统计算 | 是 | 学员筛选、课包运营、经营分析 |

| `studentActivityStatus` | 活跃状态：近30天活跃、31-90天活跃、91-180天沉默、180天以上沉睡、从未正式上课 | 系统计算 | 是 | 在期学员、历史学员、教练端、经营分析 |
| `studentLessonVolumeTag` | 历史课时标签：历史课时30+、历史课时50+、历史课时100+ | 系统计算 | 是 | 学员分层、教练端、经营分析 |
| `studentOperationReminderTag` | 运营提醒标签：课包待续费、有余额未活跃、已转单次、暂无提醒；`暂无提醒` 在系统中显示为 `-` | 系统计算 | 是 | 学员跟进、课包运营、经营分析 |
| `lastFormalLessonAt` | 最近一次正式课上课时间 | 系统计算 | 是 | 活跃状态、在期学员、教练端 |

| `membershipStatus` | 会员账户状态 | 系统计算/会员账户状态 | 是 | 会员管理、会员订单、财务展示链 |
| `source` | 标准来源 | 系统计算 | 是 | 筛选、渠道占比、转化分析 |
| `campus` | 标准客户归属校区 | 系统计算 | 是 | 页面筛选、排课默认、财务展示兜底 |
| `owner` | 标准客户负责人 | 系统计算 | 是 | 学员/线索归属、排课默认、转化分析 |
| `leadStage` | 线索阶段：新线索、跟进中、已约体验、已体验待成交、已成交、已流失 | 手填/系统计算 | 是 | 线索池、跟进、成交分析 |
| `dealType` | 成交类型/成交构成：课程、订场、订场会员；兼容历史值：会员、课程+订场、课程+会员、订场+会员、课程+订场+会员；标准展示统一为课程、订场、订场会员及组合，如课程+订场+订场会员 | 系统计算/兼容历史成交字段 | 是 | 线索池、成交统计、客户链路 |
| `customerType` | 类型：成人、青少年 | 手填/导入标准化 | 是 | 线索池、客户分层、经营分析 |
| `demandProduct` | 需求产品：私教课、小班课、订场、会员、陪打、约球、穿线、合作、其他 | 手填/导入标准化 | 是 | 线索池、需求分析、产品分析 |

硬规则：

1. 历史学员和在期学员不是两张客户事实表，是 `studentRosterScope` 的两个视图。
2. 订场用户和会员管理不是两套客户解释，是 `courtStage` 和 `membershipStatus` 的两个视图。
3. 历史 `leadId/fromLeadId` 只能作为兼容别名，新链路必须写 `sourceLeadId`。
4. 页面如需展示或筛选来源、校区、负责人、学员阶段、订场阶段、会员状态，必须走统一访问器或后端统一读模型。
5. 线索阶段只回答“现在推进到哪里”，成交类型只回答“最后成交了什么”，不得再用人工 `是否转化` 字段作为主口径。
6. 历史 `consultType` 只能兼容映射到 `demandProduct`；历史 `conversionType` 只能兼容映射到 `dealType`；历史 `enrollAtRaw/formalSignupAt` 页面展示统一叫“成交时间”。
7. `lostReason` 页面展示统一叫“流失原因”；`formalCoach` 页面展示统一叫“成交教练”。
8. 学员活跃与标签字段必须按 `08-具体需求/01-管理后台/01-客户与线索/04-学员活跃与标签体系.md` 和 `05-全平台数据口径.md` 执行；页面不得自行拆分资源置换、赠课或 0 元正式课标签。

## 八、全平台状态枚举与流转规则

### 1. 线索状态

| 状态 | 含义 | 允许进入方式 | 允许下一步 | 统计影响 |
|---|---|---|---|---|
| 新线索 | 刚进入线索池，尚未有效跟进 | 手动新增、导入、系统生成 | 跟进中、已约体验、已流失、无效 / 重复 / 测试 / 误录 | 计入有效线索，除非被排除 |
| 跟进中 | 已发生跟进动作 | 新增跟进记录 | 已约体验、已成交、已流失 | 计入有效线索 |
| 已约体验 | 已安排体验课 | 创建体验课排课或体验预约 | 已体验待成交、已成交、已流失 | 计入预约体验 |
| 已体验待成交 | 体验课已到课但未成交 | 体验课有效完成 | 已成交、已流失 | 计入已体验 |
| 已成交 | 发生课程、订场或会员成交 | 有效购买、有效订场、会员开卡 / 续充 | 留存、复购、再次消费 | 计入对应成交口径 |
| 已流失 | 明确不继续 | 运营标记并填写原因 | 可重新激活为跟进中 | 不计后续转化，保留历史 |
| 无效 / 重复 / 测试 / 误录 | 不应进入业务统计 | 人工标记或导入识别 | 修正为有效状态 | 从有效线索分母排除 |

硬规则：线索阶段只表达“现在推进到哪里”；成交类型用 `dealType` 单独表达，不得用人工“是否转化”替代。

### 2. 学员列表范围

| 范围 | 定义 | 来源 | 退出条件 |
|---|---|---|---|
| 历史学员 | 所有有过有效排课或上课事实的客户，包含体验课、正式课、课包课、单次付费课和 0 元单次课 | 客户生命周期读模型、排课事实推导 | 不因课包用完退出 |
| 在期学员 | 历史学员的子集：课包有余额，或近 90 天有正式课上课记录 | 购买、权益、排课事实推导 | 超过 90 天无正式课且无课包余额后退出在期列表 |

硬规则：历史学员和在期学员是同一客户生命周期的两个当前视图，不是两张独立客户表；在期学员必须是历史学员的子集。

### 3. 课包、购买、权益状态

| 对象 | 状态 | 含义 | 关键规则 |
|---|---|---|---|
| 课包 | active | 可售卖 | 可新建购买 |
| 课包 | inactive | 停售 | 不允许新购买，不影响历史购买 |
| 课包 | merged | 已并入其他课包 | 不允许作为新购买主商品 |
| 购买 | active | 有效购买 | 计入课程收入和待履约 |
| 购买 | voided | 已作废 | 关联权益应作废，写追溯 |
| 购买 | refunded | 已退款 | 财务按退款 / 冲正规则处理 |
| 权益 | active | 可用 | 可被排课消耗 |
| 权益 | depleted | 已用完 | 不可继续消课 |
| 权益 | expired | 已过期 | 不可继续消课，除非有延期规则 |
| 权益 | voided | 已作废 | 不可排课，不计有效余额 |

硬规则：`remainingLessons`、`usedLessons`、权益 `status` 是系统根据购买、排课、流水推导的结果，不能靠页面手填。

### 4. 排课状态

| 状态 | 含义 | 课时影响 | 财务影响 | 反馈影响 |
|---|---|---|---|---|
| 已排课 | 课程已安排，尚未完成 | 通常不最终扣课，视业务动作而定 | 不直接确认入账 | 不要求反馈 |
| 已结束 | 课程已到结束时间或已完成 | 可触发消课 | 消课后确认入账 | 进入待反馈 |
| 已取消 | 课程取消 | 不扣课；如已扣课需回退 | 如已入账需回退 | 不计待反馈 |
| 待反馈 | 已结束但未提交反馈 | 不改变课时 | 不改变财务 | 计入未反馈 |
| 已反馈 | 已提交课后反馈 | 不改变课时 | 不改变财务 | 计入反馈完成 |

硬规则：取消已消课排课必须回退权益和财务影响；不能只把排课状态改成已取消。

### 5. 订场与会员状态

| 对象 | 状态 | 含义 | 规则 |
|---|---|---|---|
| 订场用户 | active | 正常客户 | 可产生订场、会员和财务历史 |
| 订场用户 | inactive | 隐藏、删除或被合并 | 不应出现在默认有效列表，历史财务保留 |
| 会员账户 | active | 正常会员期 | 可储值消费和权益消耗 |
| 会员账户 | extended | 延续期 | 有余额但已过原有效期，延长到最晚清零日 |
| 会员账户 | cleared | 到期清零 | 余额已清零，应有账户事件 |
| 会员账户 | voided | 账户作废 | 不计有效会员 |
| 会员订单 | active | 有效订单 | 计入会员储值收入和待履约 |
| 会员订单 | voided | 已作废 | 需回退账户、权益、财务 |
| 会员订单 | refunded | 已退款 | 按退款 / 冲正处理 |

硬规则：会员充值计入总收入、会员储值收入和待履约；充值本身不计入已入账。只有储值消费、扣款、权益消耗发生时，才影响已入账。

### 6. 约球状态

| 状态 | 展示名 | 含义 | 下一步 |
|---|---|---|---|
| open | 招募中 | 可报名 | full、booked、cancelled |
| full | 已满员 | 人数达到目标 | booked、cancelled |
| booked | 已订场 | 运营已确认场地 | playing、attendance_pending、cancelled |
| playing | 进行中 | 活动正在发生 | attendance_pending、fee_pending |
| attendance_pending | 待确认到场 | 等运营确认到场名单 | fee_pending |
| fee_pending | 待确认费用 | 等财务确认费用和收款 | settled |
| settled | 已结清 | 费用完成 | 关闭 |
| cancelled | 已取消 | 活动取消 | 关闭，保留日志 |

硬规则：约球费用动作必须写费用分摊和操作日志；取消、退款、转让不能只改活动状态。

## 九、字段写入与展示硬规则

1. 必填字段不能靠前端提示兜底，服务端也必须校验。
2. 日期字段保存原始时间时必须能展示成标准页面格式；列表优先 `YYYY-MM-DD`，详情需要时展示 `YYYY-MM-DD HH:mm`。
3. 页面不得展示数据库内部 ID、流水 ID、导入批次、原始 ISO 时间、调试字段，除非该页面是审计页。
4. 历史字段只能作为兼容别名，不得继续作为新页面字段名扩散。
5. 金额字段必须明确应收、实收、差价、退款、待履约、已入账，不得混用。
6. 状态字段只能从本文枚举中取值；新增状态必须先更新本文，再改代码。
7. 删除、作废、退款、取消、合并、清零必须记录操作人、时间、原因和关联对象。
8. 校区字段必须能支撑权限过滤；没有校区且无法推导校区的数据，校区管理员默认不可写。
9. 教练字段必须同时考虑 `coachId` 和历史 `coach/coachName`，但新链路优先写 `coachId`。
10. 客户身份字段必须优先走统一客户生命周期，不能让页面各自拼姓名、手机号、来源、校区、负责人。
