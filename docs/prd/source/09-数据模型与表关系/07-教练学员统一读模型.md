# 教练学员统一读模型

> 版本：2026-08-23
> 状态：方案定版，作为后续开发依据。
> 定位：统一教练小程序、教练端 Web、管理端教练主页里的“教练能看到哪些学员、每个 tab 展示谁、数字怎么算”的口径。

## 1. 目标

1. 小程序、教练端 Web、管理端教练主页必须读取同一套教练学员读模型。
2. 页面不得分别用排课、课包、学员表临时拼出另一套“我的学员”。
3. 不使用“全部”tab。
4. 不使用“其他”身份。
5. `当前学员 = 在课 + 结课`，只包含当前归属给该教练的正式服务学员。
6. 体验课学员不能污染当前学员，也不能进入在课 / 结课。
7. 教练上过的所有有效体验课学员都必须能在体验 tab 看到，不管后续是否转化、转给谁。

## 2. 最终建模原则

最终方案不再使用互斥的 `primaryIdentity`。

原因是同一个学员和同一个教练之间可能同时存在多种关系：

1. 上过这个教练的体验课。
2. 后来归属给别的教练。
3. 这个教练又帮别的教练代过正式课。
4. 这个学员曾经归属过这个教练，后来转走。

所以模型不回答“这个学员唯一身份是什么”，只回答：

1. 这个学员和这个教练发生过哪些事实。
2. 这个学员当前是否归属这个教练。
3. 当前归属正式服务是在课还是结课。
4. 最终应该出现在哪些 tab。

最终模型是：

```text
教练 + 学员
= 历史池
+ 正交事实位
+ 当前归属服务状态
+ 展示 tab 布尔字段
+ 排序时间字段
```

## 3. 逻辑模型

每个 `coachId + studentId` 生成一条读模型记录。

```text
coachStudentRosterItem = {
  coachId,
  studentId,

  inCoachHistory,
  inCurrentStudentRoster,

  isCurrentOwner,
  isHistoricalOwner,

  hasTrialFact,
  hasOwnedFormalFact,
  hasFormalFactWithCoach,
  hasNonOwnedFormalFact,

  nonOwnedFormalKind,
  currentOwnedServiceStatus,
  trialConversionStatus,
  paymentTypes,

  showInActiveTab,
  showInCompletedTab,
  showInTrialTab,
  showInSubstituteTab,

  latestTrialLessonAt,
  latestOwnedFormalLessonAt,
  latestNonOwnedFormalLessonAt,
  latestFormalLessonWithCoachAt,
  currentOwnershipStartedAt,
  currentOwnershipEndedAt,
  serviceCompletedAt,
  activeTabSortAt,
  completedTabSortAt,
  trialTabSortAt,
  substituteTabSortAt,

  modelVersion,
  updatedAt
}
```

## 4. 字段口径

| 字段 | 口径 |
|---|---|
| `inCoachHistory` | 这个学员和这个教练发生过至少一种有效事实：体验、当前归属、历史归属、正式上课、非归属正式上课。 |
| `inCurrentStudentRoster` | 当前学员，等于 `showInActiveTab || showInCompletedTab`。 |
| `isCurrentOwner` | 当前正式服务归属教练是该教练。不能靠最近上课教练反推。 |
| `isHistoricalOwner` | 该教练曾经是这个学员的正式服务归属教练。学员转走后仍保留历史事实。 |
| `hasTrialFact` | 该教练给这个学员上过有效体验课。取消、爽约、未到、未来待上课、测试排课不算。 |
| `hasOwnedFormalFact` | 该教练作为当前或历史归属教练，服务过这个学员的正式课或正式权益。 |
| `hasFormalFactWithCoach` | 该教练给这个学员上过有效正式课，不区分是否归属。 |
| `hasNonOwnedFormalFact` | 该教练在“课程发生当时”不是该学员归属教练，但给学员上过有效正式课。必须按上课时的归属快照判断，不能用当前归属倒推。 |
| `nonOwnedFormalKind` | `NONE` / `SUBSTITUTE_FOR_OTHER_OWNER` / `NO_OWNER_FORMAL`。分别表示无、替别的归属教练上课、无归属正式散客课。 |
| `currentOwnedServiceStatus` | 只对当前归属学员有效：`ACTIVE` / `COMPLETED` / `NONE`。非当前归属学员固定为 `NONE`。 |
| `trialConversionStatus` | `NONE` / `UNCONVERTED` / `CONVERTED_TO_ME` / `CONVERTED_TO_OTHER`。 |
| `paymentTypes` | 正式服务付费方式数组：`PACKAGE` / `SINGLE` / `PACKAGE_THEN_SINGLE` / `MIXED` / `ZERO_FORMAL`。体验课不进入这个字段。 |

## 5. 在课 / 结课口径

在当前系统未增加“手动服务状态”前，`在课 / 结课` 必须沿用管理端现有在期学员口径，不能另起一套。

### 5.1 在课

```text
showInActiveTab = true
= isCurrentOwner = true
+ currentOwnedServiceStatus = ACTIVE
```

`ACTIVE` 的当前落地口径：

1. 当前归属给该教练。
2. 且存在正式服务事实。
3. 且满足以下任一条件：
   - 当前正式课包剩余课时 > 0；
   - 最近 90 天内有有效正式课上课事实。

### 5.2 结课

```text
showInCompletedTab = true
= isCurrentOwner = true
+ currentOwnedServiceStatus = COMPLETED
```

`COMPLETED` 的当前落地口径：

1. 当前归属给该教练。
2. 有正式服务事实。
3. 不满足 `ACTIVE` 条件。

### 5.3 重要边界

1. 体验课不参与 `ACTIVE / COMPLETED` 判断。
2. 非当前归属学员不进入在课 / 结课。
3. 曾经归属但现在转走的学员，不能自动塞进原教练的结课 tab，否则会污染“当前学员 = 在课 + 结课”。
4. 如果未来业务要求“真实服务结束”不再依赖近 90 天规则，必须新增明确的服务状态字段或手动结课动作，再替换本节口径。

## 6. Tab 展示规则

存储层使用布尔字段，不使用 `visibleTabs` 数组作为查询条件。

| Tab | 字段 | 绝对规则 |
|---|---|---|
| 在课 | `showInActiveTab` | 当前归属该教练，且正式服务状态为 `ACTIVE`。 |
| 结课 | `showInCompletedTab` | 当前归属该教练，且正式服务状态为 `COMPLETED`。 |
| 体验 | `showInTrialTab` | 该教练上过有效体验课，不管后续是否转化、转给谁。 |
| 代课 | `showInSubstituteTab` | 该教练上过有效非归属正式课，且当前不归属该教练。 |

补充说明：

1. 页面可以继续叫“代课”，但技术口径是“非归属正式课”。
2. `showInSubstituteTab` 同时覆盖两类场景：
   - 学员归属别人，该教练替别人上正式课；
   - 学员没有归属，该教练上了单次正式课或 0 元正式课。
3. 行内必须用 `nonOwnedFormalKind` 区分“代课”和“无归属正式课”，避免运营误解。
4. 一个学员可以同时出现在多个 tab，例如同一个教练既上过体验，又上过非归属正式课。

## 7. 三个核心漏洞的最终修复

### 7.1 历史归属转走后消失

问题：

```text
学员曾经归属 A，后来转给 B。
A 不再是当前归属，也不是代课，也不是体验。
如果只靠当前身份，A 视角会丢失这个历史事实。
```

修复：

1. 增加 `isHistoricalOwner`。
2. 历史归属只进入教练历史池，不自动进入当前在课 / 结课 tab。
3. 未来管理端教练主页如需看“历史归属学员”，应使用 `isHistoricalOwner = true && isCurrentOwner = false` 做历史下钻，不要污染当前学员数字。

### 7.2 无归属正式课 / 散客漏展示

问题：

```text
学员没有归属教练，但上了 A 的单次正式课。
如果代课只定义为“归属别人”，这个学员无处可放。
```

修复：

1. 增加 `hasNonOwnedFormalFact`。
2. 增加 `nonOwnedFormalKind = NO_OWNER_FORMAL`。
3. 页面仍进入“代课”tab，但行内展示为“无归属正式课”。
4. 如果后续产品认为“代课”这个名字不准确，可以把 tab 文案改成“非归属”，但底层口径不变。

### 7.3 主身份互斥导致冲突

问题：

```text
学员上过 A 的体验课，后来归属 B，之后 A 又代过 B 的正式课。
如果只能选一个主身份，就会丢掉体验或代课其中一个事实。
```

修复：

1. 删除 `primaryIdentity`。
2. 使用可叠加事实位：`hasTrialFact`、`isCurrentOwner`、`isHistoricalOwner`、`hasNonOwnedFormalFact`。
3. tab 由事实位生成，不由单一身份生成。

## 8. 代课事实必须按历史快照计算

`hasNonOwnedFormalFact` 不能用“当前是否归属”倒推。

错误算法：

```text
现在不归属我 + 历史上我上过正式课 = 代课
```

这个算法会把“曾经正常归属，后来转走”的学员误判为代课。

正确算法：

```text
某节正式课发生时
+ 上课教练 = 当前教练
+ 当时的正式服务归属教练 != 当前教练
= 非归属正式课事实
```

如果课程发生时没有归属教练：

```text
nonOwnedFormalKind = NO_OWNER_FORMAL
```

如果课程发生时归属其他教练：

```text
nonOwnedFormalKind = SUBSTITUTE_FOR_OTHER_OWNER
```

## 9. 性能模型

### 9.1 查询字段必须拍平

列表页不能依赖数组字段做查询。

禁止把下面字段作为存储层查询条件：

```text
visibleTabs: [ACTIVE, COMPLETED, TRIAL, SUBSTITUTE]
```

必须拍平成：

```text
showInActiveTab
showInCompletedTab
showInTrialTab
showInSubstituteTab
```

前端接口可以返回 `studentTabKeys` 方便展示，但它只能由后端根据布尔字段生成，不能作为权威查询字段。

### 9.2 秒级读取要求

教练学员列表必须满足：

1. 按 `coachId + tab` 读取，不允许远程扫描全量学员后再筛选。
2. 顶部数量必须和当前 tab 过滤后的完整集合一致，不能只统计当前页。
3. 搜索、筛选、排序、分页必须基于同一份读模型。
4. 小程序、教练端 Web、管理端教练主页不能各自计算数量。

建议索引或快照键：

```text
coachId + showInActiveTab + activeTabSortAt
coachId + showInCompletedTab + completedTabSortAt
coachId + showInTrialTab + trialTabSortAt
coachId + showInSubstituteTab + substituteTabSortAt
```

如果使用 TableStore 或快照包，不要求照搬 SQL 索引，但必须达到同等效果：按教练和 tab 直接读取，不扫全表。

## 10. 排序时间字段

每个 tab 必须有独立排序时间。

| 字段 | 用途 |
|---|---|
| `latestTrialLessonAt` | 体验 tab 排序。 |
| `latestOwnedFormalLessonAt` | 当前归属正式服务最近上课时间。 |
| `latestNonOwnedFormalLessonAt` | 代课 / 非归属正式课 tab 排序。 |
| `latestFormalLessonWithCoachAt` | 该教练和该学员最近一次正式课时间，不区分归属。 |
| `currentOwnershipStartedAt` | 当前归属开始时间。 |
| `currentOwnershipEndedAt` | 最近一次归属结束时间。 |
| `serviceCompletedAt` | 当前归属正式服务进入结课的时间。 |
| `activeTabSortAt` | 在课 tab 排序字段。 |
| `completedTabSortAt` | 结课 tab 排序字段。 |
| `trialTabSortAt` | 体验 tab 排序字段。 |
| `substituteTabSortAt` | 代课 tab 排序字段。 |

默认排序建议：

1. 在课：最近正式上课时间倒序；没有上课时间时，用归属开始时间倒序。
2. 结课：结课时间倒序；没有结课时间时，用最近正式上课时间倒序。
3. 体验：最近体验课时间倒序。
4. 代课：最近非归属正式课时间倒序。

## 11. 同步架构

### 11.1 当前阶段

当前项目不强制立刻引入 MQ、Kafka、Canal。

更安全的落地方式：

1. 所有页面只读统一后端读模型。
2. 读模型由一个统一 builder 生成，不能散落在页面和接口里重复计算。
3. 排课、购课、归属变化后，可以用按需重建、摘要重建或快照刷新保证秒级生效。
4. builder 必须幂等：同一批事实重复计算，结果完全一致。
5. 任一同步失败时，必须能用全量重建恢复。

### 11.2 后续阶段

当数据量或实时性超过当前 builder / 快照能力时，再升级事件驱动。

可监听的事实事件：

```text
ClassCompletedEvent
ClassCancelledEvent
OwnershipChangedEvent
OrderPaidEvent
EntitlementChangedEvent
StudentMergedEvent
```

事件驱动不是第一阶段强制项，但事件消费者必须满足：

1. 幂等。
2. 可重放。
3. 可全量重建对账。
4. 不允许写入半成品快照后被页面读取。

## 12. 页面使用规则

### 12.1 教练小程序

1. 只读取后端返回的统一 `studentRoster`。
2. 不在小程序端自行判断体验、在课、结课、代课。
3. 不展示“全部”tab。
4. tab 数字读取后端统计，不用本地列表条数临时凑。

### 12.2 教练端 Web

1. 和小程序读取同一套 `coachStudentRosterItem`。
2. 页面字段、筛选、搜索和排序不能另算。

### 12.3 管理端教练主页

1. 管理端查看某个教练时，读取同一套教练学员读模型。
2. 管理端可以额外展示历史下钻，例如“历史归属”，但不能把历史归属并入当前学员。
3. 管理端大盘统计不直接依赖这张教练视角表；大盘应读取平台级聚合模型。

## 13. 关键场景验收

| 场景 | A 教练展示 | B 教练展示 |
|---|---|---|
| A 上体验课，学员未转化 | A 的体验 tab | 无 |
| A 上体验课，后来买 A 的正式服务 | A 的体验 tab + 在课 / 结课 | 无 |
| A 上体验课，后来买 B 的正式服务 | A 的体验 tab | B 的在课 / 结课 |
| A 上体验课，后来归属 B，A 又代 B 上正式课 | A 的体验 tab + 代课 tab | B 的在课 / 结课 |
| 学员曾归属 A，后来转归属 B | A 保留历史归属事实，不进当前在课 / 结课 | B 的在课 / 结课 |
| 学员无归属，上了 A 的单次正式课 | A 的代课 tab，行内标记“无归属正式课” | 无 |
| A 只是替 B 上正式课 | A 的代课 tab | B 的在课 / 结课 |
| A 上未来体验课，尚未完成 | 不展示在体验 tab | 无 |
| A 的体验课取消 / 爽约 / 未到 | 不展示在体验 tab | 无 |
| A 的正式课取消 / 测试排课 | 不影响在课 / 结课 / 代课 | 不影响 |

## 14. 反向测试

开发必须补充以下反向测试：

1. 只体验学员不能进入在课。
2. 只体验学员不能进入结课。
3. 代课学员不能进入当前学员。
4. 无归属正式课不能丢失。
5. 历史归属转走后不能被误判为代课。
6. 历史归属转走后不能进入原教练当前学员。
7. 同一学员同时有体验和代课事实时，两个 tab 都要出现。
8. 小程序和管理端同一个教练的 tab 数字必须一致。
9. 搜索、筛选后顶部数字必须和筛选后完整集合一致。
10. 不得返回“全部”tab。

## 15. 最终结论

1. 最终模型采用“事实位 + 当前归属服务状态 + 拍平 tab 字段”，不采用互斥主身份。
2. 当前学员只由 `showInActiveTab + showInCompletedTab` 组成。
3. 体验、代课、历史归属都是可叠加事实，不污染当前学员。
4. 代课必须按上课当时的归属快照判断，不能用当前归属倒推。
5. 查询字段必须拍平，列表读取必须按教练和 tab 直取，保证秒级。
6. 第一阶段不强制 MQ/Kafka；统一 builder、幂等重建、快照刷新更适合当前系统。
