## 1. 模型目标

客户生命周期模型解决一个核心问题：同一个自然人在系统里可能先是线索，再成为体验学员、正式学员、订场用户、会员用户，页面不能把这些身份当成多个人。

复刻系统时必须实现：

| 能力 | 规则 |
|---|---|
| 统一识别 | 同一客户在不同业务表中通过人工合并 ID、手机号、微信身份、会员账户、订场账户串联。 |
| 统一展示 | 姓名、手机号、来源、校区、负责人使用同一生命周期结果。 |
| 当前分层 | 普通学员和正式学员是当前视图，不能同一客户同时出现在两个当前列表。 |
| 历史保留 | 客户转正式后，体验链和线索链仍用于转化分析，不在普通学员当前列表重复展示。 |
| 统一统计 | 线索池、普通学员、正式学员、转化与留存、经营分析读取同一套生命周期/指标结果。 |

## 2. 权威实现入口

## 3. 上游事实对象

| 对象 | 表/来源 | 生命周期使用字段 | 说明 |
|---|---|---|---|
| 线索 | `ft_leads` | `id`、姓名、手机号、来源、校区、负责人、需求产品、阶段、成交类型、成交时间 | 首次触达和转化来源。 |
| 跟进记录 | `ft_lead_followups` | `leadId`、跟进内容、跟进结果、下次跟进时间、操作人 | 用于判断跟进状态和运营动作。 |
| 学员 | `ft_students` | `id`、姓名、手机号、来源、校区、负责人、学生阶段、关联线索 | 教学身份主档。 |
| 购买记录 | `ft_purchases` | `studentId`、购买时间、课包、实收、状态 | 判断正式学员和成交。 |
| 权益账户 | `ft_entitlements` | `studentId`、`purchaseId`、总课时、剩余课时、状态 | 判断课包余额和履约状态。 |
| 排课 | `ft_schedule` | `studentId`、教练、校区、上课时间、课程状态 | 判断体验、已上课、教练关联。 |
| 订场用户 | `ft_courts` | 订场用户 ID、姓名、手机号、订场历史、会员关联 | 判断订场阶段和订场消费。 |
| 会员账户 | `ft_membership_accounts` | 账户 ID、订场用户 ID、手机号、状态、余额 | 判断会员身份。 |
| 会员订单 | `ft_membership_orders` | 会员账户、购买时间、实收、状态 | 判断会员成交和储值。 |
| 约球用户 | `match_users` | openid、unionid、手机号 | 仅在手机号/显式关联后进入统一客户视角。 |

## 4. 识别优先级

识别顺序必须固定，禁止页面自行判断：

| 优先级 | 识别依据 | 规则 |
|---:|---|---|
| 1 | 人工合并客户档案 ID | 如果系统已有合并结果，以合并结果为准。 |
| 2 | 已有关联字段 | `sourceLeadId`、`studentId`、`courtId`、`membershipAccountId` 等显式关系优先。 |
| 3 | 手机号 | 标准化手机号后匹配；空手机号不参与手机号合并。 |
| 4 | 微信 unionid/openid | 仅用于微信端身份追踪；没有手机号时不能直接覆盖后台客户。 |
| 5 | 会员账户/订场账户 | 用于补全会员和订场身份。 |
| 禁止 | 姓名 | 姓名只能展示，不能作为唯一合并依据。 |

## 5. 生命周期标准字段

| 字段 | 含义 | 来源优先级 | 展示规则 |
|---|---|---|---|
| `customerId` | 生命周期统一客户 ID | 合并 ID > studentId > leadId > courtId > membershipAccountId | 内部字段，不直接展示。 |
| `displayName` | 姓名 | 学员/订场/会员/线索中最新可信值 | 页面展示为“姓名”。 |
| `phone` | 主手机号 | 标准化手机号 | 页面展示为手机号，缺失显示为空状态。 |
| `source` | 来源 | 线索来源优先，其次学员/订场来源 | 必须映射统一来源字典。 |
| `campus` | 归属校区 | 线索分配校区/客户主校区/业务发生校区按页面场景取值 | 页面必须标明归属校区或业务发生校区。 |
| `owner` | 负责人 | 线索负责人/学员负责人/账号数据范围 | 不得用教练名替代运营负责人。 |
| `leadStage` | 线索阶段 | 线索事实和跟进记录 | 用于线索池和转化分析。 |
| `studentStage` | 学员阶段 | 体验证据、购买证据、权益证据 | `trial` 为普通学员，`formal` 为正式学员。 |
| `courtStage` | 订场阶段 | 订场历史和消费历史 | 用于订场用户。 |
| `membershipStatus` | 会员状态 | 会员账户和会员订单 | 用于会员管理。 |
| `hasTrialExperience` | 是否有体验 | 排课/反馈/线索预约 | 用于普通学员和转化漏斗。 |
| `hasCourseDeal` | 是否课程成交 | 有有效购买记录 | 用于正式学员和成交指标。 |

## 6. 当前视图分层规则

| 视图 | 进入条件 | 退出条件 | 禁止项 |
|---|---|---|---|
| 线索池 | 有线索记录，且未被明确隐藏/作废 | 成交、流失或转入下游后不再作为普通未处理线索 | 不得因为同手机号已有学员就丢失线索历史。 |
| 普通学员 | 有体验预约/体验记录/学员档案，但没有有效课包成交 | 产生有效课程购买后进入正式学员 | 不得展示课程成交作为普通学员主指标。 |
| 正式学员 | 有有效购买记录或有效权益账户 | 购买/权益全部作废时按历史规则退出当前正式视图 | 不得只看 `students` 类型字段判断正式。 |
| 订场用户 | 有订场账户或订场历史 | 账户作废或仅历史保留时按订场页规则展示 | 不得当作独立自然人重复统计。 |
| 会员用户 | 有会员账户或会员订单 | 会员账户作废/过期按会员规则展示 | 不得脱离订场用户和客户生命周期。 |

## 7. 页面影响范围

| 页面 | 使用方式 | 验收重点 |
|---|---|---|
| 线索池 | 顶部指标、列表、详情、转化按钮 | 与转化与留存同源。 |
| 普通学员 | 当前普通学员列表和详情 | 不漏掉已约体验但未正式成交客户。 |
| 正式学员 | 当前正式学员列表、课包、权益、上课记录 | 与购买记录、权益账户一致。 |
| 订场用户 | 客户资料、订场消费、会员入口 | 与会员管理同一自然人。 |
| 会员管理 | 会员账户、订单、权益流水 | 与订场用户和财务一致。 |
| 经营分析 | 转化、留存、来源、渠道效率 | 与线索池和学员页同指标。 |
| 教练端 | 本人课程、本人成员 | 只按教练授权范围读取，不扩展全量客户。 |

## 8. 写入规则

| 动作 | 写入对象 | 生命周期处理 |
|---|---|---|
| 新增线索 | `ft_leads` | 生成或关联生命周期客户。 |
| 转普通学员 | `ft_students` + 关联字段 | 保留 `sourceLeadId`，来源/校区/负责人继承线索。 |
| 购买课包 | `ft_purchases` + `ft_entitlements` | 客户进入正式学员当前视图。 |
| 新增订场用户 | `ft_courts` | 按手机号或显式关联进入同一客户。 |
| 开会员/续充 | `ft_membership_accounts` + `ft_membership_orders` | 会员身份挂到订场/客户生命周期。 |
| 人工合并 | 合并关系记录 | 以后所有页面优先使用合并结果。 |

## 9. 删除、作废和历史兼容

- 删除应优先做业务作废或隐藏，不能直接破坏历史链路。
- 历史字段如 `leadId/fromLeadId` 只能映射到统一字段，不得继续扩散到新页面。
- 空手机号客户不能被姓名误合并。
- 旧学员类型字段只能作为兼容输入，当前普通/正式判断以生命周期结果为准。

## 10. 验收清单

| 编号 | 检查项 | 通过标准 |
|---|---|---|
| CL-01 | 同手机号线索转普通学员 | 普通学员出现，来源/校区/负责人保留。 |
| CL-02 | 普通学员购买课包 | 正式学员出现，普通学员当前列表退出。 |
| CL-03 | 同人既订场又买会员 | 订场用户和会员管理展示同一姓名/手机号。 |
| CL-04 | 线索池顶部和转化与留存 | 同一时间范围下核心漏斗数字一致。 |
| CL-05 | 空手机号同名客户 | 不被自动合并。 |
| CL-06 | 历史字段兼容 | 页面展示标准字段名，不展示旧字段名。 |
