## 1. 使用规则

1. 任何新想法、页面问题、字段问题、口径问题、上线问题，先进入需求池。
2. 需求池不是执行计划；它只负责收纳和澄清。
3. 进入开发前，必须把需求拆到具体 PRD 文件：页面需求进 08，数据模型进 09，字段状态进 06，指标口径进 05，技术上线进 07。
4. 如果需求影响财务、权益、会员、订场、排课完成、生产数据，默认标记为高风险。
5. 需求进入 Roadmap 后，需求池状态改为“已进入 Roadmap”，并关联 Roadmap 阶段编号。

## 2. 需求池字段标准

| 字段 | 必填 | 说明 |
|---|---|---|
| 编号 | 是 | REQ-001 格式，永久不复用。 |
| 需求/问题 | 是 | 用业务语言说明要解决什么。 |
| 来源 | 是 | 用户提出、运营反馈、测试发现、线上事故、代码审计等。 |
| 影响端 | 是 | 管理后台、教练 Web、教练小程序、约球小程序、外部触点。 |
| 影响页面 | 是 | 写清具体页面或 PRD 路径。 |
| 影响对象 | 是 | 客户、线索、学员、课包、权益、排课、订场、会员、财务等。 |
| 是否影响口径 | 是 | 是/否；影响时必须更新 05/06/09。 |
| 风险等级 | 是 | 普通、高风险、财务高风险。 |
| 优先级 | 是 | P0/P1/P2/P3。 |
| 状态 | 是 | 待澄清、待评估、待排期、已进入 Roadmap、已完成、暂不做。 |
| 对应 PRD 修改位置 | 是 | 不能只写“待补”，必须写目标文件。 |
| 验收方式 | 是 | 自动测试、人工验收、数据核对、页面核对。 |
| 备注 | 否 | 记录约束、疑问、阻塞。 |

## 3. 状态定义

| 状态 | 含义 | 下一步 |
|---|---|---|
| 待澄清 | 需求还不清楚，不能评估。 | 补业务场景、角色、页面、预期结果。 |
| 待评估 | 问题清楚，但影响范围/成本/风险未评估。 | 做影响面和风险评估。 |
| 待排期 | 确认要做，但未放入 Roadmap。 | 等待版本安排。 |
| 已进入 Roadmap | 已纳入 12 的阶段计划。 | 拆具体 PRD 和验收。 |
| 已完成 | 已实现并验收。 | 记录完成日期和验证方式。 |
| 暂不做 | 当前阶段不做。 | 写清不做原因和重新评估条件。 |
