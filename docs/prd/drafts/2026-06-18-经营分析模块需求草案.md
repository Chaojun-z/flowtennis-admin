# 经营分析模块需求草案

> 日期：2026-06-18
> 目标：把球馆经营分析需求整理成可执行、可拆分、可验收的产品草案。
> 范围：管理后台新增“经营分析”模块，不单独建设外部 BI 平台。

> 2026-06-25 口径更新：
> 本文是历史需求草案，转化、留存、复购、订场会员、总成交等指标以 [FlowTennis 全平台数据口径总表](/Users/shaobaolu/Desktop/FlowTennis/flowtennis-mgmt-main/docs/FlowTennis全平台数据口径总表.md) 为准。
> 本文中的“新增线索 → 预约体验 → 体验到课 → 成交购买 → 同项目续费”等旧漏斗描述不得作为最新实现口径。

---

## 1. 总结论

经营分析模块要解决的不是“多放几个图表”，而是让管理者能稳定回答 4 个问题：

1. 这个月整体经营好不好？
2. 哪些校区、时段、场地还有空间？
3. 线索从哪里来，在哪一步流失？
4. 教练课时、体验转化、续费情况是否健康？

因此模块结构确定为 4 页：

1. 经营总览
2. 场地运转
3. 转化与留存
4. 教练与人效

暂不做：

1. 净利润
2. 成本拆解
3. 渠道投放成本
4. 获客 ROI
5. 教练产值
6. 复杂 AI 建议
7. 自定义 BI 报表平台

原因：当前没有稳定成本、渠道投入费用和完整归因数据。先做现有数据能支撑、口径能说清楚的经营分析。


原则：

1. 经营分析只读，不做业务写入。

3. 财务相关数字只读取既有可信口径，不在本模块重写财务规则。
4. 所有指标必须能追溯到原始业务数据。

## 3. 全局口径

### 3.1 时间口径

1. 今日：按北京时间当天。
2. 本周：按自然周。
3. 本月：按自然月。
4. 自定义：用户选择开始日期和结束日期。

### 3.2 场地时间口径

默认配置：

1. 营业时间：06:00-22:00。
2. 黄金时段：16:00-22:00。
3. 非黄金时段：06:00-16:00。
4. 内部占用：算场地占用，不算收入。
5. 取消/退款：不算有效使用。

后续可扩展为按校区配置不同营业时间和黄金时段。

### 3.3 漏斗口径

```text
新增线索 → 预约体验 → 体验到课 → 成交购买 → 同项目续费
```

定义：

1. 新增线索：线索表在筛选时间内新增。
2. 预约体验：线索状态为已约体验，或有体验课时间。
3. 体验到课：线索状态为体验课完成，或存在对应体验课上课记录。
4. 成交购买：该学员产生有效购买记录。
5. 同项目续费：同一学员再次购买同一个课程/课包。

不计入成交：

1. 作废购买。
2. 退款购买。
3. 删除购买。

### 3.4 课程类型口径

按现有课程/课包名称和已有字段归类：

1. 成人1v1
2. 成人1v2
3. 成人团课
4. 青少年
5. 体验课
6. 其他

归类规则要集中维护，不能分散写在多个页面里。

### 3.5 同项目续费口径

1. 买 A 后再次买 A，算 A 的续费。
2. 买 A 后买 B，暂不计入续费。
3. 如果历史数据无法明确判断 A 与 A 是否同项目，先不强行计入。

### 3.6 教练工时口径

1. 每个教练每天可排 8 小时。
2. 每个教练每周工作 6 天，休息 1 天。
3. 今日可排工时：8 小时。
4. 本周可排工时：48 小时。
5. 本月可排工时：当月自然天数 × 8 × 6 / 7。
6. 自定义时间可排工时：单日按 8 小时；多日按筛选天数 × 8 × 6 / 7。

说明：

1. 当前不按每位教练真实排班表计算。
2. 当前不区分个人固定休息日。
3. 先用统一折算口径，保证简单、稳定、可解释。

目标：看出哪个校区、哪个时段、哪片场地有空间。

### 5.1 页面草图

```text
场地运转
────────────────────────────────────────

┌──────┬──────┬──────┬──────┬──────────┐

├──────┼──────┼──────┼──────┼──────────┤
│ A校区 │ ¥xx  │ xxh  │ xx%  │ xx%      │
│ B校区 │ ¥xx  │ xxh  │ xx%  │ xx%      │

- 哪些校区非黄金时段空闲多
```

### 5.2 指标清单

必须展示：

1. 校区场地收入
2. 已用场时
3. 可售场时
4. 综合利用率
5. 黄金时段利用率
6. 非黄金时段利用率
7. 场地热力图

可选展示：

1. 校区环比变化
2. 内部占用场时

### 5.3 计算规则

```text
可售场时 = 场地数量 × 营业小时数 × 筛选天数

已用场时 = 有效订场场时 + 内部占用场时

场地利用率 = 已用场时 / 可售场时

黄金时段利用率 = 黄金时段已用场时 / 黄金时段可售场时

非黄金时段利用率 = 非黄金时段已用场时 / 非黄金时段可售场时
```

### 5.4 数据来源

1. 场地账户/订场流水：`ft_courts.history`。
2. 场地基础配置：现有校区、场地名称、价格方案；不足部分新增只读配置。
3. 内部占用：订场流水中的内部占用类型。

### 7.2 指标清单

必须展示：

1. 在职教练数
2. 实际授课小时
3. 可排工时
4. 工时利用率
5. 体验课数量
6. 体验课转化率
7. 同项目续费率或同项目续费人数

不展示：

1. 教练产值
2. 教练收入排名
3. 销售归因产值

### 7.3 计算规则

```text
实际授课小时 = 有效排课时长合计

可排工时 = 筛选天数 × 8 × 6 / 7

工时利用率 = 实际授课小时 / 可排工时

体验课转化率 = 该教练体验课成交人数 / 该教练体验课到课人数

同项目续费率 = 该教练名下同项目续费人数 / 该教练名下到期或已完成首购项目人数
```

注意：

1. 第一版不做教练产值。
2. 如果续费分母暂时不稳，先展示同项目续费人数和占比说明。
3. 体验课归因优先按体验课授课教练。
4. 续费归因：买了 A，又续费 A，算 A 项目的续费；跨项目续费不纳入第一版。

### 7.4 数据来源

1. 教练：`ft_coaches`。
2. 排课：`ft_schedule`。
3. 体验课：排课课程类型、线索体验字段。
4. 购买：`ft_purchases`。
5. 课程/课包：`ft_packages`、历史兼容课程字段。

## 8. 后端接口建议

新增只读接口：

```text
GET /api/page-data/operations
```

建议返回结构：

```text
{
  filters: {
    range,
    campus,
    courseType
  },
  overview: {},
  courts: {},
  conversion: {},
  coaches: {},
  meta: {
    generatedAt,
    metricVersion,
    warnings: []
  }
}
```

原则：

1. 后端集中计算经营指标。
2. 前端只负责展示。
3. 不新增生产写入口。
4. 不修改现有财务聚合口径。
5. 如果某个指标数据不足，接口返回 `warnings`，页面显示“口径待补”或隐藏该指标。

### 8.1 后端代码边界

经营分析后端不能继续把大段逻辑塞进 `api/index.js`。

建议文件边界：

```text
server/page-data/operations-page.js
server/metrics/operations-metrics.js
```

职责划分：

1. `api/index.js`：只负责挂载路由。
2. `server/page-data/operations-page.js`：负责接收请求、读取筛选参数、返回页面数据。
3. `server/metrics/operations-metrics.js`：负责经营指标计算。
4. 财务收入相关只复用现有财务读模型或财务快照能力，不复制一套新算法。

禁止事项：

1. 禁止把经营分析指标计算散写在 `api/index.js`。
2. 禁止改购买、权益、会员、订场写入逻辑。
3. 禁止改财务核心口径。
4. 禁止为了经营分析顺手重构 `courts.js`、`coachops.js`、财务核心逻辑。

## 9. 前端页面建议

新增管理后台一级页面：

```text
经营分析
```

页面内部 4 个 Tab：

1. 经营总览
2. 场地运转
3. 转化与留存
4. 教练与人效

设计原则：

1. 不做炫酷大屏。
2. 风格跟现有后台一致。
3. 先保证数据清楚、表格可读、筛选稳定。
4. 热力图只用于场地时段，不扩展成复杂 BI 图表系统。
5. 管理提示必须是规则型提示，不写夸张结论。

### 9.1 图表与表格组件选型

图表统一使用 Apache ECharts。

必须使用 ECharts 的图表能力：

1. 漏斗图：用于转化与留存。
2. 热力图：用于场地分时段利用率。
3. 柱状图：用于收入结构、多校区对比。
4. 折线图：用于本月趋势。
5. 散点图：保留给后续教练分布分析，不作为第一版必须项。

禁止事项：

1. 禁止手写漏斗图、热力图、柱状图、折线图。
2. 禁止为了经营分析引入 React/Tailwind dashboard 组件库。
3. 第一版不引入 AG Grid。
4. 第一版不做自定义拖拽 BI。

表格处理：

1. 第一版优先复用现有后台标准表格。
2. 如果后续需要大数据虚拟滚动、列冻结、复杂排序、下载等高级表格能力，再评估 Tabulator。
3. 经营分析第一版不因为表格能力引入新的前端框架。

### 9.1.1 前端代码边界

ECharts 不能直接散写在经营分析页面里。

建议新增全局图表组件层：

```text
public/assets/scripts/standard/charts.js
```

组件层职责：

1. 封装 ECharts 初始化、销毁、resize。
2. 封装折线图。
3. 封装柱状图。
4. 封装漏斗图。
5. 封装热力图。
6. 预留散点图。

经营分析页面职责：

1. 调用标准图表组件。
2. 组合指标卡、图表、表格。
3. 不自己手写图表。
4. 不重写现有标准表格。
5. 不修改其他业务页面。

4. 财务总览、收款流水、入账流水、教练结算等原入口不动。
5. 教练管理、校区管理、价格方案、账号管理等原入口不动。

### 9.3 财务模块关系

财务模块不合并进经营分析。

定位区别：

1. 财务中心：账务核对、收款流水、入账流水、教练结算，是财务人员核账工具。
2. 经营分析：收入结构、转化、场地、教练利用，是管理者看经营趋势和经营问题的工具。

融合方式：

1. 经营总览可以读取财务中心已有可信收入口径。
2. 经营分析不重新定义总收入、课程收入、场地收入、会员储值。
3. 经营分析里的收入数字必须能和财务中心追溯一致。
4. 财务中心保留独立入口，不能被经营分析替代。
5. 如果经营分析和财务中心数字不一致，必须优先停止上线并排查口径，不允许用经营分析新口径覆盖财务口径。

## 10. 与线索池改造的关系

线索池口径升级已在 `cab7b6f fix: unify lead stage display` 落到主干，内容包括：

1. 线索成交后不删除、不移走，只更新统一字段“线索阶段”。
2. 线索池列表不再显示“跟进状态 / 是否转化 / 转化类型”三套容易打架的字段。
3. 体验学员保留体验历史，即使后续已转正式。
4. 正式学员增加成交路径。
5. 学员、订场用户、会员能反查来源线索。

这项改造对经营分析是正向影响，会让“转化与留存”更准确。

### 10.1 对经营分析的影响

可以增强的指标：

1. 渠道成交数。
2. 渠道成交金额。
3. 体验转化率。
4. 直接成交数。
5. 课程转化、订场转化、会员转化拆分。
6. 成交路径：体验转化、直接成交、老客续费。
7. 线索到成交耗时。
8. 学员、订场、会员反查来源线索。

经营分析应优先复用线索池统一口径：

```text
线索阶段
student.leadId / sourceLeadId
court.leadId / sourceLeadId
membershipAccount.leadId / sourceLeadId
student.dealPath
```

说明：

1. 实际字段名以代码最终落地为准。
2. 经营分析不能自己再发明“跟进状态 / 是否转化 / 转化类型”三套重复口径。
3. 旧字段如果仍存在，只能作为兼容来源，不作为经营分析展示口径。

### 10.2 转化与留存页面更新

转化漏斗优先按“线索阶段”计算：

```text
未转化
已约体验
已体验待转化
课程转化
直接成交
订场转化
会员转化
课程+订场
课程+会员
订场+会员
已流失
```

不再单独展示：

```text
跟进状态
是否转化
转化类型
```

正式学员成交路径：

```text
体验转化
直接成交
老客续费
```

### 10.3 执行顺序建议

建议先让线索池改造上线并稳定，再做经营分析的转化与留存最终口径。

如果经营分析和线索池改造并行开发：

1. 后端经营指标先兼容旧字段。
2. “线索阶段”存在时优先用“线索阶段”。
3. 不因为经营分析反向改动线索池业务流程。
4. 经营分析只读“线索阶段”和成交路径，不负责写入这些状态。

## 14. 风险与处理

### 14.1 续费率分母风险

风险：如果“到期人数”数据不稳，续费率可能不可信。

处理：

1. 第一版优先展示同项目续费人数。
2. 续费率只有在分母口径稳定后展示。
3. 页面必须显示口径说明。

### 14.2 体验课到课口径风险

风险：线索状态和排课记录可能不完全一致。

处理：

1. 优先使用排课记录判断实际到课。
2. 线索状态作为补充。
3. 接口返回数据来源提示。

### 14.3 财务口径风险

风险：经营总览收入和财务页收入出现不一致。

处理：

1. 经营总览收入必须复用财务既有可信口径。
2. 不允许本模块重新定义财务收入。
3. 有差异时不得上线为“正式口径”。

### 14.4 线索池并行改造风险

风险：经营分析开发时，线索池字段还在变化。

处理：

1. 经营分析先通过适配层读取字段。
2. 不在页面代码里直接散落字段判断。
3. 线索池字段稳定后，再收敛适配逻辑。
4. 不因为经营分析修改线索池写入流程。

## 15. 最终产品判断

这不是一个半成品看板，而是一个轻量、正式的经营分析模块。

它的价值不在图表数量，而在：

1. 口径统一。
2. 数据可信。
3. 老板能看总览。
4. 运营能看转化。
5. 店长能看场地。
6. 教学负责人能看教练课时和续费。

当前版本用现有数据可以支撑主体功能；成本、净利润、渠道投入和教练产值等数据不足的部分先不做。
