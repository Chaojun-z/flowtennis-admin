# 多校区权限写入校验第一阶段方案

> 线程：F3 多校区与权限写入校验方案  
> 日期：2026-06-14  
> 范围：只读本地代码与文档后整理方案；不改代码；不改权限逻辑；不连接线上。

---

## 1. 第一阶段目标

第一阶段只解决一个问题：有校区范围的管理账号，不能通过接口写入、修改、删除自己无权管理校区的数据。

本阶段不重做完整权限体系，不新增复杂岗位矩阵，不做财务只读角色，不调整现有业务口径。

---

## 2. 第一阶段角色只保留哪些

第一阶段只保留 3 类角色口径：

| 角色 | 现有字段表达 | 可见范围 | 写入原则 |
| --- | --- | --- | --- |
| 总部管理员 | `role=admin` + `dataScope=all` | 全部校区 | 可做全局管理和高风险操作 |
| 校区管理员 | `role=admin` + `dataScope=campus` + `campusIds` | 指定校区 | 只能写自己 `campusIds` 范围内的常规业务数据 |
| 教练 | `role=editor` + `dataScope=coach` | 本人相关数据 | 第一阶段不开放管理端业务写入 |

暂不启用：

- 财务只读
- 运营
- 合伙人
- 自定义权限点矩阵
- 新 `roleKey`

原因：当前系统已有 `admin/editor + dataScope/campusIds`，第一阶段应先补写入边界，避免一边换角色体系、一边改写接口导致爆炸。

---

## 3. 校区管理员能写哪些数据

校区管理员只允许写“明确归属自己校区”的常规业务数据：

| 数据域 | 可写范围 | 必须满足 |
| --- | --- | --- |
| 学员 | 新增、编辑、删除本校区学员 | 学员自身或关联排课、购买、课包能推导出的校区，必须落在当前用户 `campusIds` 内 |
| 排课 | 新增、编辑、取消本校区排课 | `schedule.campus` 必须在当前用户 `campusIds` 内；编辑时旧记录和新记录都要校验 |
| 班次 | 新增、编辑、删除本校区班次 | `class.campus` 必须在当前用户 `campusIds` 内；已有排课的班次仍走现有业务限制 |
| 购买记录 | 新增、编辑本校区购买记录 | 学员、课包、购买记录、生成的权益，至少要能归属到当前用户 `campusIds` 内 |
| 订场用户 | 新增、编辑本校区订场用户 | `court.campus` 或历史记录里目标校区必须在当前用户 `campusIds` 内 |
| 会员订单 | 给本校区订场用户开卡、续充 | 订单关联的 `courtId` / `membershipAccountId` 必须属于当前用户 `campusIds` |
| 会员权益流水 | 本校区会员权益消耗 | 关联会员账户、订场用户、订单必须属于当前用户 `campusIds` |
| 教练反馈/教练提案 | 继续沿用现有教练本人规则 | 管理端校区管理员如代操作，也必须校验排课校区 |

校区管理员第一阶段不能写：

- 账号角色、数据范围、密码重置
- 校区资料
- 全局课程产品
- 全局课包规则、课包合并、课包排序
- 会员方案
- 价格方案
- 财务流水手工调整
- 清空、替换、迁移、批量导入、批量删除、跨校区合并

---

## 4. 哪些接口必须校验目标 campus/campusIds

所有写接口必须先过“动作权限”，再过“目标校区范围”。第一阶段优先覆盖以下接口。

### 4.1 订场

| 接口 | 校验目标 |
| --- | --- |
| `POST /courts` | 新订场用户的 `campus` / `campusIds` / `history` 校区 |
| `PUT /courts/:id` | 旧订场用户校区 + 新订场用户校区 |
| `DELETE /courts/:id` | 被删除订场用户校区 |
| `POST /membership-orders` | 关联 `courtId`、会员账户、订单目标校区 |
| `PUT /membership-orders/:id` | 旧订单关联校区 + 新订单关联校区 |
| `DELETE /membership-orders/:id` | 被作废订单关联校区 |
| `PUT /membership-accounts/:id` | 会员账户关联订场用户校区 |
| `POST /membership-benefit-ledger` | 会员账户、订单、订场用户校区 |

### 4.2 学员与排课

| 接口 | 校验目标 |
| --- | --- |
| `POST /students` | 学员目标校区；如果没有显式校区，不能让校区管理员新增成“无校区” |
| `PUT /students/:id` | 旧学员可见范围 + 新学员目标校区 |
| `DELETE /students/:id` | 被删除学员可见范围 |
| `POST /students/:id/reminder-link` | 学员可见范围 |
| `POST /students/:id/reminder-settings` | 学员可见范围 |
| `POST /students/:id/reminder-unbind` | 学员可见范围 |
| `POST /schedule` | 新排课 `campus` |
| `PUT /schedule/:id` | 旧排课 `campus` + 新排课 `campus` |
| `DELETE /schedule/:id` | 被删除排课 `campus` |
| `POST /classes` | 新班次 `campus` |
| `PUT /classes/:id` | 旧班次 `campus` + 新班次 `campus` |
| `DELETE /classes/:id` | 被删除班次 `campus` |

### 4.3 课包、购买、权益

| 接口 | 校验目标 |
| --- | --- |
| `POST /purchases` | 学员校区 + 课包 `campusIds` + 生成购买/权益 `campusIds` |
| `PUT /purchases/:id` | 旧购买校区 + 新购买校区 + 关联权益校区 |
| `DELETE /purchases/:id` | 被作废购买及关联权益校区 |
| `POST /entitlements/:id/manual-adjust` | 权益、购买、课包、学员推导校区 |
| `DELETE /entitlements/:id` | 被删除权益及关联购买/学员/课包校区 |

### 4.4 单条明细读取也要补校区校验

这些不是写接口，但会绕过列表过滤，第一阶段应和写校验一起补：

| 接口 | 校验目标 |
| --- | --- |
| `GET /purchases/:id` | 购买记录推导校区 |
| `GET /membership-orders/:id` | 订单关联订场用户校区 |
| `GET /membership-accounts/:id` | 账户关联订场用户校区 |
| `GET /entitlements/:id` | 权益推导校区 |
| `GET /schedule/:id` | 排课校区 |
| `GET /courts/:id` | 订场用户校区 |
| `GET /classes/:id` | 班次校区 |
| `GET /packages/:id` | 课包 `campusIds` |

## 5. 哪些高风险操作只能总部管理员做

第一阶段以下操作只允许总部管理员做，校区管理员不能做：

| 操作 | 接口/入口 |
| --- | --- |
| 创建、更新账号 | `POST /admin/create-user`、`POST /admin/update-user` |
| 重置账号密码 | `POST /admin/reset-user-password` |
| 查看完整账号列表 | `GET /admin/users` |
| 清空测试数据 | `POST /admin/clear-test-data` |
| 替换订场数据 | `POST /admin/replace-courts` |
| 初始化批量数据 | `POST /init-data` |
| 订场导入 | `POST /courts/import` |
| 订场批量删除 | `POST /courts/batch-delete` |
| 订场合并 | `POST /courts/merge` |
| 订场历史迁移 | `POST /courts/migrate-legacy`、`POST /courts/migrate-finance-legacy` |
| 校区新增、编辑、删除 | `/campuses` 写接口 |
| 全局课程产品新增、编辑、删除 | `/products` 写接口 |
| 全局课包规则新增、编辑、删除 | `/packages` 写接口 |
| 课包合并、排序 | `POST /packages/merge`、`PUT /packages/order` |
| 会员方案新增、编辑、删除 | `/membership-plans` 写接口 |
| 价格方案新增、编辑、删除 | `/price-plans` 写接口 |
| 会员账户对账修复 | `POST /membership-accounts/reconcile` |
| 课包余额手工调整 | `POST /entitlements/:id/manual-adjust` |
| 购买记录作废 | `DELETE /purchases/:id` |
| 会员订单作废 | `DELETE /membership-orders/:id` |

说明：购买作废、会员订单作废、手工调课包余额会影响财务和权益流水，第一阶段不下放给校区管理员。

## 6. 财务只读角色第一阶段是否纳入

不纳入。

原因：

1. 财务页不是单表读取，而是由学员、购买、权益、订场、会员、排课等多张业务表聚合。
2. 只加一个“财务只读”角色，不能保证源表明细、单条接口、导出、页面聚合都安全。
3. 第一阶段目标是“写入越权止血”，财务只读属于第二阶段“页面和明细读取权限”。

第一阶段只做两件和财务有关的限制：

- 校区管理员写入的业务数据，必须限制在授权校区内，避免污染财务来源数据。
- 直接影响财务的高风险动作，先只允许总部管理员做。

## 7. 要新增哪些权限函数

建议只新增少量通用函数，先不要做完整权限引擎。

### 7.1 放在 `api/permissions.js`

| 函数 | 用途 |
| --- | --- |
| `isHeadquartersAdmin(user)` | 判断总部管理员：`admin + dataScope=all` |
| `isCampusAdmin(user)` | 判断校区管理员：`admin + dataScope=campus + campusIds非空` |
| `getAllowedCampusSet(user)` | 返回当前用户可管理校区集合；总部管理员返回特殊全量标记 |
| `userCanAccessAnyCampus(user, campusIds)` | 目标多校区有任一校区命中即可读 |
| `userCanManageAllCampuses(user, campusIds)` | 写入时要求目标所有校区都在授权范围内 |
| `assertCanManageCampusIds(user, campusIds, message)` | 不通过直接抛 `无权限操作该校区数据` |
| `assertHeadquartersAdmin(user, message)` | 高风险操作只允许总部管理员 |

### 7.2 放在 `api/index.js`

| 函数 | 用途 |
| --- | --- |
| `campusIdsForWriteTarget(row, type, refs)` | 从业务记录和关联记录推导目标校区 |
| `assertCanWriteTargetCampuses(user, row, type, refs)` | 通用写入校区校验 |
| `assertCanReadTargetCampuses(user, row, type, refs)` | 单条 GET 校区校验 |
| `assertCanWriteStudent(user, oldRow, nextRow, refs)` | 替换现有 `assertStudentWriteAccess` |
| `assertCanWriteScheduleInCampus(user, oldRow, nextRow, refs)` | 替换现有 `assertCanWriteSchedule` |
| `assertCanWriteClassInCampus(user, oldRow, nextRow, refs)` | 替换现有 `assertCanWriteClass` |
| `assertCanWriteCourtInCampus(user, oldRow, nextRow, refs)` | 订场用户新增/编辑/删除 |
| `assertCanWriteMembershipInCampus(user, target, refs)` | 会员账户、订单、权益流水 |
| `assertCanWritePurchaseInCampus(user, oldRow, nextRow, refs)` | 购买记录新增/编辑 |

校验原则：

1. 总部管理员直接通过。
2. 校区管理员必须有 `campusIds`。
3. 写入目标必须能推导出校区。
4. 新增记录不能是空校区。
5. 编辑记录必须同时校验旧记录和新记录，禁止把本校区记录改到其他校区。
6. 删除、作废、取消必须校验被操作旧记录。
7. 推导不到校区时，校区管理员默认拒绝，总部管理员可继续按原业务规则处理。

## 9. 哪些接口不能一口气改

这些接口内部副作用多，不能和基础权限函数一次性混改；必须分批、小步改：

| 接口/模块 | 不能一口气改的原因 | 建议拆法 |
| --- | --- | --- |
| `POST/PUT/DELETE /schedule` | 会写排课、权益流水、课包余额、班次课时、订场储值、财务流水、教练索引 | 先加入口校区校验；再单独补取消/删除；最后补储值和财务链回归 |
| `POST/PUT/DELETE /purchases/:id` | 会同时写购买、权益、权益索引、权益流水，作废影响财务口径 | 先新增/编辑校区校验；作废先只允许总部管理员；后续再评估是否下放 |
| `POST /membership-orders` | 会写会员账户、会员订单、订场历史、会员权益流水 | 先校验 `courtId`；再校验已有账户；最后补回滚测试 |
| `POST /membership-benefit-ledger` | 同时支持会员权益和学员权益，校区来源不同 | 先拆清楚两条来源，再加校验 |
| `POST /courts/merge` | 会改订场用户、会员账户、订单、权益流水、事件，可能跨校区 | 第一阶段只限总部管理员，不做校区下放 |
| `POST /courts/import` | 批量写入，且历史记录影响财务 | 第一阶段只限总部管理员；后续要有 dry-run 和批次审计后再谈下放 |
| `POST /courts/batch-delete` | 批量删除/归档，容易误伤财务历史 | 第一阶段只限总部管理员 |
| `/packages` 写接口、`/packages/merge`、`/packages/order` | 课包规则会影响后续购买、权益、排课消课 | 第一阶段只限总部管理员 |
| `/products` 写接口 | 产品被班次、课包引用 | 第一阶段只限总部管理员 |
| `/admin/create-user`、`/admin/update-user` | 一旦可改 `dataScope/campusIds`，就能提升权限 | 第一阶段只限总部管理员 |
| `/campuses` 写接口 | 校区本身是权限边界 | 第一阶段只限总部管理员 |

## 10. 第一阶段落地顺序

1. 新增权限基础函数和测试。
2. 先把高风险入口改成只允许总部管理员。
3. 给订场普通新增/编辑/删除补校区校验。
4. 给学员、排课、班次补校区写校验。
5. 给购买、会员订单、会员权益流水补校区写校验。
6. 给单条 GET 补校区读校验。
7. 跑权限测试、相关业务规则测试、财务门禁。

---

## 11. 验收口径

第一阶段完成后，必须能证明：

1. 校区管理员不能写其他校区数据。
2. 校区管理员不能把本校区记录改成其他校区。
3. 校区管理员不能操作无校区归属的新记录。
4. 教练不能通过管理端写接口写业务数据。
5. 高风险操作只有总部管理员能做。
6. 单条明细 GET 不能绕过列表校区过滤。
7. 权限拒绝统一返回 403，且不产生任何写入。
8. 财务、权益、排课、会员相关回归测试通过。
