# FlowTennis 自动化门禁落地方案

> 状态：部分过期
> 生效日期：2026-05-10
> 最后审查日期：2026-08-24
> 维护人：FlowTennis 项目负责人
> 唯一依据：用于理解自动化门禁建设方向；当前实际命令以 `package.json` 和 `.github/workflows/ci-guard.yml` 为准。
> 替代文档：`docs/governance/文档状态清单.md`
> 目标：把当前“主要靠文档、提示词、人工验收”的治理方式，升级成**机器自动拦截、自动审查、自动阻断**的落地方案。  
> 适用场景：当前团队几乎没有技术人力、长期依赖 AI（Codex）开发和迭代。

---

## 1. 先说结论

你现在真正缺的，不是更多规范，而是：

**让仓库自己拦错。**

也就是说，后续必须让下面这条链真正成立：

`AI 改代码 -> 机器自动检查 -> 不通过直接阻断 -> AI 继续修 -> 直到通过`

而不是：

`AI 改代码 -> 你手动验收 -> 上线后才发现又坏了`

这份文档要解决的，就是怎么把“规则”变成“自动门禁”。

---

## 2. 这份文档解决什么问题

这份文档回答 5 个问题：

1. 现在为什么靠人工验收一定会失效。
2. 自动化门禁至少要拦什么。
3. 哪些检查应该先落地。
4. 哪些检查不能依赖历史生产总数。
5. 落地顺序和验收标准是什么。

---

## 3. 为什么你现在不能再依赖人工

你的现状很明确：

- 你不懂代码
- 没有专职技术人力
- 长期依赖 AI 开发
- 系统每天真实数据都在变
- 一旦上线出错，代价很大

这意味着：

1. 你不适合承担“第一道技术审查”
2. 你也不可能每天人工对完所有口径
3. AI 不能只靠提示词自律

所以：

**必须把最重要的检查前移，变成自动化拦截。**

---

## 4. 自动化门禁的目标

当前阶段，自动化门禁不追求覆盖全世界，只追求两件事：

### 目标 1：拦住高概率事故

比如：

- 财务关键数字明显漂移
- 核心接口直接报错
- 登录链路坏掉
- 高敏感页数据加载主路径挂掉

### 目标 2：尽量不依赖人工判断

也就是说：

- 机器能判断的，就不要留给人
- AI 能从日志修复的，就不要留给你

---

## 5. 自动化门禁分三层

### 第 1 层：静态门禁

作用：

- 不跑业务，只看仓库结构和规则是否被破坏

适合检查：

1. 是否触碰高危文件
2. 是否改了受保护目录
3. 是否修改了财务相关模块但没带说明
4. 是否新增了禁止的前端做法（如散写内嵌 SVG）

### 第 2 层：核心冒烟门禁

作用：

- 以最快速度判断“系统还活着吗”

适合检查：

1. 登录接口是否正常
2. `/page-data/finance` 是否正常返回
3. `/page-data/workbench` 是否正常返回
4. 核心保存接口是否至少可调用

### 第 3 层：财务回归门禁

作用：

- 判断“这次改动有没有把财务口径带坏”

适合检查：

1. 财务 5 个关键数字
2. 财务关键样本链路
3. 关键业务事实与财务口径的一致性

---

## 6. 为什么不能只对比“当前生产总数”

这是你必须理解的一点。

你说得对：

> 系统每天都在用，数据每天都在变化，不能每次都回到历史旧数据。

这意味着自动化门禁不能写成：

`当前生产总收入必须永远等于某个历史旧数`

因为正常业务发生后，这个数本来就会变。

所以自动化必须拆成两套：

### 套路 A：固定快照回归

作用：

- 验证代码逻辑有没有变坏

方法：

- 用 staging 的固定数据快照
- 在这份固定快照上计算财务 5 个核心数
- 必须稳定等于基准

这能判断：

- 代码逻辑有没有把口径改坏

### 套路 B：生产实时监控

作用：

- 发现线上异常漂移

方法：

- 不对比固定绝对值
- 对比“日环比 / 周环比 / 结构比例 / 不变量”

比如：

- 课包收入不应突然断崖式减少 70%
- 总收入不应小于子收入合计
- 成交笔数和收入结构不应出现明显异常跳变

这能判断：

- 线上是否出现异常行为

### 结论

不能再把“历史旧总数”当作生产唯一真理。  
正确方式是：

- staging 用固定快照守逻辑
- production 用实时监控守异常

---

## 7. 当前阶段最先要落地的自动化门禁

优先级从高到低如下：

### P0：财务固定快照回归

目标：

- 在固定数据集上计算：
  - 总收入
  - 课包收入
  - 订场收入
  - 会员储值
  - 成交笔数

要求：

- 和基准严格一致
- 不一致返回失败退出码

### P0：核心接口冒烟

目标：

- 自动调用：
  - 登录
  - `/page-data/finance`
  - `/page-data/workbench`
  - 至少一个高危保存接口的 dry-run 或测试路径

要求：

- 不得出现关键 `401 / 404 / 500`

### P1：高危改动识别

目标：

- 如果本次改动触达：
  - `api/index.js`
  - `purchases`
  - `entitlements`
  - `courts`
  - `membership_orders`
  - `financial` 相关逻辑

则自动提示“必须跑财务回归”

### P1：前端标准约束检查

目标：

- 禁止新散写内嵌 SVG
- 禁止绕过标准页规则直接手写新壳

### P2：生产异常监控

目标：

- 后续上线后做实时异常告警

## 8. 自动化门禁与 GitHub Actions 的关系

### 当前最现实方案

1. 先写脚本
2. 再把脚本接进 GitHub Actions

也就是说顺序不能反：

不是先有 Actions 再想跑什么，
而是先把真正能跑的脚本写出来，再让 Actions 调它。

### 第一阶段 Actions 只做最小集

建议只做：

1. 安装依赖
2. 跑关键测试
3. 跑财务回归脚本
4. 不通过直接失败

不要一开始就做过于复杂的大流水线。

---

## 9. 为什么这套方案适合“只有 AI、没有技术人力”的场景

因为它满足你最核心的要求：

### 1. 不依赖你看代码

你只需要看：

- 通过
- 不通过
- 差异报告

### 2. 能约束 AI

AI 不一定记住规则，但它会被：

- 失败退出码
- CI 红灯
- 日志报错

强制约束。

### 3. 可持续

不是一次人工验收完就结束，而是每次改动都会重复执行。

---

## 10. 这套自动化门禁完成的标志

必须同时满足：

1. 存在真实可运行的财务回归脚本
2. 存在真实可运行的关键接口冒烟脚本
3. GitHub Actions 能自动执行它们
4. 不通过时能明确阻断
5. AI 能根据失败日志继续修复

只要少一项，都还不能叫“真正落地”。

---

## 11. 一句话结论

对你们现在这种“几乎全靠 AI 开发”的模式，最靠谱的治理方式不是继续增加提醒，而是：

**把最容易出事故的地方，全部前移成自动化门禁。**

这样以后不是靠你盯住每一次迭代，而是让仓库自己先挡住大部分错误。
