# FlowTennis `api/index.js` 高危链路解耦实施方案

> 版本：2026-05-10  
> 目标：不是立刻大重构，而是先把最容易误伤财务和生产数据的高危链路从 `api/index.js` 里拆出边界，降低 AI 改一处坏多处的概率。  
> 说明：本方案强调“先止血、再收边界、最后再拆大文件”，不走大爆炸重构。

---

## 1. 先说结论

`api/index.js` 现在最大的问题，不只是“大”，而是：

**高危写逻辑、启动副作用、业务规则、页面聚合，全堆在一个地方。**

这会导致：

1. AI 改一个需求时，很容易顺手碰到不该碰的链路
2. 财务与业务边界在代码结构上没有被真正锁死
3. 启动逻辑和修复逻辑混在正常请求路径里

所以当前阶段最现实的目标不是“立刻把 5591 行拆成完美架构”，而是：

**先把高危链路物理隔离出来，形成最基本的防腐层。**

---

## 2. 这份方案解决什么问题

这份方案重点解决：

1. 为什么 `api/index.js` 是高频事故源
2. 哪几条链路最该先拆
3. 怎么拆才不会爆炸
4. 拆完后 AI 为什么更不容易误伤财务

---

## 3. 当前最危险的 4 条链路

### 链路 1：启动副作用链

涉及：

- `init()`
- `bootstrapMabaoFinanceSeed()`
- `repairImportedLedgerDuplicates()`
- `syncDefaultPricePlans()`

问题：

- 不是普通请求处理逻辑
- 却与正常 API 生命周期混在一起

### 链路 2：教学售卖写链

涉及：

- `packages`
- `purchases`
- `entitlements`
- `entitlement_ledger`

问题：

- 购买生成权益
- 排课扣减权益
- 财务页又依赖这些结果

### 链路 3：订场 / 会员 / 财务耦合链

涉及：

- `courts`
- `membership_orders`
- `membership_accounts`
- `membership_benefit_ledger`
- `financial_ledger / courts.history`

问题：

- 主档、会员、财务互相缠绕

### 链路 4：约球反向写财务链

涉及：

- `match_*`
- `match-court-finance`

问题：

- 一个子系统反向写另一个业务域

---

## 4. 第一阶段不要做什么

为了避免重构把系统再炸一次，第一阶段明确不做：

1. 不全量重写 `api/index.js`
2. 不一次性改完所有路由
3. 不强行引入复杂事件总线
4. 不立即把所有业务都拆成微服务

---

## 5. 第一阶段真正该做什么

### Step 1：把启动副作用链剥离成独立模块

目标：

- `init()` 只保留最安全的启动职责
- bootstrap / repair 不再埋在普通请求主链里

建议拆分为：

- `server/bootstrap/init-safe.js`
- `api/ops/bootstrap-mabao-finance-seed.js`
- `api/ops/repair-imported-ledger-duplicates.js`

### Step 2：把财务口径读取与普通业务写链隔开

目标：

- 课包 / 购买 / 权益逻辑，不直接散落到财务聚合逻辑里

建议拆分为：

- `api/services/teaching-sales/*`
- `api/read-models/finance/*`

### Step 3：把 `courts` 主档写路径和财务口径读取分开

目标：

- `courts` 仍作为主档
- 但财务展示不再直接把它当万能底座

### Step 4：把约球财务同步链独立出来

目标：

- 至少让人一眼能看出：
  - 哪段是约球
  - 哪段是订场财务同步

---

## 6. 对“物理防腐层”的正式解释

Claude 和 Gemini 提到的核心点是对的：

**不能只靠提示词和规则管住 AI，必须让代码结构本身也管住 AI。**

在你们当前阶段，这里的“物理防腐层”不一定非要一步做成事件驱动全家桶，先做到下面这件事就有巨大价值：

### 让高危链路有独立文件边界

比如：

- 课包售卖逻辑在 `teaching-sales`
- 财务读模型在 `finance-read-model`
- 启动副作用在 `ops/bootstrap`

这样 AI 改课包需求时，默认只会围绕 `teaching-sales` 工作，而不是在一个 5591 行巨石里顺手碰到财务和启动逻辑。

### 第二阶段再考虑更强隔离

后续等系统稳定后，再评估：

- 事件驱动
- 凭证驱动记账
- 异步入账链

但这不应该是当前第一步。

---

## 7. 为什么这套方案比“直接大拆”更可靠

因为你们当前状态不适合理想化重构。

### 当前现实

1. 没有技术人力
2. 高度依赖 AI
3. 主干还没彻底清
4. 环境还没完全分层

这时候如果直接搞大重构，风险非常高。

### 当前更正确的做法

先做：

1. 高危链路边界隔离
2. 启动副作用剥离
3. 财务读模型独立
4. 约球同步链独立

这样是“边止血边重构”，更适合现在。

---

## 8. 这一方案完成后的效果

如果第一阶段做完，至少会带来 4 个直接收益：

1. AI 改动范围更清晰
2. 财务链路更不容易被顺手碰到
3. 启动副作用不再混在正常请求路径里
4. 后续要做财务回归和环境治理时，定位更容易

---

## 9. 一句话结论

`api/index.js` 现在最危险的不是“大”，而是“高危逻辑没有物理边界”。  
当前最优先的不是追求完美重构，而是先把：

- 启动副作用
- 教学售卖写链
- 财务读模型
- 约球财务同步链

从巨石里拆出清晰边界。  
只要这一步做了，AI 以后误伤财务和生产数据的概率就会明显下降。
