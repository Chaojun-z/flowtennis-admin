# FlowTennis dev-staging-prod 环境建设方案

> 版本：2026-05-10  
> 目标读者：技术负责人、外部架构顾问、接手开发、其他 AI  
> 文档目标：把当前“本地预览还在共用线上数据、测试环境不独立”的问题拆解清楚，并给出符合中大型 SaaS 平台标准的环境建设方案。  
> 使用场景：技术负责人需要判断“为什么必须分环境、怎么分、先做什么、做到什么程度才算合格”。

---

## 1. 先说结论

你们当前最危险的一条红线是：

**本地预览 / 测试联调 / 小程序联调，离线上真实数据和线上真实财务口径太近。**

这在合格的 SaaS 工程标准里，不是普通缺陷，而是：

**必须优先整改的架构风险。**

原因很直接：

1. 开发环境不能默认围着生产真实数据转。
2. 测试环境不能和生产财务基线共用。
3. 小程序 / PWA / Web 联调不能默认靠生产环境验证。
4. 一旦开发和测试靠生产太近，任何功能改动都更容易误伤真实数据口径。

所以：

**环境分层不是锦上添花，而是让这套系统进入健康迭代状态的必要条件。**

---

## 2. 这份文档解决什么问题

这份文档重点回答 7 个问题：

1. 为什么当前环境方式不合格。
2. 为什么“本地预览也用线上数据”是红线。
3. 合格的 SaaS 平台至少需要哪些环境层次。
4. 每层环境分别承担什么职责。
5. 这几层环境的数据应该怎么区分。
6. 如何避免“课包开发顺手把财务基线带坏”。
7. 这套方案为什么可靠。

---

## 3. 当前环境方式为什么不合格

### 3.1 当前真实现状

从当前仓库和现状来看：

1. 本地开发通过 `.env` 直接连真实 TableStore / Postgres
2. 教练端微信小程序默认请求线上 `https://www.flowtennis.cn/api`
3. 修数脚本、审计脚本、导入脚本也默认围绕同一套生产环境变量
4. 财务关键口径没有被独立环境或独立基线保护

### 3.2 这意味着什么

这意味着当前实际上缺少：

- 真正独立的开发数据环境
- 真正独立的预发布环境
- 真正受保护的生产财务基线

所以现在你们很多所谓“测试”，实际上更接近：

**围着生产环境做开发验证。**

这就是为什么风险会非常高。

### 3.3 为什么这是红线

因为在合格 SaaS 平台里：

1. `dev` 是给开发试错的，不是给生产事实背书的
2. `staging` 是给合并后验证的，不是给日常开发凑合用的
3. `prod` 是给真实用户用的，不是给功能联调用的

如果这三者不分，就会出现：

- 功能开发误伤生产数据
- 测试结论不稳定
- 线上事故在开发阶段就埋雷

---

## 4. 合格 SaaS 平台至少需要哪三层环境

最少要有：

1. `dev`
2. `staging`
3. `prod`

对你们当前阶段来说，这不是奢侈配置，而是最低合格线。

---

## 5. 每层环境的职责定义

## 5.1 `dev` 本地 / 开发环境

### 作用

- 日常开发
- UI 调试
- 普通功能联调
- 本地快速验证

### 原则

- 默认不连生产真实数据
- 默认不能改生产真实财务口径
- 允许试错
- 允许局部脏数据
- 允许快速重置

### 不该承担的职责

- 不负责验证最终上线口径
- 不负责财务基准核对
- 不负责正式验收

### 对你们现在的意义

现在最应该先把：

`本地预览 = 线上真实数据`

这条链切断。

---

## 5.2 `staging` 预发布环境

### 作用

- 合并后的集成联调
- 上线前回归
- 多端联调
- 财务快照对比
- 业务验收

### 原则

- 结构尽量接近生产
- 数据不是生产实时数据
- 允许做完整回归
- 允许财务基准校验
- 不允许长期变成第二个开发垃圾场

### 不该承担的职责

- 不用于日常无序开发
- 不用于直接修生产问题

### 对你们现在的意义

以后你要验收的，应该优先是 `staging`，不是开发者本地混合环境。

---

## 5.3 `prod` 生产环境

### 作用

- 真正承接业务使用
- 真正承接财务口径
- 真正承接用户数据

### 原则

- 不用于日常联调
- 不用于功能试错
- 不用于随手验证
- 高危写入口必须关闸
- 财务口径必须冻结守护

### 对你们现在的意义

`prod` 必须重新定义为：

- 只用来正式运行
- 不再成为开发和测试的默认依赖面

---

## 6. 为什么光有三层环境还不够

因为你们现在的问题里，“财务”是特殊高风险域。

所以除了 `dev / staging / prod` 之外，还必须再加一个概念：

## 6.1 财务基线

财务基线不是第四套完整环境，而是：

**一套冻结的、可比对的、不能被普通需求随意共用改口径的财务标准。**

### 财务基线至少包括

1. 一份关键数字基准文件
2. 一套生成这些数字的固定脚本 / 接口
3. 一套发布前对比规则

### 为什么财务基线必须单独存在

因为你们当前最大事故类型不是“功能按钮坏了”，而是：

- 课包改动导致财务口径漂移
- 页面改动导致收入数字不一致

这类事故不能只靠 `staging` 环境本身防住，必须靠：

**环境 + 基准双重守护。**

---

## 7. 各环境的数据应该怎么分

这是最关键的一部分。

### 7.1 `dev` 数据

建议来源：

- 测试种子数据
- 脱敏样本数据
- 手工构造场景数据

必须满足：

1. 不能默认读生产真实数据
2. 可以快速清空重建
3. 可以故意制造异常场景做测试

### 7.2 `staging` 数据

建议来源：

- 脱敏后的生产快照
- 固定版本的业务验证数据集

必须满足：

1. 数据规模接近真实
2. 但不是真实生产实时数据
3. 财务关键数字可对照
4. 能重复回归

### 7.3 `prod` 数据

特点：

- 真实用户
- 真实财务
- 真实业务

要求：

- 只接受正式发布写入
- 修数必须单独流程

---

## 8. 当前最应该先切断的三条危险链

### 危险链 1：本地开发直连生产

这条必须先断。

### 危险链 2：小程序默认直连线上

至少要能区分：

- 开发版小程序
- 预发布验证版
- 正式版

### 危险链 3：脚本默认读生产 `.env`

修数 / 审计 / 导入脚本必须显式区分环境，而不是默认拿生产配置。

---

## 9. 对当前几个端的环境要求

你们现在不是单端，所以每个端都要讲清楚。

### 9.1 管理后台 Web

要求：

- 本地开发默认连 `dev`
- 预发布验收连 `staging`
- 正式线上只连 `prod`

### 9.2 教练端 Web

要求：

- 和管理后台共享同一套后端分层
- 不能因为是“教练视图”就跳过环境治理

### 9.3 教练端 PWA

要求：

- 本质是 Web 外壳，环境策略必须跟 Web 保持一致
- 不能因为安装成 PWA 就偷偷继续连生产调试

### 9.4 教练端微信小程序

要求：

- 开发版连 `dev` 或专用小程序测试 API
- 预发布版连 `staging`
- 正式版连 `prod`

### 9.5 约球小程序 / 约球子系统

要求：

- Postgres 也必须有 `dev / staging / prod`
- 不允许约球开发直接围着生产财务同步链调

---

## 10. 为什么这样能避免“改课包把财务改坏”

这是最关键的业务解释。

因为现在这类事故背后，实际是三件事叠在一起：

1. 课包功能和财务页共享部分底层来源
2. 测试和验证离生产口径太近
3. 发布前没有固定财务基准对比

环境分层后，会发生什么变化：

### 在 `dev`

- 你可以改课包
- 可以改购买
- 可以改权益
- 但默认不应该把 `prod` 财务基线带着一起跑

### 在 `staging`

- 你验证功能
- 顺便用冻结财务基准做对比
- 一旦数漂了，先停

### 在 `prod`

- 只有正式发布后才允许进入
- 不再承担开发和试错职能

这就是为什么环境分层不是形式主义，而是真能降低事故率。

---

## 11. 环境建设的现实推进顺序

这件事不能幻想一周内全部完美完成，要分阶段。

### Phase 1：止血

目标：

- 本地预览不再默认直连生产真实数据
- 修数脚本不再默认拿生产环境

优先动作：

1. 拆本地 `.env`
2. 拆生产 `.env`
3. 给脚本增加环境显式选择

### Phase 2：建立 `staging`

目标：

- 上线前有一个统一验收环境

优先动作：

1. 独立一套 staging 部署
2. 独立 staging 数据源
3. 小程序 / PWA / Web 都能接到 staging

### Phase 3：建立财务基准守护

目标：

- 任何影响财务页的改动，发布前都能比对

优先动作：

1. 冻结关键数值基准
2. 建立对比脚本
3. 把对比放进发布前流程

### Phase 4：制度化

目标：

- 把环境分层变成常态，而不是一次性项目

优先动作：

1. 写进团队规则
2. 写进 AI 协作规则
3. 写进发布 checklist

---

## 12. 环境建设完成的验收标准

环境分层不是“看起来有三套配置”就算完成。

必须同时满足：

1. 本地开发默认不再连生产真实数据
2. staging 可独立完成完整验收
3. Web / PWA / 教练小程序 / 约球都能区分环境
4. 生产环境不再承担开发试错
5. 修数脚本默认不再直接指向生产
6. 财务关键数字有冻结基准
7. 发布前能在 staging 做财务对比

只要这 7 条里有 2~3 条做不到，就不能说环境建设完成。

---

## 13. 为什么这份方案是可靠的

它可靠的原因，不是因为“听起来规范”，而是因为它直接针对了你们当前事故的根因：

### 根因 1：开发环境离生产太近

方案通过 `dev/staging/prod` 分层处理。

### 根因 2：财务基线没有独立保护

方案通过“环境 + 财务基准”双重守护处理。

### 根因 3：多端共用后端导致联调成本高

方案通过“每个端都接入环境分层”处理。

### 根因 4：修数脚本和开发混流

方案通过“脚本环境显式化、默认不生产”处理。

所以这不是空谈“要规范”，而是能实际降低事故概率的方案。

---

## 14. 一句话结论

如果不把环境分层做起来，你们后面再怎么补测试、补流程、补文档，都会继续被下面这条根问题拖住：

**开发、测试、预发布、生产，当前没有被真正切开。**

而对一个要长期演进、还要走 SaaS 化的平台来说，这条问题不解决，后面所有健康迭代目标都不成立。
