# 财务独立台账第一阶段方案

> 版本：2026-06-14  
> 范围：只设计第一阶段，不改代码、不改财务口径、不切换财务页来源、不连接线上。

---

## 1. 第一阶段目标

第一阶段不是重做财务页。

目标只有一个：

```text
在现有财务页继续稳定运行的前提下，新增一套旁路财务流水和读模型，用来和旧口径并行对账。
```

第一阶段完成后：

1. 业务动作仍按现有逻辑写业务表。
2. 财务页仍按现有 `/page-data/finance` 快照展示。
3. 新财务流水只做影子账和对账。
4. 只有连续对账稳定后，后续阶段才讨论页面切换。

---

## 2. 当前财务页依赖哪些业务表

当前财务页入口是：

```text
GET /page-data/finance
```

后端会把多张业务表拼成 `financeNormalizedRows`，前端再用这批统一行展示：

- 财务总览
- 收款流水
- 入账流水
- 教练结算

当前主要依赖如下。

| 表 | 当前用途 |
|---|---|
| `ft_purchases` | 课包购买收款，形成课程实收和课包待确认收入 |
| `ft_entitlements` | 找到购买对应课包、总课时、剩余课时、校区归属，用于计算课包消耗确认收入 |
| `ft_entitlement_ledger` | 课包扣课、退回、历史导入消耗流水，形成课程已入账 |
| `ft_schedule` | 直接收款课程、课程补差、排课消课来源、教练结算来源 |
| `ft_courts.history` | 会员储值、会员订场、散客订场、约球订场、退款、冲正的主要财务来源 |
| `ft_membership_orders` | 会员充值/开卡订单；当前会避开已落在 `courts.history` 里的重复会员订单 |
| `ft_membership_accounts` | 当前接口会加载，用于会员范围过滤和储值余额核对链路；不应作为财务确认收入的唯一来源 |
| `ft_students` | 学员姓名、校区、课包归属辅助信息 |
| `ft_campuses` | 校区编码到校区名称的解析 |
| `ft_users` | 操作人姓名标准化 |

当前还有一个历史/备用路径：

```text
financeLegacyUnifiedRows()
```

它在前端本地兜底使用，逻辑是：

1. 如果本地已有 `financialLedger`，优先转成财务行。
2. 否则继续从 `purchases / entitlements / entitlement_ledger / courts.history` 拼行。

但正常打开财务页时，前端优先使用后端 `/page-data/finance` 返回的 `financeNormalizedRows`，所以现在并不是纯读 `ft_financial_ledger`。

## 3. 哪些业务动作应该生成财务流水

第一阶段建议只覆盖已经影响财务页的动作，不扩展新业务。

| 业务动作 | 旧业务表变化 | 新财务流水动作 |
|---|---|---|
| 课包购买 | 新增 `ft_purchases`，新增/更新 `ft_entitlements` | `package_receipt`：实收增加，待确认增加 |
| 课包作废 | `ft_purchases.status=voided`，权益作废 | `package_void` 或冲正：冲回未生效收款；已有消耗时第一阶段不自动处理 |
| 排课消课 | 新增/更新 `ft_schedule`，写 `ft_entitlement_ledger`，减少 `ft_entitlements.remainingLessons` | `lesson_consume`：已确认收入增加，待确认减少 |
| 取消/退回消课 | 写 `ft_entitlement_ledger` 回退，恢复权益 | `lesson_return`：已确认收入减少，待确认增加 |
| 手工课包扣减/退回 | 写 `ft_entitlement_ledger`，更新 `ft_entitlements` | `manual_lesson_consume` / `manual_lesson_return` |
| 直接收款课程 | `ft_schedule` 上有直接收款金额 | `direct_course_receipt`：实收增加，已确认收入增加 |
| 课程补差/场地费补差 | 当前已有 `ft_financial_ledger` 写入痕迹 | `course_surcharge`：实收增加，已确认收入增加 |
| 会员储值/开卡/续充 | `ft_membership_orders`、`ft_membership_accounts`、`ft_courts.history` | `membership_recharge`：实收增加，待确认增加 |
| 会员储值订场扣款 | `ft_courts.history` 消费，会员余额减少 | `member_booking_consume`：已确认收入增加，待确认减少 |
| 散客订场现场收款 | `ft_courts.history` 消费 | `guest_booking_receipt`：实收增加，已确认收入增加 |
| 订场退款 | `ft_courts.history` 退款 | `booking_refund`：按支付方式冲减实收/已确认/待确认 |
| 订场冲正 | `ft_courts.history` 冲正 | `booking_reversal`：生成反向流水，不改原流水 |
| 约球收款同步 | Postgres 约球分摊同步到 `match-court-finance` 的 `courts.history` | `match_fee_sync`：实收增加，已确认收入增加 |
| 约球退款同步 | 约球退款同步到 `courts.history` | `match_refund_sync`：实收减少，已确认收入减少 |
| 会员权益核销 | `ft_membership_benefit_ledger` | 第一阶段只记录业务权益流水；是否进入财务确认，必须按券/权益是否有实收来源单独评审 |

第一阶段不建议把“赠送、补偿、内部占用、教练结算、平台手续费”一次纳入财务主账。它们规则差异大，应该先作为异常/备注明细对账。

## 4. 财务流水最小字段

第一阶段建议继续统一到一张表：

```text
ft_financial_ledger
```

最小字段必须够用，但不要一次做复杂会计科目。

| 字段 | 说明 |
|---|---|
| `id` | 流水唯一 ID |
| `ledgerVersion` | 读模型版本，例如 `finance-ledger-v1` |
| `status` | `active` / `voided` / `reversed` |
| `businessDate` | 业务发生日期时间，用于财务归属 |
| `createdAt` | 系统写入时间 |
| `updatedAt` | 更新时间 |
| `operationId` | 单次操作 ID |
| `batchId` | 批次 ID |
| `operationType` | 操作类型，例如 `package-purchase` |
| `operationBy` | 操作人 |
| `campus` / `campusName` | 校区 |
| `userType` | `student` / `court_user` / `guest` / `match_user` |
| `userId` | 用户 ID |
| `userName` | 用户名称快照 |
| `businessType` | `课程` / `会员储值` / `会员订场` / `散客订场` / `约球局` |
| `actionType` | `收款` / `消耗` / `退款` / `冲正` / `作废` |
| `ledgerType` | 更细类型，例如 `package_receipt`、`lesson_consume` |
| `sourceType` | 来源单据类型，例如 `purchase`、`schedule`、`court_history` |
| `sourceId` | 来源单据 ID |
| `sourceSubId` | 来源子记录 ID，例如 `courts.history.id` |
| `paymentChannel` | 支付方式 |
| `paymentStatus` | `success` / `pending` / `failed` |
| `cashDelta` | 实收变化，单位必须用“分”，收款为正，退款为负 |
| `recognizedRevenueDelta` | 已确认收入变化，单位必须用“分” |
| `deferredRevenueDelta` | 待确认收入变化，单位必须用“分” |
| `entitlementDelta` | 权益变化，可选，例如课时 `-1`、储值 `-24000` |
| `productSnapshotName` | 商品/课包/会员方案名称快照 |
| `sourceSnapshot` | 最小业务快照，只放对账必要字段 |
| `idempotencyKey` | 幂等键，防止重复生成流水 |
| `reversalOfLedgerId` | 冲正指向原流水 |
| `notes` | 备注 |

金额硬规则：

1. 财务流水内金额一律用“分”的整数。
2. 财务页展示时再转成“元”。
3. 新台账读模型必须和旧财务页目前展示口径保持一致，第一阶段不能借机改算法。

## 5. 新旧财务口径如何并行比对

第一阶段采用“双轨并行”。

### 5.1 旧口径

旧口径继续是当前正式口径：

```text
业务表 -> buildFinancePageSnapshot() -> financeNormalizedRows -> 财务页
```

旧口径负责线上展示，不能动。

### 5.2 新口径

新口径只做旁路：

```text
业务动作 -> ft_financial_ledger -> finance_ledger_read_model -> 对账报告
```

新口径不服务财务页，只输出对账结果。

### 5.3 对账维度

每天或每次操作后，对比以下指标：

| 指标 | 旧口径来源 | 新口径来源 |
|---|---|---|
| 总实收 | `financeNormalizedRows.cashDelta` 汇总 | `ft_financial_ledger.cashDelta` 汇总 |
| 总核销确收 | `recognizedRevenueDelta` 汇总 | `recognizedRevenueDelta` 汇总 |
| 待确认收入 | `deferredRevenueDelta` 汇总 | `deferredRevenueDelta` 汇总 |
| 课程实收 | 课程收款行 | 课程类流水 |
| 课程已入账 | 课程消耗/直接课收款确认 | 课程类确认流水 |
| 会员储值实收 | 会员储值收款行 | 会员储值流水 |
| 会员耗卡核销 | 会员订场储值扣款行 | 会员订场消耗流水 |
| 散客/约球订场 | `courts.history` 订场行 | 订场流水 |
| 流水条数 | 旧规范化行数 | 新读模型行数 |
| operationId 覆盖率 | 旧规范化行是否带追踪字段 | 新流水是否带追踪字段 |

### 5.4 允许差异的处理

第一阶段差异不能直接改账，只能分类。

| 差异类型 | 处理方式 |
|---|---|
| 历史期初差异 | 标记为 `opening_balance_gap`，不追写历史明细 |
| 旧导入白名单增量 | 标记为 `verified_import_increment`，保留旧口径 |
| 缺少来源单据 | 标记为 `missing_source`，进入异常报告 |
| 重复流水 | 标记为 `duplicate_idempotency_key`，禁止进入新读模型有效汇总 |
| 金额尾差 | 标记为 `rounding_gap`，必须能追到具体课包或订单 |
| 业务表有、台账无 | 标记为 `ledger_missing`，只报警不自动补写 |
| 台账有、业务表无 | 标记为 `source_missing`，只报警不展示给财务页 |

### 5.5 通过标准

第一阶段不以“新口径完全替代旧口径”为验收。

建议通过标准：

1. 核心五个数连续 7 天与旧口径一致，或差异都有明确白名单。
2. 新增业务动作的 `operationId / batchId` 覆盖率为 100%。
3. 新台账没有重复幂等键。
4. 每一条新流水都能回查到来源业务单。
5. 对账报告能指出差异来自哪张表、哪条业务记录。

## 6. 第一阶段哪些页面不切换，只做对账

以下页面第一阶段全部不切换数据来源。

| 页面 | 第一阶段处理 |
|---|---|
| 财务总览 | 不切换，仍使用 `/page-data/finance` 的旧快照 |
| 收款流水 | 不切换，仍使用 `financeNormalizedRows` |
| 入账流水 | 不切换，仍使用 `financeNormalizedRows` |
| 教练结算 | 不切换，仍使用 `schedule` 聚合结果 |
| 订场用户页 | 不切换，仍读 `ft_courts` |
| 会员管理页 | 不切换，仍读会员账户、会员订单、会员权益流水 |
| 购买记录页 | 不切换，仍读 `ft_purchases` |
| 课包余额页 | 不切换，仍读 `ft_entitlements` |
| 排课表 | 不切换，仍按现有排课/扣课逻辑 |
| 约球管理页 | 不切换，仍按 Postgres 约球链路和现有同步逻辑 |

第一阶段新增的只应该是：

1. 后台只读对账脚本/报告。
2. 新旧口径差异表。
3. 台账覆盖率报告。

不新增运营入口，不让运营重复录财务。

## 7. 哪些风险最高，不能一口气改

### 7.1 最高风险一：直接把财务页切到 `ft_financial_ledger`

不能做。

原因：

1. 当前财务页还有“已核对快照 + 白名单增量”的历史口径。
2. `ft_financial_ledger` 目前只覆盖部分动作，不能代表全量财务。
3. 一旦直接切换，可能导致总收入、课包收入、会员储值、订场收入大幅漂移。

### 7.2 最高风险二：回填全部历史财务流水

不能一口气做。

历史数据来源混杂：

1. 私教课 CSV 导入。
2. 马坡订场/会员导入。
3. `courts.history` 历史财务。
4. `entitlement_ledger` 历史消课。
5. 已核对财务快照。

第一阶段只能做“历史期初 + 新增动作追踪”，不能把历史流水强行重建成看似完整的新总账。

### 7.3 最高风险三：同时改业务写入和财务口径

不能做。

例如：

1. 改课包购买逻辑时顺手改收入确认。
2. 改排课扣课时顺手切换财务页来源。
3. 改会员储值时顺手重算历史余额。

这些必须拆开，否则出错时无法判断是业务写错、台账写错，还是财务页聚合错。

### 7.4 最高风险四：会员储值和订场混在一起切

会员储值链路同时涉及：

1. `ft_membership_accounts`
2. `ft_membership_orders`
3. `ft_membership_benefit_ledger`
4. `ft_courts.history`
5. 财务页储值/订场口径

这里最容易出现“充值算了两次”或“储值扣款没有减少待确认”的问题。第一阶段只能旁路对账。

### 7.5 最高风险五：课包消耗按新规则重新确认收入

当前旧口径按 `amountPaid / totalLessons * lessonDelta` 计算。

第一阶段新台账必须先复刻旧口径，不能直接引入“排课结束 + 反馈后确认”等新规则。那些是未来口径升级，不属于第一阶段。

### 7.6 最高风险六：约球财务和订场财务同时改

约球在 Postgres，财务结果同步进 `ft_courts.history` 的 `match-court-finance` 账户。

第一阶段只对同步结果生成/校验旁路台账，不改约球原链路，不改订场财务页口径。

## 8. 第一阶段推荐落地顺序

1. 固定旧口径基准：用现有 `/page-data/finance` 作为旧口径输出。
2. 定义 `ft_financial_ledger` v1 最小字段和幂等键。
3. 只给新增业务动作旁路生成财务流水。
4. 建一个只读读模型，把新流水转成和 `financeNormalizedRows` 同形的行。
5. 做新旧对账报告，先对核心数字，再对明细。
6. 连续稳定后，再评估第二阶段是否把某个小页面切到新读模型。

第一阶段结束时，不应该出现任何财务页来源切换。
