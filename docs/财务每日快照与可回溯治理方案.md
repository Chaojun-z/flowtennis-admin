# 财务每日快照与可回溯治理方案

> 版本：2026-05-31  
> 目标：让每天真实经营数据可以安全变化，同时保留快速回溯、定位和恢复能力。

---

## 1. 核心结论

固定财务基线继续保留，但它只用于防止代码改坏财务口径。

真实经营每天都会产生新数据，必须用每日财务快照和操作批次来管理，不能用固定基线代表当天真实收入。

---

## 2. 两类基线

### 2.1 固定代码门禁基线

用途：

1. 校验财务算法是否被改坏。
2. 校验财务页面聚合口径是否漂移。
3. 校验代码改动没有误伤旧确认样本。

当前命令：

```bash
npm run guard:finance
```

限制：

1. 它不代表当天线上真实财务数据。
2. 它不判断今天新增订场、会员储值、买课包、消课是否正确。
3. 它不能替代生产数据快照。

### 2.2 每日经营财务快照

用途：

1. 记录每天真实经营后的安全版本。
2. 出错时快速回到上一个安全点。
3. 对比某次操作前后财务变化。

快照至少应覆盖：

1. 订场用户与订场流水：`ft_courts`
2. 会员账户：`ft_membership_accounts`
3. 会员订单：`ft_membership_orders`
4. 会员权益流水：`ft_membership_benefit_ledger`
5. 课包购买：`ft_purchases`
6. 课包余额：`ft_entitlements`
7. 课包消耗流水：`ft_entitlement_ledger`
8. 财务总览和财务流水接口返回值

---

## 3. 每次经营动作必须可追溯

以下动作必须有 `batchId` 或 `operationId`：

1. 订场流水新增、退款、冲正
2. 会员储值、续充、作废、余额清零
3. 课包购买、作废
4. 排课、取消排课、消课、退课
5. 导入、补账、修数

每个批次至少记录：

1. 操作人
2. 操作时间
3. 业务动作类型
4. 写入实例
5. 涉及表名
6. 涉及记录 ID
7. 操作前核心金额
8. 操作后核心金额
9. 财务总览变化
10. 是否通过校验

---

## 4. 操作后必须校验三段链路

任何收入或权益相关动作完成后，必须同时确认：

1. 业务表写入正确
2. 财务流水产生正确
3. 财务总览变化正确

不得只说“数据库查到了”。

当前本地校验命令：

```bash
npm run validate:finance-operation -- --before <操作前快照.json> --after <操作后快照.json> --type <动作类型> --amount <金额>
```

当前支持的动作类型：

1. `package-purchase`：买课包
2. `lesson-consume`：排课消课
3. `membership-recharge`：会员储值
4. `member-booking`：会员订场储值扣款
5. `court-booking`：散客订场现金或微信收款

### 4.1 买课包

期望变化：

1. `ft_purchases` 新增购买记录
2. `ft_entitlements` 新增或更新课包余额
3. 财务总收入增加
4. 课包收入增加
5. 未入账收入增加
6. 已入账收入不因购买本身增加

### 4.2 排课消课

期望变化：

1. `ft_schedule` 新增或更新排课
2. `ft_entitlements` 剩余课时减少
3. `ft_entitlement_ledger` 写入消课流水
4. 已入账收入增加
5. 未入账收入减少
6. 课包余额减少

### 4.3 会员储值

期望变化：

1. `ft_membership_accounts` 新增或更新会员账户
2. `ft_membership_orders` 新增会员订单
3. `ft_courts.history` 写入充值流水
4. 总收入增加
5. 会员储值收入增加
6. 未入账收入增加
7. 已入账收入不因充值本身增加

### 4.4 会员订场储值扣款

期望变化：

1. `ft_courts.history` 写入订场消费
2. 会员余额减少
3. 已入账收入增加
4. 未入账收入减少
5. 会员订场流水可追溯

### 4.5 散客订场现金或微信收款

期望变化：

1. `ft_courts.history` 写入订场消费
2. 总收入增加
3. 订场收入增加
4. 已入账收入增加
5. 未入账收入不增加

---

## 5. 恢复原则

发生异常时按以下顺序处理：

1. 先停止继续写入相关数据。
2. 先查线上 `/api/diag`，确认实例是 `flowtennis-ue`。
3. 先导出当前异常状态作为恢复前备份。
4. 优先按 `batchId` 或 `operationId` 回滚单次操作。
5. 单批次无法恢复时，再考虑恢复到每日快照。
6. 整库或整表恢复必须用户明确同意。
7. 恢复后重新核对业务页、财务接口和财务页面。

---

## 6. AI 操作纪律

AI 处理财务问题时必须遵守：

1. 不靠记忆恢复数据。
2. 不靠猜测补写财务流水。
3. 不在没有备份的情况下修数。
4. 不把固定代码基线当成当天真实财务。
5. 不把业务表写入成功当成财务生效。
6. 连续两次定位失败必须停下汇报。

---

## 7. 后续落地顺序

推荐顺序：

1. 每日自动财务快照
2. 关键经营动作生成 `batchId` / `operationId`
3. 操作后自动比对财务变化
4. 财务页升级为实时总账 + 日结快照
5. 按批次回滚

2. 每日经营快照已具备本地只读生成命令。
