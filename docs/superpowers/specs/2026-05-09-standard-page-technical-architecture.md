# 标准页组件库技术架构文档

## 1. 文档目的

本文件用于把“标准页组件库”从概念文档落到技术架构层，避免后续出现以下问题：

1. 名义上组件化，实际上复制学员页代码
2. 页面继续自己拼 HTML，只是外面套了个壳
3. 公共层和业务层职责不清
4. 后续线程各自理解不同，导致组件库失控

本文件解决的是：

1. 组件库应该怎么分层
2. 页面配置应该怎么组织
3. 什么代码必须进公共层
4. 什么代码必须留在页面层
5. 旧页面与新标准页如何共存

## 2. 架构目标

标准页组件库的技术目标不是“抽几个公共函数”，而是建立一套可持续复用的后台页面生产方式。

必须满足：

1. 页面骨架统一
2. 表格能力统一
3. 分页能力统一
4. 弹窗壳统一
5. 页面通过配置驱动生成
6. 允许受控扩展，但不允许推翻壳子

边界说明：

1. 本次标准页组件库优先服务管理端后台页面
2. 教练网页端不直接复用“管理端标准列表页壳”
3. 教练网页端仅允许按需复用底层基础能力与部分标准单元格

## 3. 技术分层

建议把标准页体系分成四层：

### 3.1 基础 UI 层

职责：

1. 最基础的可复用 UI 单元
2. 不关心业务语义

包含：

1. 按钮
2. 输入框
3. 下拉框
4. 日期选择器
5. 标签
6. 提示反馈

特点：

1. 只负责样式和交互基础能力
2. 不直接承载页面逻辑

### 3.2 标准页能力层

职责：

1. 封装标准页的核心公共能力
2. 是后续页面真正复用的主层

包含：

1. `PageShell`
2. `ExplainBanner`
3. `StatCards`
4. `FilterBar`
5. `TableToolbar`
6. `DataTable`
7. `Pagination`
8. `StandardModal`
9. `ConfirmDialog`
10. `ToastFeedback`

特点：

1. 负责统一页面结构
2. 负责统一表格和分页行为
3. 负责统一弹窗框架

### 3.3 页面适配层

职责：

1. 把某个业务页面的字段、筛选项、列、弹窗定义映射到标准页能力层
2. 属于“配置 + 少量扩展逻辑”

包含：

1. 页面配置对象
2. 页面特有单元格渲染函数
3. 页面特有统计计算
4. 页面特有字段转换

特点：

1. 不允许自己重写整页结构
2. 只允许在标准能力预留的扩展口工作

### 3.4 业务数据层

职责：

1. 数据加载
2. 数据转换
3. 保存
4. 删除
5. 业务校验

特点：

1. 与 UI 层解耦
2. 能被页面适配层调用

## 4. 目录组织建议

当前项目不是现代框架化组件工程，因此第一版不建议做大迁移，而应在现有目录里建立清晰边界。

建议结构：

1. `public/assets/scripts/core/`
   - 放基础状态、通用工具、公共渲染 helper

2. `public/assets/scripts/standard/`
   - 放标准页能力层
   - 例如：
     - `page-shell.js`
     - `filter-bar.js`
     - `data-table.js`
     - `pagination.js`
     - `standard-modal.js`
     - `table-cells.js`

3. `public/assets/scripts/page-configs/`
   - 放页面配置层
   - 例如：
     - `students.config.js`
     - `campusmgr.config.js`

4. `public/assets/scripts/pages/`
   - 放页面入口文件
   - 页面入口负责：
     - 注册配置
     - 调用标准页能力
     - 绑定页面特有动作

这个结构的目的不是追求完美，而是让后续线程知道：

1. 什么是公共层
2. 什么是配置层
3. 什么是页面入口层

## 5. 页面配置模型

标准页采用半配置式模型。

建议页面配置对象拆成以下部分：

### 5.1 meta

1. 页面 id
2. 页面标题
3. 页面说明
4. 是否显示解释条
5. 是否显示统计区

### 5.2 stats

1. 统计卡列表
2. 卡片取值逻辑
3. 副说明生成逻辑

### 5.3 filters

1. 搜索定义
2. 下拉筛选定义
3. 日期筛选定义
4. 默认值
5. 执行方式
6. 下拉选项数量统计规则

### 5.4 actions

1. 主按钮
2. 次按钮
3. 批量操作入口

### 5.5 table

1. 列定义
2. 排序定义
3. 列筛选定义
4. 行操作定义
5. 固定列定义

### 5.6 pagination

1. 默认每页条数
2. 可选每页条数
3. 跳页是否开启

### 5.7 modals

1. 详情弹窗
2. 新增弹窗
3. 编辑弹窗
4. 删除确认弹窗

### 5.8 data

1. 原始数据获取方式
2. 列表刷新规则
3. 保存后刷新规则
4. 删除后回退规则

### 5.9 extensions

1. 自定义单元格渲染
2. 自定义区块
3. 页面特有小逻辑

## 6. 公共层与页面层边界

### 6.1 必须进入公共层的内容

以下能力一旦稳定，必须抽进标准公共层：

1. 页面骨架
2. 搜索和筛选栏壳
3. 表格壳
4. 左右固定列能力
5. 分页器
6. 跳页逻辑
7. 每页条数切换
8. 空值统一显示
9. 额度条 / 余额条单元格
10. 标准弹窗壳

### 6.2 必须保留在页面层的内容

以下内容不应该过早进公共层：

1. 页面特有统计计算
2. 页面特有字段拼装
3. 页面特有业务校验
4. 页面特有文案细节

## 7. 扩展口规范

为了避免标准库过死，同时也防止页面绕开标准库，所有扩展必须走明确扩展口。

建议扩展口：

1. `headerExtra`
2. `extraFilters`
3. `cellRenderer`
4. `rowActions`
5. `modalSections`
6. `summaryBuilders`

规则：

1. 扩展口允许加内容
2. 扩展口不允许重写整页壳
3. 不允许页面直接覆盖公共组件内部 DOM 结构

## 8. 学员页到组件库的抽取边界

学员页不是直接整体复制为组件库，而是按以下顺序抽：

### 第一批先抽

1. 分页器
2. 左右固定列能力
3. 空值显示 helper
4. 额度条 / 余额条单元格

### 第二批再抽

1. 页面骨架
2. 搜索筛选壳
3. 标准弹窗壳

### 第三批按需补

1. 列筛选
2. 更多筛选
3. 批量操作

## 9. 新旧页面共存方案

第一阶段不可能让全站页面一起迁移，因此必须允许旧页面和新标准页共存。

共存策略：

1. 旧页面保持现状，不强制大改
2. 新标准页优先从学员管理、校区管理开始
3. 抽象出的公共能力先只服务试点页
4. 稳定后再逐步接其它页面

阶段路线必须明确：

1. 第一阶段只做局部页面验证，不做全局表格壳替换
2. 第二阶段将已验证稳定的能力收编进全局标准能力层
3. 第三阶段再逐页迁移其它页面接入全局标准能力

必须避免两个错误方向：

1. 一开始就全局替换，导致大范围回归风险
2. 永远只在页面局部修补，最终无法形成标准库

这样做的目的：

1. 降低冲突
2. 降低回归风险
3. 避免一次性大重构

## 10. 禁止事项

为了保证真正组件化，后续线程必须遵守以下禁止事项：

1. 禁止直接复制学员页整段 HTML 到其它页面
2. 禁止页面绕开分页器自己写一套分页
3. 禁止页面绕开标准表格自己写左右固定列逻辑
4. 禁止页面自行定义空值规则
5. 禁止页面在标准能力之外私写新表格风格

## 11. 技术架构完成标准

当以下条件满足时，可视为第一版技术架构成立：

1. 学员页不再依赖私有分页结构
2. 学员页固定列能力可被其它页面复用
3. 校区页能接入同一套分页和表格壳
4. 页面入口层、配置层、公共层职责清晰

## 12. 结论

标准页组件库的最优技术方案不是“抽一些函数”，而是建立：

1. 公共能力层
2. 页面配置层
3. 页面入口层
4. 业务数据层

只有这样，后续线程才能在不破坏标准的前提下持续扩展。
