## 结论

1. 本轮范围内未发现 `cleanup-*`、`finalize-*`、`archive-*` 脚本。
2. 大多数写入脚本已有默认 dry-run、`--write` 写入闸门和线上 `/api/diag` 实例一致性校验。
3. 主要缺口是：多数历史导入/修数脚本没有 `operationId / batchId`，报告多为控制台输出，无法稳定被 `validate-finance-operation --operation-id` 和 `rollback-finance-operation-dry-run` 追踪。
4. P0 风险集中在会影响课包、权益、消课流水、订场流水的大批量导入或修数脚本。

## 风险分级

- `P0`：触达财务或权益核心表，且批量写入、删除、修正历史流水，必须优先补齐追踪和回滚 dry-run 能力。
- `P1`：触达核心业务表，但影响面较小，或已有部分 `operationId / batchId`。
- `P2`：只读预检查、线索类写入、索引修复等，仍需生产安全闸门，但财务风险较低。

## 必须补齐的安全能力

P0/P1 写入脚本建议统一补齐：

1. `operationId / batchId`：所有新增、更新、修正行都必须写入；删除动作必须在报告中记录被删记录快照。
2. dry-run 报告：dry-run 和 write 都应生成落盘 JSON 报告，记录目标实例、触达表、记录 ID、金额变化、删除清单。
3. 线上实例校验：写入前必须校验本地目标实例和线上 `/api/diag` 一致；不一致直接失败。
4. validate 识别：写入后可用 `validate-finance-operation --operation-id` 查到业务表和财务变化摘要。
5. rollback dry-run 识别：可用 `rollback-finance-operation-dry-run --operation-id` 输出建议回滚动作，不做真实回滚。
